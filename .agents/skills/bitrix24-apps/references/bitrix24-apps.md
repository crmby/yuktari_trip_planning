## Коротко: 15 правил, которые нельзя нарушать

1. **Ключ живёт только на сервере.** Его нельзя класть в браузер, в JS-бандл, в URL, в `localStorage`, в Git или в чат-ответ. Храните ключ в переменных окружения или в секретах платформы [VC Keys & Auth].
2. **Первый вызов — `GET /v1/me`.** Он показывает тип ключа, портал, скоупы, `capabilities` и тариф. Модель строит дальнейшие запросы по нему [VC Quick Start].
3. **Для аналитики берите ключ только на чтение** (`READONLY`) с минимальными скоупами: для дашборда по CRM это `crm` и `user` [VC Scopes, App runtime].
4. **Личный ключ `vibe_api_` действует от имени своего владельца.** Любой посетитель приложения увидит данные владельца ключа. Поэтому сервисный дашборд держите закрытым (`OWNER_ONLY` / `NAMED_USERS`) [VC App runtime].
5. **Встраивание в интерфейс Битрикс24 через VibeCode возможно только с ключом авторизации `vibe_app_`.** Личный ключ `vibe_api_` этого не умеет [VC Keys & Auth].
6. **Не открывайте доступ шире без явного «да» пользователя.** Это касается смены `accessPolicy` с `OWNER_ONLY` на более открытую, `PUBLIC` и режима OPEN [VC Infrastructure, Access].
7. **Внутри приложения, открытого через обработчик VibeCode, BX24 JS SDK не работает.** `BX24.init` не завершается, `BX24.placement.info()` возвращает `null`. Контекст берите из параметров URL [VC App runtime].
8. **Домен портала берите только из `GET /v1/me` → `data.portal`.** Строке запроса и `ancestorOrigins` доверять нельзя [VC App runtime].
9. **Не грузите все данные при открытии страницы.** Шлюз VibeCode ждёт заголовки ответа приложения не дольше 14 секунд. Готовьте данные заранее в фоне и отдавайте кэш [VC App runtime].
10. **Для подсчётов используйте `POST /v1/{entity}/aggregate`, а не выгрузку всех записей.** У агрегации есть потолок в 5000 записей — проверяйте `meta.truncated` [VC Entity API].
11. **Разрешите показ во фрейме Битрикс24.** Не отдавайте `X-Frame-Options` и пропишите портал в CSP `frame-ancestors` [Б24-док; VC].
12. **Проверяйте `application_token` у событий и обращений от Битрикс24** [Б24-док; VC Event subscriptions].
13. **Деплой на VM может провалиться с HTTP 200.** Проверяйте поле `success` и шаги `data.steps[]`. Таймаут клиента ставьте не меньше 690 секунд [VC Deploy].
14. **Создание сервера, деплой на спящий сервер и включение «всегда онлайн» — это расход Вайбов.** Делайте это только с согласия пользователя [VC Pricing].
15. **«Готово» означает, что вы проверили работу в боевой среде.** Открыть приложение из Битрикс24, открыть ссылку в приватном окне браузера (как посторонний), убедиться, что ключа нет в браузере. Остальное — «сделано локально, не проверено».

## 0. Как пользоваться этим файлом: порядок действий агента

1. **Уточните задачу одним-двумя вопросами, если пользователь не сказал сам:**
   - что делает приложение;
   - кто им пользуется: только владелец, сотрудники портала или внешние клиенты;
   - где оно открывается: внутри Битрикс24, по отдельной ссылке или работает в фоне;
   - только читает CRM или пишет в неё;
   - портал облачный или коробочный;
   - где размещать (раздел 5.3).
2. **Выберите способ интеграции** по таблице в разделе 1.
3. **Определите, какие ключи нужны** (раздел 2). Попросите пользователя самого положить ключ в `.env` на сервере или в секреты приложения на платформе. Если пользователь всё же вставил ключ в чат (Quick Start VibeCode это допускает), запишите его только в `.env`, проверьте, что `.env` в `.gitignore`, и больше нигде его не повторяйте.
4. **Вызовите `GET /v1/me`** и проверьте:
   - тип ключа;
   - портал (`data.portal`);
   - `scopes`;
   - `capabilities.servers.create.available`;
   - `placements.bindPrerequisite`;
   - `b24Credentials.ready`;
   - `data.capabilities.servers.preview` (доступны ли токены доступа).
5. **Сверьте поля сущностей** через `GET /v1/guide` и `GET /v1/{entity}/fields`. Имена полей в VibeCode отличаются от имён в Битрикс24 (раздел 3.7).
6. **Спроектируйте приложение по схеме «сервер-посредник»** (BFF): сервер ходит в API, браузер получает только готовые агрегаты. Решите, как и когда обновляется кэш (раздел 8).
7. **Возьмите подходящий шаблон** (раздел 6) и начните с его `INDEX.md` и `AGENTS.md`.
8. **Реализуйте и проверьте офлайн**: линтер и тесты без реальных данных.
9. **Выложите** (раздел 5) и **встройте** (раздел 4).
10. **Пройдите чек-лист «готово»** (раздел 10).
11. **Отчитайтесь**: что изменено, что реально проверено и где, что не проверено, какие есть блокеры.

## 1. Карта способов интеграции с Битрикс24

### 1.1. Способы

**Входящий вебхук Битрикс24** [Б24-док]
- Это секретный адрес вида `https://<портал>/rest/<id_сотрудника>/<секрет>/<метод>.json`.
- Запросы выполняются с правами сотрудника, который создал вебхук, и только в рамках выбранных скоупов. Можно задать срок действия.
- Ограничения: интерфейса внутри Битрикс24 нет. Методы, которым нужен контекст приложения, недоступны — например, `placement.bind`, часть телефонии, часть сценариев чат-ботов.
- Создаётся в Битрикс24 в пункте «Разработчикам» левого меню. В классическом интерфейсе он находится в группе «Приложения».

**Исходящий вебхук** [Б24-док]
- Битрикс24 отправляет POST на ваш адрес при наступлении события.
- В запросе приходят `event`, `data`, `ts` и `auth` с полями `domain`, `member_id`, `application_token`.
- `auth[application_token]` нужно сверять с токеном, который показан при создании вебхука.

**Локальное приложение Битрикс24** [Б24-док]
- Бывает трёх видов: статическое (HTML/JS без сервера, событий не получает), серверное с интерфейсом (страница во фрейме и события) и серверное без интерфейса (фоновые задачи).
- Работает по OAuth 2.0: `client_id` вида `local.xxxx.yyyy` и `client_secret` из карточки приложения.
- Пользователь открывает приложение во фрейме портала.

**Приложение Маркетплейса** (общий REST Б24)
- Тиражное приложение: один код обслуживает много порталов.
- Публикуется через партнёрский кабинет и модерацию.
- Изоляция данных строится по `member_id`.

**Платформа VibeCode** [VC] — надстройка над Битрикс24. Её части:
- **Прокси-API `https://vibecode.bitrix24.tech/v1`** — единый REST для сущностей Битрикс24 (`/v1/deals`, `/v1/leads` и др.) по ключу VibeCode.
- **Личный ключ `vibe_api_`** — ходит в портал через вебхук портала от имени владельца ключа [VC Errors: Auth].
- **OAuth-приложения `/v1/apps` + ключ `vibe_app_`** — регистрируют на портале настоящее локальное OAuth-приложение и дают встраивание (placements) и «прозрачную» авторизацию сотрудников [VC Apps].
- **Хостинг Black Hole** — серверы и galaxy-контейнеры, деплой по API, HTTPS-субдомен `app-xxxxxxxx.vibecode.bitrix24.tech`, шлюз Gateway с политиками доступа, сон и пробуждение, свой домен, SQLite, управляемая доставка событий [VC Infrastructure].
- **Витрина приложений (`/v1/applications`), секреты приложения, вход внешних пользователей (App login), внешний API приложения** [VC Application catalog].
  - `id` из `/v1/applications` и `id` из `/v1/apps` — **разные** сущности и не взаимозаменяемы: подстановка `id` витрины в `/v1/apps/...` даёт `404`.
- **Чертежи приложений (App Blueprints)** — готовые ТЗ [VC App Blueprints]:
  - `GET /v1/app/blueprints/:slug?locale=ru` возвращает сырой markdown (не JSON);
  - скоуп не нужен, подходит любой ключ, привязанный к порталу;
  - список `slug` отдельно не публикуется — ссылку даёт промпт из кабинета (`/blueprints`);
  - раздел открывают порталам по очереди, пока он закрыт — `403 BLUEPRINTS_DISABLED`;
  - в ТЗ приложение ходит в Б24 одним ключом владельца.
- **AI-агенты** — автономный бот в чатах Б24 на собственном облачном сервере (рантайм Hermes) [VC Agents]:
  - создаются только в кабинете `/agents`; через API доступно лишь чтение (`GET /v1/agents`);
  - по умолчанию сервер вытесняемый; лимит `maxAgentsPerUser` — 3 по умолчанию;
  - к приложениям-дашбордам отношения не имеют.
- **Коворк/Код** — подписка на AI-квоту для десктопа, режима Code и агентов [VC Cowork]:
  - окна квоты: 5 часов, неделя, месяц; тарифы Free, Pro ×1, Max ×5, Ultra ×20;
  - ключ Коворк/Код (`vibe:cowork`) — только для данных; для деплоя нужен проектный ключ `POST /v1/cowork/deploy-key`.
- **Требования к доступу** [VC Quick Start, Infrastructure]:
  - в России нужна активная подписка BitrixGPT + Маркетплейс;
  - в Казахстане и Узбекистане — платный или демо-тариф Битрикс24;
  - в Беларуси — платный или демо-тариф Битрикс24 либо платная подписка Битрикс24 Маркет Плюс.
- **Без коммерческого тарифа REST самого Битрикс24 не работает.** Вместе с ним перестают работать и прокси `/v1/deals`. На бесплатном тарифе приходит `B24_PAID_TARIFF_REQUIRED`, на «Демо» REST работает [VC Infrastructure, Errors].
- **Коробочный портал** нужно сначала подключить к платформе [VC Connect Self-Hosted Bitrix24].

### 1.2. Когда что выбирать

| Задача | Что выбрать | Почему |
|---|---|---|
| Скрипт, отчёт или выгрузка для себя, без интерфейса в Б24 | `vibe_api_` (VibeCode) или входящий вебхук | Один заголовок, работает от имени владельца, подходит для cron [VC Quick Start] |
| Фоновая автоматизация по расписанию | `vibe_api_` | Сессия `vibe_app_` живёт 24 часа и не продлевается — скрипту нечем заново пройти авторизацию [VC Quick Start] |
| Дашборд руководителя внутри Б24, данные «как у владельца» | `vibe_api_` с режимом `READONLY` на сервере для данных + встраивание через OAuth-приложение VibeCode (`vibe_app_`) или через локальное приложение | Ключ на сервере. Доступ закрыть политикой `OWNER_ONLY` / `NAMED_USERS` или проверкой пользователя |
| Приложение для сотрудников, каждый видит данные по своим правам | `vibe_app_` + сессия пользователя (per-user) или локальное приложение OAuth | Запросы идут от имени открывшего сотрудника [VC Keys & Auth] |
| Тираж на много порталов (Маркетплейс) | Свой multi-tenant сервер, шаблон `_b24-marketplace-php` | OAuth-приложение VibeCode привязано к одному порталу, для другого портала его регистрируют заново [VC Apps] |
| Реакция на события (новый лид, задача) | VibeCode: управляемые подписки на сервере под `vibe_app_`. Свой сервер: `event.bind` на ваш HTTPS | Подробно в разделе 5 |
| Клиенты без доступа к вашему Б24 | VibeCode App login (SDK `@bitrix24/vibecode-auth`, только на сервере платформы) или своя авторизация | [VC App login] |
| Вызов вашего приложения из внешней системы | VibeCode «Внешний API приложения» или свой API | [VC External API] |
| Чат-бот | VibeCode Bot Platform (скоупы `imbot`, `im`) | [VC Bots] — в этом справочнике не разбирается |

### 1.3. Чем отличаются схемы

| | Входящий вебхук | Локальное приложение (OAuth) | Маркетплейс | VibeCode `vibe_api_` | VibeCode `vibe_app_` |
|---|---|---|---|---|---|
| От чьего имени запросы | создатель вебхука | пользователь, открывший приложение (токены `AUTH_ID`) | пользователь портала-установщика | владелец ключа | пользователь с сессией `vibe_session_` |
| Интерфейс во фрейме Б24 | нет | да | да | нет | да (места встраивания) |
| Порталов | один | один | много | один | один |
| Где хранятся токены | вебхук на вашем сервере | ваш сервер (`AUTH_ID`/`REFRESH_ID`) | ваш сервер, отдельно на каждый `member_id` | ключ на сервере, вебхук держит платформа | токены портала держит платформа, у вас `vibe_session_` (24 ч) |
| Нужен VibeCode | нет | нет | нет | да | да |

## 2. Ключи и секреты: все виды

### 2.1. Сводная таблица

| Что | Формат | Где взять | Что даёт | Где хранить | Чего нельзя |
|---|---|---|---|---|---|
| **Личный API-ключ VibeCode** | `vibe_api_…`. Ключ, выданный через Коворк/Код: `vibe_api_` + 32 символа + `_` + 6 hex, всего 48 символов [VC Cowork] | Кабинет → «Ключи API» (`/keys`) | Доступ к данным **одного** портала от имени владельца. Заголовок `X-Api-Key` или `Authorization: Bearer` [VC Keys & Auth] | env сервера / секрет приложения | Нельзя в браузер и Git. | **Ключ авторизации (OAuth-приложения)** | `vibe_app_…` | Кабинет → «Ключи авторизации» (`/apps`) или `POST /v1/apps` (поле `rawKey`, показывается **один раз**) [VC Apps] | Встраивание в Б24 и запросы от имени пользователя. Нужна пара заголовков: `X-Api-Key: vibe_app_…` + `Authorization: Bearer vibe_session_…` | env сервера | Нельзя передавать в `Authorization: Bearer` → `401 WRONG_AUTH_SCHEME` [VC Keys & Auth] |
| **Токен сессии пользователя** | `vibe_session_…` | `POST /v1/oauth/token`, `POST /v1/oauth/placement-session`; на Black Hole Gateway кладёт его в заголовок `X-Vibe-Authorization` | Действие от имени пользователя. | **Ключ Коворк/Код** | префикс в документации не назван, скоуп `vibe:cowork` | Десктоп Коворк/Код | Только данные: чат, REST-прокси. Инфраструктура → `403 INFRA_FORBIDDEN_FOR_COWORK_KEY` [VC Cowork] | — | — |

API принимает только имена [VC App secrets] | Попадают в приложение как переменные окружения | Платформа | Нельзя имя `PORT` и префиксы `VIBE_`, `HERMES_EVENT_INGEST_`. До 100 имён. Значение видит любой, кто выполняет команды на машине |
| **Токен доступа `api-bearer`** | JWT | `POST /v1/infra/servers/:id/access-tokens` | E2E-проверка через публичный путь. JWT живёт до 10 минут, продлевается через `/refresh` [VC Access tokens] | Короткоживущий, в CI | Не подменять им запросы от имени пользователя |

| **Входящий вебхук Б24** | `https://<портал>/rest/<user_id>/<секрет>/` | Б24 → «Разработчикам» | Полный доступ в рамках скоупов, с правами создателя [Б24-док] | env сервера | **Это пароль.** Нельзя в клиентский код и в URL логов. Для рабочих интеграций лучше POST [Б24-док] |

В VibeCode `client_id` виден как `bitrixClientId`, секрет не возвращается никогда [VC Apps] | OAuth-обмен и продление токенов | env / приватный файл с правами 0600 | Секрет не в Git и не в браузер |

### 2.2. Правила обращения с ключами

- **Хранение.** Переменные окружения или менеджер секретов — не код и не Git. Не передавайте ключи через мессенджеры и почту. Давайте ключу только нужные скоупы. Заводите отдельный ключ на каждый сервис. Для серверных интеграций включайте белый список IP и конечный срок действия. Перевыпускайте ключи по расписанию, например раз в 90 дней [VC Keys & Auth].
- **Репозиторий.** В репозиторий кладите только `.env.example` с заглушками (`VIBE_API_KEY=vibe_api_XXXX`). Сам `.env` — в `.gitignore`. Перед коммитом проверьте staged diff на секреты.
- **Ключ показывается один раз.** Если он потерян, ключ перевыпускают [VC Keys & Auth].
- **Срок действия:** без ограничения, 30, 90, 180 или 365 дней. После истечения приходит `401 KEY_EXPIRED`, при этом `status` остаётся `ACTIVE` [VC Keys & Auth].
- **Белый список IP:** только точные адреса IPv4/IPv6, подсети CIDR не поддерживаются. Запрос с другого адреса → `403 IP_NOT_ALLOWED` [VC Keys & Auth].
- **Режим доступа** (`accessMode`): `READWRITE` (по умолчанию) или `READONLY`. Запись ключом `READONLY` → `403 WRITE_BLOCKED_READONLY_KEY`. Платформенные исключения из запрета (деплой, exec, upload, `POST /v1/apps` и др.) перечислены в `GET /v1/me` → `writeRestriction.exceptions` [VC Access mode].
- **Скоупы Битрикс24 закрепляются в момент выпуска ключа.** Если добавить скоуп существующему ключу, `/v1/me` его покажет, но запросы получат `BITRIX_ACCESS_DENIED`. Решение: перевыпустить ключ. Для `vibe_app_` — перевыпустить ключ авторизации на карточке приложения и авторизоваться заново [VC Keys & Auth]. Через `PATCH /v1/apps/:id` право Б24 добавить нельзя → `403 OAUTH_SCOPE_CHANGE_REQUIRES_REISSUE`, сузить набор можно [VC Apps].
- **Скоупы VibeCode** (`vibe:infra`, `vibe:ai`, `vibe:search`, `vibe:storage`, `vibe:feedback`) в форме создания отмечены заранее. Снимайте лишние [VC Scopes].
- **Перевыпуск.** Старый ключ работает ещё до 24 часов, но не дольше своего срока [VC Keys & Auth].
- **Отзыв.** В кабинете: «Деактивировать» → `REVOKED`. Другие серверы платформы могут ещё до ~5 минут принимать ключ, потом → `401 KEY_INACTIVE` [VC Keys & Auth].
- **Готовность ключа к вызовам Б24.** `status: ACTIVE` ещё не гарантирует, что вызовы к порталу пройдут. У `vibe_api_` может не оказаться вебхука портала, и тогда любой вызов к порталу вернёт `401 TOKEN_MISSING`. Признак — `GET /v1/me` → `b24Credentials.ready`. Лечится пунктом «Переподключить» в меню ключа. Ответ `/v1/me` кэшируется на 30 секунд, поэтому после починки читайте `GET /v1/me?refresh=tariff` [VC Keys & Auth].
- **Владельца ключа уволили** → `403 OWNER_BLOCKED` на всех его ключах, приложениях, ботах и агентах [VC Keys & Auth].

### 2.3. Сколько ключей можно создать («слоты»)

[VC Keys & Auth, Cowork]

- **Лимит на пользователя портала.** По умолчанию и максимум — 100. Администратор задаёт значение от 1 до 100: «Настройки» → «Лимиты для пользователей» → «Макс. ключей на пользователя».
- **Портальный потолок платформы.** Считается по всем живым ключам портала. Администратор его не поднимает.
- **Что входит в счёт:**
  - личные ключи `vibe_api_`;
  - ключи авторизации `vibe_app_` — каждый `POST /v1/apps` создаёт новый ключ;
  - ключи агентов;
  - проектные ключи деплоя;
  - ключи, выписанные самой платформой. Поэтому `used` бывает больше, чем список ключей в кабинете.
- **Что не входит:** ключ десктопа Коворк/Код.
- **Истёкший ключ место не освобождает.** Освобождает только отзыв («Деактивировать»).
- **Отказ:** `409 KEY_LIMIT_REACHED`, в `error.details` приходят `limit`, `used`, `requested`. Поле `scope: "portal"` означает, что сработал портальный потолок. Если поля `scope` нет, сработал лимит пользователя.
- **Состояние квоты заранее:** `GET /v1/cowork/applications/defaults` → `data.quota.keysUsed` / `keysLimit`. В примере документации `keysLimit: 10`.

## 3. Работа с API

### 3.1. Основы VibeCode API [VC Entity API, Keys & Auth, Errors]

- **Базовый адрес:** `https://vibecode.bitrix24.tech/v1`. Сущности — `/v1/{entity}` во множественном числе: `deals`, `leads`, `contacts`, `companies`, `tasks`, `users`, `statuses`, `items/{entityTypeId}` и др.
- **Авторизация:** `X-Api-Key: vibe_api_XXXX`. Для `vibe_app_` дополнительно `Authorization: Bearer vibe_session_XXXX`. Эндпоинты `/v1/me`, `/v1/guide` и `/v1/oauth/*` работают без Bearer.
- **Схема полей тоже требует сессию.** `GET /v1/{entity}/fields` и `GET /v1/userfields/*` у ключа `vibe_app_` работают только с сессией. Чтобы прочитать поля до появления сессии, используйте `vibe_api_` или `GET /v1/guide` (`data.entities[].fieldsDetailed`) [VC Keys & Auth].
- **Тело запроса** — только JSON: `Content-Type: application/json`. `multipart/form-data` на `/v1` не поддерживается, кроме деплоя и иконки. `text/plain` → `415 FST_ERR_CTP_INVALID_MEDIA_TYPE`.
- **Размер тела:** по умолчанию до 1 МБ, при создании и обновлении записей — до 40 МиБ. Больше → `413 PAYLOAD_TOO_LARGE`.
- **Успешный ответ:** `{ "success": true, "data": …, "meta": {…} }`. У `list` и `search` в `data` массив, у `get` и `create` — объект.
  - `create` → HTTP 201.
  - `DELETE` → HTTP 204 с пустым телом.
- **Ошибка:** `{ "success": false, "error": { "code", "message", … } }`. Дополнительные поля бывают такие: `hint`, `userMessage`, `details`, `retryAfter`, `b24Code`, `requiredScope`, `keyScopes`, `fix`, `cause`. **Ветвитесь по `error.code`**, а не по тексту: язык сообщения заранее неизвестен.
- **Самоописание:**
  - `GET /v1/me` — ключ, портал, скоупы, лимиты, `capabilities`, тариф;
  - `GET /v1/guide` — контракт полей всех сущностей;
  - `GET /v1/openapi.json` — OpenAPI 3.1, авторизация не нужна; есть срез `?scope=crm`;
  - у `openapi.json` и `guide` работает `ETag` / `If-None-Match` → `304`.
- **Часовой пояс при записи дат:** заголовок `X-Vibe-Timezone: Europe/Moscow` (IANA). Сейчас действует только на проверенные поля задач.
- **Windows PowerShell портит кириллицу в `-Body`.** Передавайте тело байтами: `[System.Text.Encoding]::UTF8.GetBytes($body)`. Node.js `fetch` и Python `requests` кодируют UTF-8 сами [VC Infrastructure].
- **curl со скобочными фильтрами:** нужен флаг `-g` (`--globoff`), а URL берите в одинарные кавычки. Иначе ошибка `bad range in URL` [VC Filtering].

### 3.3. Пагинация [VC Entity API, Filtering, Optimization]

- **Автопагинация.** При `limit > 50` платформа сама собирает страницы по 50 и отдаёт до 5000 записей одним ответом. Если записей больше, приходят первые 5000 и `meta.hasMore: true`.
- **Конец выборки определяйте по `meta.hasMore`, а не по `meta.total`.** `total` необязателен и может отставать до минуты.
- **Курсор — лучший способ для десятков тысяч записей.** Сортируйте строго `order[id]=asc`, и в ответе придёт `meta.nextAfterId`. Передайте его обратно как `filter[>id]=<nextAfterId>`. Курсор есть у сделок, лидов, контактов, компаний, предложений и элементов смарт-процессов.
  ```
  GET /v1/deals?order[id]=asc&limit=50&withTotal=false&select=id,title&filter[>id]=<nextAfterId>
  ```
- **Большие `offset` опасны.** `offset ≥ 2500` может дать `INTERNAL_ERROR`, на больших смещениях держите `limit ≤ 500`. Параллельные запросы с разными `offset` на одном фильтре → `400 UNSTABLE_OFFSET_PAGINATION`.
- **Частичный провал страниц.** Если часть страниц не загрузилась, ответ всё равно `200`, а рядом приходит `meta.pageErrorSample` (`KEYSET_DISCONTINUITY`, `PAGE2_COUNT_FAILED`, `LAZY_COUNT_NO_PROGRESS`, `QUERY_LIMIT_EXCEEDED`). Проверяйте это поле.
- **Поиск с диапазоном дат больше 14 дней** автоматически режется на окна по 7 дней. Неполная выдача отмечается `meta.warnings[].code = WINDOW_TRUNCATED`. Отключается параметром `autoWindow: false`.
- **Счётчик записей обходом не считают** — для этого есть `aggregate` с `count`.

### 3.4. `select`, сортировка, `include` [VC Entity API, Includes]

- **`select`:** `?select=id,title` или `?select[]=id&select[]=title`. Поле `id` возвращается всегда.
  - Незнакомое имя поля у сверенных сущностей (сделки, лиды, контакты, компании) → `400 UNKNOWN_SELECT_FIELD`.
  - `*` или `UF_*` — все поля.
- **`include` — связанные данные:** `?include=contact,company`. Данные приходят в `data._included`. Допустимые имена перечислены в `/fields` → `data.include`: у сделок `contact`, `company`; у лидов `contact`, `company`, `contactBinding`.

### 3.5. Агрегация [VC Entity API, Recipe CRM analytics]

```json
POST /v1/leads/aggregate
{
  "aggregate": [{ "field": "*", "function": "count" }],
  "filter": { "createdAt": { "$gte": "2026-10-01T00:00:00", "$lte": "2026-10-31T23:59:59" } },
  "groupBy": "sourceId"
}
```

- **Функции:** `count` (с полем `"*"`), `sum`, `avg`, `min`, `max`. Без массива `aggregate` считается только `count`.
- **`groupBy`:** до 5 полей и только из списка `aggregatable` сущности.
  - Сделки: `amount`, `stageId`, `stageSemanticId`, `categoryId`, `assignedById`, `sourceId`, `currency`.
  - Лиды: `stageId`, `statusId`, `opportunity`, `amount`, `sourceId`, `assignedById`, `currencyId`.
- **Ответ:** `data.count`, `data.aggregates`, `data.groups[]` (только при `groupBy`), `data.meta.{totalRecords, recordsProcessed, truncated, recordsShortfall, warnings}`.
- **Потолок 5000 записей.** Для `sum`/`avg`/`min`/`max` и `groupBy` платформа подгружает не больше 5000 записей. Дальше либо `meta.truncated: true` с предупреждением `AGGREGATE_TRUNCATED`, либо (на части аккаунтов) `422 AGGREGATION_LIMIT_EXCEEDED`. **Обрабатывайте обе ветки.** Поле `meta.truncated` приходит всегда — проверяйте его значение.
- **Деньги в разных валютах** → `AGGREGATE_MIXED_CURRENCIES`. Группируйте по валюте.
- **Пустые группы не приходят.** Стадии и источники без записей в `groups` отсутствуют — дорисовывайте нули сами.

### 3.6. Фильтры: три синтаксиса [VC Filtering]

Фильтры работают в `GET ?filter[...]` (скобочная форма или URL-кодированная JSON-строка; смешивать эти формы нельзя → `400 INVALID_FILTER`) и в теле `POST …/search` как `{"filter":{…}}`.

1. **Операторы `$`:** `$gt`, `$gte`, `$lt`, `$lte`, `$ne`, `$contains`, `$in`, `$nin`. Точное совпадение — значение без оператора.
   ```json
   {"filter":{"amount":{"$gte":50000,"$lte":200000},"stageId":{"$ne":"LOST"}}}
   ```
2. **Префикс в имени поля** (форма, которую понимает Битрикс24): `>=`, `>`, `<=`, `<`, `!`, `%`.
   ```json
   {"filter":{">=amount":50000,"<=amount":200000,"!stageId":"LOST"}}
   ```
3. **Оператор как ключ вложенного объекта:**
   ```json
   {"filter":{"amount":{">=":50000},"stageId":{"!":"LOST"}}}
   ```

Правила:
- **Все условия объединяются через И.** `LOGIC: "OR"` и `$or` → `400 INVALID_FILTER_OPERATOR`. «ИЛИ» по одному полю делается через `$in`. «ИЛИ» по разным полям — отдельными вызовами (например, в batch) со склейкой по `id`.
- **Префиксы Б24 `@` и `!@` не поддерживаются** → используйте `$in` / `$nin`.
- **Ключи `from`/`to` не поддерживаются.** Диапазон задаётся как `$gte` + `$lte`.
- **Пустые значения:** «поле заполнено» — `{"$ne": null}`, «поле пусто» — `null`. В GET пустое значение передаётся так: `?filter[x]=`.
- **Даты:** ISO 8601. Строка без пояса читается в поясе пользователя ключа. Знак `+` в query кодируйте как `%2B`.
- **Неизвестное поле** → `400 UNKNOWN_FILTER_FIELD` со списком доступных полей. Сам Битрикс24 неизвестный ключ фильтра молча отбрасывает и возвращает всю коллекцию.
- **Два написания одного поля** (`amount` + `OPPORTUNITY`) → `400 INVALID_DUPLICATE_FILTER_FIELD`.
- **Телефон** сравнивается целой строкой и только по первому номеру. Для поиска по номеру есть `POST /v1/duplicates/find`.

### 3.7. Форматы полей [VC Entity API, Deals, Leads]

- **Имена полей.** В запросах всегда camelCase. Имена в VibeCode могут отличаться от Битрикс24: сумма сделки — `amount` (в Б24 `opportunity`). Исходное имя Б24 в ответах не возвращается.
- **Лиды:**
  - канонические имена в ответах — `stageId`, `opportunity`, `currencyId`;
  - псевдонимы для записи и фильтра — `statusId`, `amount`, `currency`;
  - дата создания — `createdTime`, в фильтре принимается и псевдоним `createdAt`;
  - чтобы записанная сумма не затёрлась, передавайте `isManualOpportunity: true`.
- **Сделки:** `createdAt`, `updatedAt`, `closedAt`. `isWon`, `isLose` и др. приходят только в явном `select`, в фильтре не принимаются.
- **Источник** — `sourceId`. Его значения — коды из `GET /v1/statuses?filter[entityId]=SOURCE`.
- **UTM-поля** (`utmSource`, `utmMedium`, `utmCampaign`, `utmContent`, `utmTerm`) у лидов и сделок возвращаются при чтении, но **не принимаются в фильтре и сортировке** → `400 UNKNOWN_FILTER_FIELD` / `UNKNOWN_SORT_FIELD`.
- **Стадии:** `GET /v1/statuses?filter[entityId]=DEAL_STAGE` (для других воронок `DEAL_STAGE_{N}`), у лидов `STATUS`. Смысл стадии — `stageSemanticId`: `P` (в работе), `S` (успех), `F` (провал).
- **Даты на чтение:** у сделок datetime в UTC (`…Z`), у лидов, контактов и прочих — со смещением портала (`+03:00`). Приводите к одному поясу перед группировкой по дням.
- **Пользовательские поля:**
  - имена берутся только из `/fields` (`ufCrm…`). Запись под чужим именем молча не сохраняется, хотя ответ 200/201;
  - `money` — строка `"100|USD"`;
  - булевы у сделок `true`/`false`, у остальных сущностей CRM `"Y"`/`"N"`;
  - список (`enumeration`) — передаётся ID варианта;
  - множественные поля — массив, который заменяет набор целиком.
- **Мультиполя** email/phone при записи: `[{ "value": "…", "typeId": "WORK" }]`.

### 3.8. Batch [VC Batch]

- **Общий пакет `POST /v1/batch`:**
  - тело `{ "calls": [ … ] }`, от 1 до **50** вызовов;
  - вызов: `{ "id": "a1", "entity": "deals", "action": "list|get|create|update|delete|fields|search", "entityId": 123, "params": {…} }`. Для `get`/`update`/`delete` передавайте `entityId`, а не `params.id`;
  - вызовы независимы. Ссылок между вызовами документация не описывает.
- **Частичные ошибки.** Ответ `success: true`, даже если часть вызовов провалилась. Проверяйте `data.summary.failed` и `data.errors.<id>`. Результаты лежат в `data.results.<id>`.
- **Стоимость в единицах лимита Б24.** `list` с `limit ≤ 50`, `get`, `create`, `update`, `delete` и `fields` склеиваются в один нативный batch Б24 — 1 единица. `search` и `list` с `limit > 50` идут отдельно.
- **Через batch недоступны:** чаты, сообщения, лента, база знаний, звонки, рабочий день.
- **Пакет по одной сущности** `POST /v1/{entity}/batch` — до 500 записей. Ошибка в одном элементе отклоняет весь запрос → `400 BATCH_ITEM_VALIDATION`.

### 3.9. Лимиты и ограничение скорости [VC Keys & Auth, Optimization, Errors: Limits]

| Механизм | Цифры | Ответ |
|---|---|---|
| Граница платформы | 60 запросов/с на IP клиента, всплеск +100 | `429 RATE_LIMITED`, `Retry-After: 1` |
| Лимит портала Б24 | «10 запросов/с, общий для всех ключей портала» — так пишет VibeCode (см. противоречие ниже) | `429 RATE_LIMITED`, `Retry-After: 2` |
| Поминутные лимиты эндпоинтов | чтения по сущностям 300/мин (на сущность и операцию); `POST /v1/batch` и `POST /v1/{entity}/batch` 30/мин; `POST /v1/search` 60/мин | значения в `X-RateLimit-Limit/Remaining/Reset` |
| Общий счётчик вызывающего | 600/мин на ключ, 1200/мин на владельца | `429 CALLER_RATE_LIMITED`, `X-RateLimit-Scope` |
| Очередь портала | от ~100 вызовов в ожидании, ожидание до 80 с | `429 QUEUE_OVERFLOW` / `QUEUE_TIMEOUT` |
| Паузы по методу | ~5 мин на пару «ключ + метод»; карантин после 3 таймаутов подряд | `429 OPERATION_TIME_LIMIT` / `TIMEOUT_QUARANTINE` |
| Дневная квота (если на аккаунте включена оплата API) | `X-RateLimit-Quota`, `X-RateLimit-Used`, `X-RateLimit-Remaining` | отстают до 70 минут |

- **Таймауты.** Очередь — до 80 с. Один вызов в Б24 — до 60 с, дальше `503 BITRIX_TIMEOUT` (исход неизвестен). Соединение держится до 660 с. **Таймаут вашего клиента:** не меньше 150 с при `limit ≤ 50` и не меньше 690 с при `limit > 50`.
- **Кэш платформы.** `GET /v1/users` кэшируется на 60 с, `GET /v1/statuses` и `/fields` — на 5 минут. Обход кэша — `Cache-Control: no-cache`. Для ключей `vibe_app_` кэш не используется.
- **Как вести себя при `429`:** ждите `Retry-After`. Если заголовка нет — увеличивайте паузу (1 → 2 → 4 с, с джиттером). Снижайте параллелизм, объединяйте вызовы в batch, кэшируйте справочники.

**Классический REST Б24** [Б24-док «Лимиты REST API»]:
- Для «прочих» облачных тарифов счётчик убывает со скоростью 2 запроса/с, порог блокировки — 50. Для «Энтерпрайз» — 5 запросов/с и порог 250.
- При превышении приходит **503 `QUERY_LIMIT_EXCEEDED`**.
- Лимит ресурсоёмкости — **429 `OPERATION_TIME_LIMIT`** на пару «приложение или вебхук + метод». Учёт ведётся в 10 минутных корзинах.
- Ориентир: около 172 800 запросов в сутки при 2 запросах/с.

> **Противоречие источников.** VibeCode называет лимит портала Б24 «10 запросов/секунду». Официальная документация Б24 даёт 2/с (Энтерпрайз — 5/с). Страницы сделок и лидов VibeCode пишут ещё и про «300 в минуту на портал». Планируйте нагрузку по самому строгому значению и опирайтесь на `Retry-After`.

### 3.12. Рецепт: лиды по источникам (в том числе «YouTube»)

1. **Узнайте, как источник называется на портале.** `GET /v1/statuses?filter[entityId]=SOURCE` вернёт коды и названия. Код источника «YouTube» на конкретном портале заранее неизвестен — ищите по названию, а не угадывайте код [VC Leads].
2. **Если источник хранится в `sourceId`,** используйте одну агрегацию:
   - `POST /v1/leads/aggregate` с `groupBy: "sourceId"` (или `["sourceId","stageId"]`) и фильтром по `createdAt` за период;
   - проверьте `meta.truncated`. Если записей больше 5000 — разбейте период на месяцы или недели.
3. **Если источник хранится только в UTM-метке** (`utmSource = youtube`), фильтровать по UTM нельзя (раздел 3.7). Тогда:
   - в фоне выгрузите лиды за период курсором (`select=id,createdTime,stageId,sourceId,utmSource`, `order[id]=asc`);
   - отберите и посчитайте на сервере;
   - сохраните результат в кэш (раздел 8).
4. **Конверсия.** Доля лидов со `stageSemanticId = S`. Для сделок — по стадии `WON` / `C{N}:WON` [VC Recipe CRM analytics].
5. **Подписи.** Замените коды источников и стадий названиями из справочника `statuses`. Пустые группы дорисуйте нулями.

## 4. Встраивание в Битрикс24

### 4.1. Как портал открывает приложение

**Классическое локальное приложение или приложение Маркетплейса** [Б24-док]
- Битрикс24 открывает «Путь вашего обработчика» во фрейме **POST-запросом**:
  - в строке запроса — `DOMAIN` и `APP_SID` (`APP_SID` меняется при каждой отрисовке);
  - в теле — `AUTH_ID` (живёт 1 час), `REFRESH_ID`, `APPLICATION_TOKEN`, `APPLICATION_SCOPE`, `member_id`;
  - в примере дампа видны ещё `PROTOCOL`, `LANG`, `AUTH_EXPIRES`, `SERVER_ENDPOINT`, `status`, `PLACEMENT`;
  - для мест встраивания с контекстом (вкладка карточки, меню списка и т. п.) Б24 шлёт `PLACEMENT_OPTIONS` с ID текущей записи. VibeCode подтверждает, что Б24 присылает это поле в POST, и пробрасывает его в URL как `placement_options` [VC App runtime]; на странице [Б24-док] о серверном приложении поле не описано.
- **Сервер должен отвечать на POST по адресу обработчика.** Голая раздача статики часто отвечает `405 Not Allowed` на POST — проверьте конфиг nginx (общий REST Б24 / nginx). Шаблон `_base_universal` отдаёт `index.html` и на GET, и на POST `/` [шаблоны].
- **Установка:**
  - страница установки должна последним шагом вызвать `BX24.installFinish()`. Это может сделать администратор или пользователь с правом установки;
  - **пока `installFinish` не вызван, приложение считается неустановленным**: страница установки открывается при каждом заходе, события не доставляются, виджеты не показываются. Проверка — поле `INSTALLED` в `app.info` [Б24-док];
  - опция формы «Приложение само завершает установку» по умолчанию выключена — тогда Б24 считает приложение установленным сразу [Б24-док].
- **Требования к серверу** [Б24-док]:
  - PHP с cURL (для примеров CRest) и валидный SSL-сертификат;
  - HTTPS с первого открытия;
  - сервер не должен отдавать `X-Frame-Options` или `Content-Security-Policy`, запрещающие фрейм;
  - адрес обработчика доступен из интернета, поэтому **проверяйте источник каждого запроса**.

**Приложение VibeCode (OAuth-приложение `/v1/apps`)** [VC App runtime, Apps]
1. Б24 шлёт POST на платформенный обработчик `https://vibecode.bitrix24.tech/v1/bitrix-handler` (поле `handlerUrl`, его задаёт платформа).
2. Платформа обменивает код, создаёт `vibe_session_*` и делает 302 на ваш `appUrl`. В строку запроса добавляются:
   - `placement` — код места (`LEFT_MENU`, `CRM_DEAL_DETAIL_TAB`…);
   - `member_id`;
   - `placement_options` — JSON-строка, например `{"ID":"42"}` для вкладки сделки;
   - на Black Hole — одноразовый `__init` (JWT, 5 минут). На своём сервере вместо него приходит одноразовый `code`.
3. **Домен портала в редиректе не передаётся.** Берите его из `GET /v1/me` → `data.portal`.
4. На Black Hole Gateway обменивает `__init` на cookie `_vibe_gw` (HttpOnly, 10 минут; у мест встраивания ~40 минут, продлевается) и проставляет в каждый запрос к приложению заголовки:
   - `X-Vibe-Request-Id`;
   - `X-Vibe-User-Id` — число или значения с префиксом `net_…`, `share:…`, `vibe:…`;
   - `X-Vibe-Portal-Id` — UUID в базе VibeCode, **не** `member_id` и не домен;
   - `X-Vibe-User-Name` / `X-Vibe-User-Name-Encoded` — читайте второй через `decodeURIComponent`;
   - `X-Vibe-User-Role` — `ADMIN` | `MEMBER`;
   - `X-Vibe-Authorization: Bearer vibe_session_…`;
   - `X-Vibe-Public: true` — только при политике `PUBLIC`.
5. Входящие от клиента заголовки `X-Vibe-*` Gateway срезает.
6. **Значение `X-Vibe-User-Id` с префиксом нельзя передавать в методы Б24** (`USER_ID`, `RESPONSIBLE_ID`). Б24 приведёт строку к числу, и получится ID постороннего сотрудника.
7. **`X-Vibe-User-Role` не годится для необратимых решений.** При открытии из каталога у сотрудника без учётной записи VibeCode роль приходит `MEMBER`. Права проверяйте по профилю текущего сотрудника (`isAdmin`).

### 4.2. BX24 JS SDK

- **Подключение:**
  - в наших шаблонах и в задании курса — `<script src="//api.bitrix24.com/api/v1/"></script>` [шаблоны];
  - официальная страница SDK на 18.11.2026 показывает `//api.bitrix24.tech/api/v1/` [Б24-док]. Предпочитайте адрес из официальной документации и проверяйте, что скрипт грузится (CSP `script-src`).
- **Основные функции:**
  - `BX24.init(callback)` — ждать её перед остальными вызовами;
  - `BX24.callMethod` — вызов REST с автоматической OAuth-авторизацией;
  - `BX24.callBatch` — до 50 команд;
  - `BX24.getAuth()`, `BX24.getLang()`, `BX24.appOption.get` [Б24-док];
  - `BX24.installFinish()` [Б24-док, страница серверного приложения];
  - `BX24.fitWindow()`, `BX24.resizeWindow(w, h)`, `BX24.placement.info()`, `BX24.refreshAuth()`, `BX24.openPath()`, `BX24.isAdmin()` — (общий REST Б24). Шаблон `_b24-advanced-php` подгоняет высоту через `BX24.resizeWindow`, шаблон `_b24-single-php` продлевает сессию через `BX24.refreshAuth` [шаблоны].
- **SDK работает только внутри фрейма Б24** (общий REST Б24). Вне фрейма `BX24.init` ждёт родителя, и страница «висит». Вызывайте SDK, только если `window.self !== window.top`, и ставьте таймаут.
- **Под обработчиком VibeCode SDK не работает:** `BX24.init` не завершается, `BX24.placement.info()` → `{placement:null, options:null}`, `openPath` и `openSlider` недоступны [VC App runtime]. Это касается и Black Hole, и `appUrl` на вашем сервере. Исключение — собственное приложение Б24 со своим обработчиком: там SDK работает. Что делать вместо SDK:
  - **контекст:** `new URLSearchParams(location.search)` → `placement`, `placement_options` (JSON);
  - **открыть карточку CRM:** только по клику пользователя: `window.top.location.href = https://${portal}/crm/deal/details/${id}/`, где `portal` взят из `/v1/me`;
  - **авто-высота:** включить `placementResizeEnabled: true` (`PATCH /v1/apps/:id`) и отправлять `window.parent.postMessage({type:'vibe:resize', height}, '*')`. `targetOrigin` — именно `'*'`, а не домен портала. Опция раскатывается по порталам постепенно. **В `frame-ancestors` добавьте `https://vibecode.bitrix24.tech`**, иначе под обёрткой приложение не откроется.

### 4.3. Места встраивания (placements)

**Через VibeCode** [VC Apps — Placements]

| Метод | Что делает |
|---|---|
| `GET /v1/placements/available` | Справочник мест. Открыт любому ключу. Ответ: `data.groups` (ключ — название группы, значение — массив с полями `code`, `title`, `description`, `module`, `requiredScope`, `requiresIconName`, `restBindable`) и `data.total` |
| `POST /v1/placements/bind` | Привязать место. Тело: `{ placement, handler, title, options? }` |
| `POST /v1/placements/unbind` | Отвязать: `{ placement, handler? }`. Без `handler` снимаются все регистрации приложения на этом месте. Идемпотентно (`alreadyUnbound`) |
| `GET /v1/placements` | Что привязано. `portalSync`: `ok` / `drift` / `unknown` |

**Что нужно до привязки:**
- **Ключ `vibe_app_`.** С личным ключом → `400 OAUTH_APP_REQUIRED`.
- **Скоуп `placement`** у ключа. Без него → `403 PLACEMENT_SCOPE_MISSING`.
- **Скоуп Б24 под группу мест:** `crm`, `im`, `task`, `contact_center`. Без него → `403 PLACEMENT_APP_GRANT_MISSING` (или `502 BITRIX_UNAVAILABLE` — см. противоречие в заметках).
- **Сессия.** На части аккаунтов без `Authorization: Bearer` приходит `401 SESSION_REQUIRED`. Передавайте сессию всегда.
- **Условие Б24:** подписка BitrixGPT + Маркетплейс или коммерческий тариф. Точное условие — в `GET /v1/me` → `placements.bindPrerequisite`.

**Особенности:**
- **Технический адрес сервера в `handler` платформа заменяет на `/v1/bitrix-handler`** (`handlerRewritten: true`). Если место смотрит прямо на субдомен приложения, вместо приложения откроется экран входа. Лечится повторной привязкой.
- **У самостоятельного приложения пункт левого меню появляется сразу после создания.** Привязка `LEFT_MENU` добавляет **второй** пункт.
- **Подпись (`title`) — одна на все языки.** Повторная привязка — единственный способ её сменить.
- **Опции:**
  - `iconName` (`fa-…`, до 50 символов) — обязательна для `IM_SIDEBAR` / `IM_NAVIGATION` / `IM_TEXTAREA`;
  - `iconSvg` — до 10 000 символов;
  - `width` / `height` — для `IM_TEXTAREA`;
  - `color` — палитра чата;
  - `errorHandlerUrl` — для `PAGE_BACKGROUND_WORKER`.
- **Группы мест:** CRM Lists, CRM List Toolbars, CRM Detail Tabs, CRM Detail Toolbars, CRM Detail Activity, CRM Activity Timeline, Tasks, User Profile, Menu, Universal, Chat, Contact Center.
- **Коды, названные в документации:** `LEFT_MENU`, `CRM_DEAL_DETAIL_TAB`, `CRM_QUOTE_DETAIL_TAB`, `IM_SIDEBAR`, `IM_NAVIGATION`, `IM_TEXTAREA`, `IM_CONTEXT_MENU`, `CONTACT_CENTER`, `PAGE_BACKGROUND_WORKER`. Есть шаблон `CRM_(DYNAMIC|SMART)_<entityTypeId>_(DETAIL_TAB|DETAIL_ACTIVITY|LIST_MENU|LIST_TOOLBAR|DETAIL_TOOLBAR|ACTIVITY_TIMELINE_MENU)`. **Полный перечень берите живым вызовом `/v1/placements/available`** и не зашивайте в код.
- **Ошибки bind** (выборочно): `400 OAUTH_APP_REQUIRED`, `APP_NOT_REGISTERED`, `PLACEMENT_NOT_REST_BINDABLE`, `PLACEMENT_OPTIONS_REQUIRED`; `401 SESSION_REQUIRED`; `403 PLACEMENT_SCOPE_MISSING`, `PLACEMENT_APP_GRANT_MISSING`, `SESSION_REQUIRES_ADMIN`, `B24_EMBEDDING_INSTALL_DENIED`; `404 B24_EMBEDDING_APP_NOT_FOUND` (лечится через `relink-oauth`); `502 BITRIX_UNAVAILABLE`.

**Классический REST** [Б24-док / общий REST Б24]
- Методы `placement.bind`, `placement.unbind`, `placement.list`. Нужен скоуп `placement`, вызываются в контексте приложения; через вебхук недоступно [Б24-док]. По странице SDK `placement.bind` — только для администратора.
- В наших PHP-шаблонах места перечислены в `api/bind.php` или `APP_PLACEMENTS`. Привязка идёт при установке, идемпотентно: сначала `unbind`, затем `bind` [шаблоны].
- Номер карточки CRM приходит в `PLACEMENT_OPTIONS`: `{"ID":"42"}`.

### 4.4. Разрешить показ во фрейме: CSP и X-Frame-Options

- **Не отправляйте `X-Frame-Options`.** Задайте CSP `frame-ancestors` с доменами портала [Б24-док]. Для приложения VibeCode с авто-высотой добавьте `https://vibecode.bitrix24.tech` [VC App runtime].
- **Как это сделано в шаблонах** [шаблоны]:
  - `_b24-single-php`: `'self'`, маски `*.bitrix24.{ru,com,eu,tech,kz,by,ua,de,com.br}` и домен портала из хранилища;
  - `_b24-advanced-php`: до установки — маски порталов, после — ровно домен своего портала; у API-эндпоинтов `frame-ancestors 'none'`.
- **Частая ловушка** (общий REST Б24 / Node): `helmet` и многие шаблоны nginx по умолчанию ставят `X-Frame-Options: SAMEORIGIN` и `frame-ancestors 'self'` — это ломает фрейм.

Пример для nginx (адаптируйте; это общее знание, не из документации):

```nginx
# Не отдавать X-Frame-Options от приложения
proxy_hide_header X-Frame-Options;
add_header Content-Security-Policy "frame-ancestors https://example.bitrix24.ru https://vibecode.bitrix24.tech" always;
```

### 4.5. Cookies внутри фрейма

- **Фрейм на чужом домене — сторонний контекст.** Cookie сессии ставьте с `SameSite=None; Secure; HttpOnly`. Для браузеров с разделением cookie добавляйте `Partitioned` — так сделано в наших шаблонах: копия `gsp_session_p` в single, `SameSite=None; Partitioned` в advanced и marketplace [шаблоны].
- **Браузеры блокируют сторонние cookie** (Safari ITP и др.) (общий веб). Не делайте cookie единственным доказательством входа. В advanced-шаблоне изменяющие запросы принимаются только с заголовком `X-App-Token`, плюс проверка `Origin` / `Sec-Fetch-Site`. В marketplace-шаблоне — `X-App-Tenant` и `X-CSRF-Token` [шаблоны].
- **Запрещённые имена cookie на VibeCode:** `_vibe_gw`, `session`, `oauth_state` — используйте свои имена. `Domain` cookie платформа заменяет поддоменом приложения [VC App runtime].
- **Страница согласия OAuth Б24 и `GET /v1/oauth/authorize` во фрейме не открываются** (`X-Frame-Options`). Открывайте их в отдельной вкладке [VC OAuth, App runtime].

### 4.6. Публикация в каталог и иконка

В VibeCode есть **два разных** «каталога»:

| Что | Метод | Что даёт |
|---|---|---|
| Публикация OAuth-приложения | `POST /v1/apps/:id/publish` `{ placements?, catalogTitle?, catalogDescription?, catalogIcon?, appUrl?, sourceVersionId? }` | `catalogStatus`: `PRIVATE` → `PUBLISHED` (видно всем сотрудникам портала) → `UNPUBLISHED`. Перед публикацией нужна однократная OAuth-авторизация приложения на портале, иначе `400 NO_USER_TOKEN`. Нужен скоуп `placement`. `catalogTitle` — не больше 100 символов. Внешний `appUrl` публикуется только из кабинета или личным ключом (`EXTERNAL_URL_ACTOR_NOT_ALLOWED`, `EXTERNAL_URL_DISABLED`) [VC Apps] |
| Карточка сервера в каталоге приложений VibeCode на портале | `POST /v1/infra/servers/:id/b24-catalog/publish` | Карточку видят владелец и сотрудники с доступом. Это **не** публикация REST-приложения. Название и описание берутся из `displayName` / `description` деплоя. Готовность: `b24CatalogSync.status = SYNCED` [VC Servers] |

- **Снятие с публикации:** `POST /v1/apps/:id/unpublish` → `UNPUBLISHED`, места отвязываются. Удаление приложения: `DELETE /v1/apps/:id` → 204, ключ отзывается сразу [VC Apps].
- **Иконка:** `POST /v1/infra/servers/:id/icon`, `multipart/form-data`, поле `file`.
  - SVG — до 256 КБ, без скриптов, `on*`, `foreignObject` и внешних ссылок. PNG, JPG, GIF, WEBP — до 5 МБ.
  - На выдаче всегда PNG 256×256.
  - Фавикон: `<link rel="icon" href="/_gw/icon">`, обновляется примерно за 5 минут [VC App icon].
- **Маркетплейс Б24** (тираж): подача через партнёрский кабинет — отдельный процесс (общий REST Б24). Наш шаблон `_b24-marketplace-php` подачу не выполняет [шаблоны].

### 5.2. Когда что выбирать

**Платформа VibeCode — когда:**
- нужен быстрый прототип или внутренний инструмент для одного портала;
- у пользователя нет своего сервера и администратора;
- нужна готовая авторизация сотрудников через Б24 без своего кода входа;
- нужны события без публичного адреса;
- допустимы сон, оплата Вайбами и динамический IP.

**Свой сервер — когда:**
- пользователь прямо сказал «хостинг VibeCode не использовать»;
- данные и код должны оставаться в своей инфраструктуре;
- нужен постоянный онлайн без сна или статический IP для белых списков;
- приложение тиражное (multi-tenant, Маркетплейс);
- нужны тяжёлые фоновые задачи или своя БД;
- у пользователя уже есть сервер и тот, кто его обслуживает.

**Гибрид — частый и нормальный вариант:**
- данные — через VibeCode API (`vibe_api_` на вашем сервере);
- встраивание — через OAuth-приложение VibeCode с `appUrl` на вашем сервере;
- хостинг — свой.

### 5.4. (А) Деплой на VibeCode: по шагам

Все вызовы идут на `https://vibecode.bitrix24.tech/v1`, нужен скоуп `vibe:infra` [VC Infrastructure].

1. **Проверка.**
   - `GET /v1/me` → `capabilities.servers.create.available`. Если `false`, объяснение лежит в `capabilities.servers.create.userMessage`.
   - Модель размещения смотрите в блоке `deployment` (`primary`: `galaxyApp` / `standalone`).
   - Лимит серверов — `data.infra.limits.max` / `used`: 100 VM на ключ; galaxy-приложения в лимит не входят.
   - **Создание сервера — это расход. Нужно согласие пользователя.**
2. **Справочники** (необязательно):
   - `GET /v1/infra/providers` → в примере один провайдер, `bitrix-cloud`;
   - `GET …/bitrix-cloud/plans` → `bc-small`, `bc-medium`, `bc-large`, `bc-xlarge`, `bc-micro`, `bc-agent`; поля `priceMonthly`, `sleepPriceMonthly`, `currency: "Vibes"`;
   - `GET …/regions` → `ru-central1-a`, `-b`, `-d`, `-e`;
   - `GET …/images` → Ubuntu 24.04 LTS. `id` образа меняется — не зашивайте его; можно передать семейство `ubuntu-2404-lts` или вообще не передавать поле [VC Providers, Cowork defaults].
3. **Создать сервер:** `POST /v1/infra/servers`.
   - Обязательные поля: `provider`, `name` (`^[a-z][a-z0-9-]*$`, 2–63 символа, **не меняется**), `plan`.
   - Полезные поля: `displayName` (2–100), `description` (до 500), `region`, `placement` (`auto` | `dedicated`).
   - Заголовок `Idempotency-Key` защищает от дубля в течение 15 минут.
   - Сервер всегда создаётся в режиме BLACKHOLE с `accessPolicy: OWNER_ONLY` и `sleepAfterMinutes: 60`.
   - Для `vibe_app_` нужна сессия, иначе `401 UNAUTHENTICATED` [VC Servers].
4. **Дождаться готовности.**
   - VM (`kind: STANDALONE`): опрашивайте `GET /v1/infra/servers/:id`, пока не будет `status = running` **и** `blackholeStatus = CONNECTED`. Обычно 1–3 минуты, опрос раз в 10 секунд.
   - Galaxy (`kind: GALAXY_APP`, `createdVia: galaxy`): `CONNECTED` не наступит, код загружают сразу [VC Infrastructure, Galaxy].
5. **Деплой:** `POST /v1/infra/servers/:id/deploy`.
   - `source` — **ровно один** из вариантов: `content` (base64 архива, до 96 МБ тела ≈ 72 МБ архива), `url` (HTTPS, до 500 МБ) или `versionId` (`v3`).
   - `runtime`: `node24`, `python311`, `python312`, `php83`, `static`. Список — `GET /v1/infra/runtimes`. Без `runtime` на чистой Ubuntu нет ни node, ни python.
   - `install`, `start` (обязателен, кроме `static`; процесс должен работать на переднем плане — связка `pm2 start … && pm2 save` не подходит).
   - `port` — 3000 (платформа передаёт его в `PORT`), `env`, `healthPath` (по умолчанию `/`).
   - **Всегда передавайте `displayName` и `description`** — из них строится карточка в каталоге Б24.
   - Если включено хранилище исходников, деплой с внешнего `url` требует заголовок `X-Skip-Source-Snapshot: <причина>`, иначе `409 SNAPSHOT_REQUIRED`.
   - **Таймаут клиента — не меньше 690 секунд.**
   - На VM провал приходит **с HTTP 200**: проверяйте `success`, `error.step` и `data.steps[].status` (`ok` / `warning` / `error`). У galaxy провал приходит со статусом 502.
   - Шаг `healthcheck` делает до 10 попыток `curl localhost:{port}{healthPath}` и засчитывает ответы 200–399.
   - `DEPLOY_TIMEOUT`, `DEPLOY_CONNECTION_TERMINATED`, `DEPLOY_TUNNEL_STALE` — исход неизвестен. **Не повторяйте вслепую**: сначала прочитайте `GET /v1/infra/servers/:id/operations` или `GET /v1/infra/operations/:operationId`.
   - Лимиты: 10 операций в минуту на пару «ключ + сервер», одновременно 1 exec/deploy на сервер [VC Deploy].
6. **Проверка через публичный путь.**
   - Выпустите токен: `POST /v1/infra/servers/:id/access-tokens` с `{"mode":"api-bearer","ttlSeconds":600}`.
   - Запросите `${appUrl}/api/health` с заголовком `Authorization: Bearer <token>`.
   - Отзовите токен: `DELETE …/access-tokens/:tokenId`.
   - Если Bearer даёт 502, а `exec` + `curl 127.0.0.1:3000` проходит, проблема в Gateway или туннеле.
   - Раздел токенов может быть выключен — проверьте `data.capabilities.servers.preview.available` [VC Access tokens].
7. **Доступ.**
   - По умолчанию `OWNER_ONLY`.
   - Чтобы пустить конкретных сотрудников: `PATCH …/access-policy` `{ "accessPolicy": "NAMED_USERS" }` + `POST …/access` `{ type: "user", userId, userName }`. Пользователей ищут через `GET …/b24-users?search=`.
   - Политики по возрастанию открытости: `OWNER_ONLY` → `NAMED_USERS` → `DEPARTMENT` → `PORTAL` → `AUTHENTICATED` → `PUBLIC`.
   - **Расширять доступ только с явного подтверждения пользователя.** На защищённых порталах приходит `409 AUDIENCE_APPROVAL_REQUIRED` с `approvalUrl` — передайте ссылку человеку; API-ключ сам согласовать не может.
   - Список доступа применяется только при `NAMED_USERS` / `DEPARTMENT`. Если список пуст, приложение доступно только владельцу.
   - Режим OPEN (прямой доступ по IP) через API не включается: `403 DIRECT_NETWORK_CHANGE_REQUIRES_HUMAN` / `OPEN_MODE_DISABLED`. В OPEN Deploy API не работает [VC Access].
8. **Встраивание в Б24** (раздел 4):
   - `POST /v1/apps` с `scopes`, включающими `placement`, и `appUrl` = адрес сервера. Сохраните `rawKey` (`vibe_app_`).
   - Один раз авторизуйте приложение на портале: откройте его из меню.
   - Затем `POST /v1/placements/bind` или `POST /v1/apps/:id/publish`.
9. **Сон и режим работы** [VC Lifecycle, Wake schedules]:
   - `PATCH …/sleep` `{ "sleepAfterMinutes": 15 | 30 | 60 | 240 | null }`. `null` — не засыпать.
   - `PATCH …/run-mode` `{ mode: "IDLE" | "SCHEDULE" | "ALWAYS" }`. Готовые расписания: `weekdays-9-18`, `weekdays-9-19`, `weekdays-9-20`, `weekdays-8-19`, `weekdays-8-20`, `daily-9-21`.
   - `POST …/wake-schedules` `{ cronExpr, timezone, label?, lead?, enabled? }` — поднять сервер к фоновой задаче, минимум раз в 5 минут, до 50 окон. Cron внутри VM вы ставите сами.
   - Ручное управление: `stop` (переводит в `sleeping` по ставке сна), `start`, `wake?wait=true`, `sleep-now`.
   - После сна у VM меняется IP. Обращение к субдомену будит сервер только при `PUBLIC`, для опознанного посетителя, с `api-bearer` или `share-url`.
10. **Секреты.**
    - Значения задаются в карточке приложения и перекрывают одноимённые `env` деплоя. Применяются без деплоя: приложение перезапускается в фоне.
    - Команды `install` и `preStart` и сборка образа секретов не получают [VC App secrets].
    - Значения `env` — однострочные; многострочные кодируйте в base64.
    - **В galaxy деплой без `env` сбрасывает прежние переменные** [VC Deploy].
11. **Данные.**
    - VM: храните данные в `/opt/data` (не в `/opt/app`, его чистит `cleanDeploy`) и перечисляйте каталог в `dataDirs`.
    - Galaxy: том `/data`. SQLite: `VIBE_DB_PATH=/data/app.db`, режим WAL, `busy_timeout=5000`. API базы: `GET /db/schema`, `POST /db/query`, бэкапы. Доступно при `features.appDb` [VC Database, Pricing].
12. **Логи:** `GET …/logs?service=app&lines=100` (`since`, `grep`). Лента событий: `GET …/activity`. Начинайте диагностику с неё [VC Infrastructure].
13. **События портала:**
    - `POST …/event-subscriptions` `{ event: "ONCRMDEALADD", appPath: "/api/b24/events" }`. Примеры кодов в документации VibeCode: `ONTASKADD`, `ONTASKUPDATE`, `ONCRMDEALADD`. Для лидов есть `ONCRMLEADADD` (общий REST Б24). Полного списка поддерживаемых событий у VibeCode нет — берите его из документации Б24.
    - Требования: сервер под `vibe_app_` (иначе `400 NOT_OAUTH_APP`), авторизованное приложение (иначе `400 NO_USER_TOKEN`), коммерческий тариф (иначе `502 BIND_FAILED`).
    - Обработчик: тело `x-www-form-urlencoded`, сверка `auth[application_token]`, ответ `2xx`, защита от повторной доставки [VC Event subscriptions].
14. **Карточка в каталоге и иконка:** `POST …/b24-catalog/publish`, `POST …/icon` (раздел 4.6).
15. **Свой домен** (по желанию):
    - `POST …/domain` `{ fqdn }` → получить `instructions[]`, завести записи `TXT vibe-verify=…` и `CNAME` (поддомен) или `A` (корень), без `AAAA`;
    - `POST …/domain/verify`;
    - сертификат выпускается обычно в течение часа [VC Domain].
16. **Остановить расходы.** `stop` и сон — это **не ноль**: диск оплачивается по ставке сна. Удаление сервера прекращает начисления. При заморозке баланса серверы останавливаются (`ACCOUNT_FROZEN`); по умолчанию через 33 дня возможно удаление [VC Pricing].

**Galaxy-приложение — отличия** [VC Galaxy, Galaxy sleep]:
- Модель (`galaxies-only` / `both` / `standalone-only`) выбирает администратор портала. Нужна именно VM — передайте `placement: "dedicated"`.
- Код передаётся только как `source.content` (base64). `source.url` работает, только если платформа включила его.
- `runtime` и `start` обязательны.
- Рабочая папка — `/opt/app`. Свой `Dockerfile` игнорируется.
- Поля `preStart`, `systemd`, `serviceName`, `cleanDeploy`, `dataDirs` не действуют.
- Нет SSH, нет `/upload`, режим доступа (BLACKHOLE/OPEN) не переключается, `PATCH /sleep` → `400 GALAXY_APP_USE_GALAXY_ROUTE`.
- Приложение спит вместе с галактикой. `wake` отвечает сразу — готовность смотрите в `reachability.effectiveStatus` (`running` / `sleeping` / `waking` / `unreachable` / `unknown`).
- Лимит памяти 512 МБ. При нехватке → `502 GALAXY_APP_START_FAILED` с `recoveryAction: "graduate-to-dedicated-vm"`.
- Операции выполняйте по id **приложения**, а не хоста (`kind: GALAXY`).

### 5.5. (Б) Деплой на свой сервер / VPS: по шагам

Общие практики ниже — общее знание, кроме мест с метками.

1. **Адрес и HTTPS.**
   - Нужен публичный домен с A-записью IPv4. Все адреса домена должны быть публичными, не из внутренней сети. URL начинается с `https://`, без логина и пароля. Иначе VibeCode отвечает `400 APP_URL_UNSAFE` [VC Move to own server, Apps].
   - Сертификат должен быть валидным (например, Let's Encrypt), HTTPS — с первого открытия [Б24-док].
2. **Reverse proxy (nginx).**
   - Приложение слушает `127.0.0.1:<порт>`, nginx проксирует на него с 443.
   - Разрешите POST на адрес обработчика (Б24 открывает приложение POST-запросом).
   - Уберите `X-Frame-Options`, задайте `frame-ancestors` (раздел 4.4). Включите HSTS и gzip.
   - Увеличьте `proxy_read_timeout`, только если действительно нужен долгий ответ. Правильнее отвечать быстро (раздел 8).
3. **Автозапуск.**
   - Юнит systemd: `Restart=always`, `User=` — непривилегированный пользователь, `EnvironmentFile=/etc/<app>/app.env` с правами 0600, вне репозитория и вне webroot. Либо аналог: pm2 с автозапуском, Docker с `restart: unless-stopped`.
   - В PHP-шаблонах: DocumentRoot = `www/`, приватный каталог данных 0700 вне `www/` [шаблоны].
4. **Ключи.**
   - `VIBE_API_KEY` (для данных) и/или `VIBE_APP_KEY` (для встраивания через VibeCode), либо `B24_CLIENT_ID` / `B24_CLIENT_SECRET` (локальное приложение) — только в env-файле сервера.
   - Ключ авторизации VibeCode платформа в сыром виде не хранит. Если его нет — «Перевыпустить ключ» в карточке приложения; прежний ключ сразу перестаёт работать [VC Move to own server].
5. **Вход и встраивание — выберите один путь.**
   - **Путь 1. OAuth-приложение VibeCode с `appUrl` на вашем сервере** [VC App runtime, OAuth, Move to own server]:
     1. Место встраивания открывает `https://<ваш-домен>/?code=<одноразовый>&placement=…&member_id=…`.
     2. Ваш сервер вызывает `POST /v1/oauth/token { app_key: <vibe_app_>, code, redirect_uri: <ровно appUrl> }` и получает `{ access_token: "vibe_session_…", user, expires_in: 86400 }`.
     3. Код одноразовый, живёт 5 минут. `redirect_uri` должен совпадать точно, иначе `400 INVALID_REDIRECT_URI` или `REDIRECT_URI_MISMATCH`.
     4. Храните `vibe_session_` на сервере, а браузеру выдайте свою cookie сессии (раздел 4.5).
     5. Личность пользователя: `GET /v1/me` с `X-Api-Key: vibe_app_…` и `Authorization: Bearer vibe_session_…` → `currentUser.bitrixUserId`, `portal`.
     6. Gateway и заголовков `X-Vibe-*` здесь **нет**, фрейм-заголовки — ваша забота.
   - **Путь 2. Собственное локальное приложение Б24 со своим обработчиком:**
     - на открытии приходят `AUTH_ID`, `member_id`, `APPLICATION_TOKEN` [Б24-док];
     - сверяйте `APPLICATION_TOKEN` с эталоном, сохранённым при установке, и `member_id` [Б24-док];
     - личность пользователя: `user.current` с `AUTH_ID` (общий REST Б24);
     - если нужны вызовы VibeCode от имени пользователя: `POST /v1/oauth/placement-session { app_key, access_token, member_id, domain }` → `vibe_session_` [VC OAuth];
     - так устроены шаблоны `_b24-single-php` и `_b24-advanced-php` [шаблоны].
6. **Данные.** Ключ `vibe_api_` (READONLY) или токены приложения — только в серверном коде. Фоновое обновление кэша по cron (раздел 8). В PHP-шаблонах `bin/process.php` запускается только из CLI под `flock` [шаблоны].
7. **События.**
   - Публичный HTTPS-адрес обработчика, `event.bind` в контексте приложения (общий REST Б24).
   - Отвечайте быстро, работу кладите в очередь.
   - Битрикс24 события повторно не доставляет [VC App runtime: «без гарантии повторной доставки»; шаблоны]. Поэтому `200` отдавайте только после надёжной записи в очередь — так сделано в advanced-шаблоне.
   - Сверяйте `auth[application_token]` по `auth[member_id]` [Б24-док].
   - Если сервер бывает недоступен — офлайн-события: `event.bind` с `event_type=offline` без `handler`, затем `event.offline.get` / `event.offline.clear` [VC App runtime].
8. **Безопасность сервера.** Открыты только 80/443 (и SSH по ключу), обновления ОС, логи без токенов и без query-строк с `code`, `__init`, `s=`. Ротация логов.
9. **Бэкап и откат.** Бэкап каталога данных и хранилища токенов. Выкладка релизами (`releases/` + симлинк `live`, данные в `shared/` — как в `MAP.md` advanced-шаблона) [шаблоны]. Перед выкладкой — копия заменяемых файлов, после — проверка контрольной суммы и готовности.
10. **Проверка.**
    - Открыть из меню Б24 — работает.
    - Открыть URL напрямую в приватном окне — данных нет (401/403 или экран «откройте из Битрикс24»).
    - Ключа нет в DevTools: Network, Sources, Application.
    - Время открытия — секунды.

### 5.6. Официальный переезд с VibeCode на свой сервер и обратно [VC Move to own server]

**Что остаётся за платформой:**
- карточка приложения, ключ авторизации, доступ;
- встройки и карточки каталогов — они начинают вести на новый адрес;
- API `/v1/*`.

**Перед переездом:**
- **Код.** Заберите его заранее: из «Исходники приложений» или промптом выгрузки, который предлагает мастер.
- **Правки в коде.** Вход делает само приложение через `code` → `POST /v1/oauth/token`. Токен хранится только на сервере. Фрейм-заголовки настраиваете вы (раздел 5.5, путь 1).

**Как переехать:**
1. Откройте «Приложения» → карточку → строка «Сервер» → «Заменить» → вкладка «Внешний сервер».
2. Пройдите шаги «Код» → «Что поменять в коде» → «Адрес» → «Что изменится».
3. Нажмите «Перенести».

Переносит владелец или администратор портала. Кнопка «Указать свой адрес» в мастере публикации меняет только адрес и сервер VibeCode не отвязывает.

**Что изменится:**
- **Пометка в каталоге.** Встройки и карточки помечаются «Вне платформы».
- **Старый сервер продолжает тарифицироваться.** Сервер VibeCode отвязывается, но не удаляется. Удалите его сами, когда новый адрес заработает.
- **Перенос доступа:**
  - списки людей переносятся максимум на первые 200 человек;
  - подотделы теряют доступ;
  - предупреждения `ACCESS_USERS_NOT_MOVED`, `ACCESS_DEPARTMENTS_NOT_MOVED`, `ACCESS_CARD_AXIS_RESET` — это не отказы.
- **Приложение со встроенным входом (App login) на свой сервер не переносится.**

**Ошибки переноса:**
- `403 EXTERNAL_URL_DISABLED` — перенос выключен для портала;
- `400 APP_URL_UNSAFE`;
- `400 APP_URL_NOT_EXTERNAL` — указан адрес на сервере VibeCode;
- `422 APP_HOST_NOT_ALLOWED_HERE`;
- `409 APPLICATION_NO_AUTH_KEY`;
- `409 APPLICATION_OP_IN_PROGRESS`.

**Обратно.** «Вернуть на Вайбкод» → выбрать или создать сервер. Код нужно выложить заново: возврат меняет только привязку. Если ключ авторизации перевыпускали, пропишите новый ключ в env сервера.

### 6.2. Как устроены

**`_base_universal`**
- Переменные: `VIBE_API_KEY`, `VIBE_BASE_URL` (по умолчанию `https://vibecode.bitrix24.tech/v1`), `PORT`, `NODE_ENV`. Без `VIBE_API_KEY` процесс сразу завершается.
- Точка входа — `src/server.js`. Отдаёт `src/public/`, на GET и POST `/` возвращает `index.html` (Б24 открывает приложение POST-запросом).
- `src/utils/api.js` — клиент с `X-Api-Key`. Разбирает `data` или `result`, листает через `fetchAll` (offset/limit, по 50).
- В `bitrix.js` есть только `isInsideBitrix()`: BX24 SDK, мест встраивания, событий и CSP в коде нет.
- **Сам по себе шаблон не защищает данные.** В документации шаблона прямо сказано: «iframe сам по себе не авторизация» и «не считать API-key proxy полноценной multi-tenant архитектурой». Если адрес публичный, нужно добавить проверку доступа (раздел 7).
- `npm run check:remote` ходит в реальные данные — это не офлайн-тест.

**`_b24-single-php`**
- Переменные: `B24_CLIENT_ID`, `B24_CLIENT_SECRET`, `APP_URL` (точный HTTPS-адрес обработчика, заканчивается на `/index.php`), `APP_DATA_ROOT`.
- Единственный обработчик — `www/index.php`. Интерфейс — `www/template.html`. Ещё есть `api/b24.php`, `session.php`, `bind.php`, `bin/process.php`.
- **Токены** лежат в `DATA_ROOT/tokens.php`: PHP-файл с `<?php exit;?>` и JSON, права 600. Refresh делается по ошибке `expired_token` / `invalid_token`.
- **Установка:** `application_token` сверяется через `hash_equals`; заставка вызывает `BX24.installFinish()`; самовосстанавливается, если `INSTALLED=false`.
- **Фрейм и cookie:**
  - `sendIframeHeaders()` снимает `X-Frame-Options` и ставит `frame-ancestors` с масками доменов Б24 и доменом портала;
  - cookie `SameSite=None; Secure; HttpOnly` и копия с `Partitioned`;
  - сессия живёт 3600 с и продлевается через `BX24.refreshAuth` → `api/session-renew.php`.
- **По умолчанию пускает только администратора портала.** Для остальных нужен серверный прокси — в шаблоне его нет.

**`_b24-advanced-php`**
- Переменные: `BXAPP_*` / `B24_*` (client id/secret, `APP_URL`, `DATA_ROOT`, `CREDS_FILE`). Есть контракт из 37 `define` (`APP_SCOPES`, `APP_PLACEMENTS`, `APP_EVENTS`…).
- OAuth-сервер — `https://oauth.bitrix24.tech/oauth/token/`.
- **Токены:** `DATA_ROOT/b24-tokens.php`. Refresh идёт под замком. Первая установка подтверждается криптографически через `verifyAndAdopt`.
- **Ядро:** ACL (`view` / `edit` / `admin`), очередь событий, задачи, `runOnce`, аудит, CSV, UI-компоненты.
- **Свой код** — в `www/api/project-hooks.php` (`projectCronJob`, `projectHandleEvent` и др.). Этого файла в шаблоне нет намеренно, его пишете вы.
- **Безопасность запросов:**
  - `frame-ancestors` после установки — ровно домен портала;
  - изменяющие запросы принимаются только с заголовком `X-App-Token` и проверкой `Origin`;
  - `api/event.php` сверяет `application_token` и `member_id` и отвечает 200 только после записи в очередь (до 64 КиБ на событие).
- **Нужен cron:** без него очередь и отзыв доступа у переведённых сотрудников не работают (TTL сессии 28800 с).
- Перед выкладкой: `php tools/release-template.php`. Перед тем как писать своё, прочитайте `BLOCKS.md` и `RECIPES.md` («нашёл — бери»).

**`_b24-marketplace-php`**
- Переменные: `B24_CLIENT_ID`, `B24_CLIENT_SECRET`, `APP_STATE_KEY` (≥ 32 байт и не равен `client_secret`), `APP_URL`, `DATA_ROOT`, `FRAME_ANCESTORS`, `APP_ENV`, `SESSION_COOKIE_NAME`.
- **Токены:** `DATA_ROOT/portals/<member_id>/b24-tokens.php`. Refresh-токен одноразовый: обмен идёт под замком портала, запись — через сравнение-и-запись поколения (CAS).
- **Профиль 1.2.0:** ленивая установка из интерфейса, только администратор, скоуп только `user_brief`. CRM не реализована.
- **События:** `OnAppInstall` / `OnAppUpdate` / `OnAppUninstall` через `event.bind` на `APP_URL?lc=<HMAC>`. Параметр `lc` нельзя писать в логи.
- Тесты: 4 набора, плюс приёмка `LIVE_ACCEPTANCE` минимум на двух порталах. Чек-лист — `SECURITY_CHECKLIST`.

## 7. Безопасность и данные

### 7.1. Ключ не попадает в браузер

- **Только серверная схема (BFF).** Браузер обращается к вашему серверу, сервер — к VibeCode или Б24 и отдаёт **готовые агрегаты**, без ключей и токенов.
- **Не возвращайте токены в JSON-ответах SPA.** Не кладите их в `localStorage` / `sessionStorage`, URL или HTML [VC App runtime].
- **Не встраивайте ключ в сборку фронтенда.** Любая переменная с префиксом, который попадает в бандл (`VITE_`, `NEXT_PUBLIC_`, `REACT_APP_` и т. п.), видна всем (общий веб).
- **Проверка:** DevTools → Network (заголовки и ответы), Sources (поиск `vibe_`), Application (storage, cookies). Ни одного `vibe_api_`, `vibe_app_`, `vibe_session_` там быть не должно.

### 7.2. Минимум прав

- Для аналитики: ключ `READONLY` [VC Access mode] со скоупами только под задачу. Дашборд CRM — `crm` + `user` [VC Scopes]. Для лидов и сделок достаточно `crm`; `user` нужен, если показываете ответственных.
- **CRM только читать.** Если задача аналитическая, код вообще не должен содержать вызовов записи — так безопаснее, чем только `READONLY`.
- Разные сервисы — разные ключи. Отдельный ключ проще отозвать [VC Keys & Auth].
- `vibe_api_` действует от имени владельца ключа. **Кто владелец ключа — тот и «смотрит» данными.** Выбирайте владельца осознанно и держите сервисный дашборд закрытым (`OWNER_ONLY`) [VC App runtime].

### 7.3. Закрыть дашборд от посторонних при публичном адресе

**Требование:** «посторонний по ссылке данные не видит, а у владельца рабочая ссылка».

**На VibeCode (Black Hole)** [VC Access, App runtime, Access tokens]:
- **Закрытая политика.** Оставьте `OWNER_ONLY` (или `NAMED_USERS` / `DEPARTMENT` со списком). Посторонний по прямой ссылке получит экран входа или `401 BH_LOGIN_REQUIRED`. Опознанный, но не допущенный пользователь — `403 BH_ACCESS_DENIED`.
- **Рабочая ссылка владельца:** пункт меню или место встраивания в Б24 (открывается через Gateway с прозрачной авторизацией) либо прямой адрес `app-…`, где владелец входит через Б24.
- **Ссылка для внешнего просмотра:** `share-url` с `identityBound: true`, тогда нужен вход через Б24. С `identityBound: false` ссылка анонимная — по сути пароль. Можно отозвать досрочно.
- **Никогда не ставьте `PUBLIC` для данных CRM.** Карточки ссылок в режиме `PUBLIC` мессенджеры кэшируют, и отозвать их потом нельзя.

**На своём сервере** — ни одного ответа с данными без проверенного контекста:
- **Проверенный контекст:**
  - **Через VibeCode OAuth:** одноразовый `code` → `/v1/oauth/token` → `currentUser`. Код одноразовый и живёт 5 минут — повторно открытая ссылка уже не сработает [VC OAuth].
  - **Через локальное приложение Б24:** `APPLICATION_TOKEN` и `member_id` совпадают с эталоном, сохранённым при установке, плюс `user.current` по `AUTH_ID` [Б24-док; общий REST Б24].
- **После проверки** выдайте **свою** короткую сессию: cookie `SameSite=None; Secure; HttpOnly; Partitioned` + CSRF или токен в заголовке (раздел 4.5). Сверяйте пользователя со списком допущенных (например, только владелец по `bitrixUserId`).
- **Рабочая ссылка владельца вне Б24:**
  - короткоживущая подписанная ссылка (HMAC с `exp`, одноразовая, выдаётся из уже проверенной сессии) — общий веб-паттерн;
  - или обычный вход (логин и пароль / OAuth);
  - на платформе VibeCode есть готовый App login, но только для серверов платформы [VC App login].
- **Прямой заход без контекста** → 401/403 и нейтральная страница «Откройте приложение из Битрикс24». Никаких данных, даже частичных.
- **Не доверяйте `DOMAIN`, `member_id` и параметрам строки запроса** без проверки токеном. Не доверяйте `Referer` и `ancestorOrigins` [VC App runtime].

### 7.4. События и вебхуки

- **Проверка подлинности.** Сверяйте `auth[application_token]` с эталоном, который сохранён при установке, и ищите эталон по `auth[member_id]`. При несовпадении — `403` [Б24-док; VC Event subscriptions].
- **Повторы.** Будьте готовы к повторной доставке: дедупликация по `data[FIELDS][ID]` + `event` + `ts`. Для роботов — по `workflow_id` / `event_token` [VC Bizproc callbacks].
- **На VibeCode с `PUBLIC` проверка токена обязательна** — запрос может прийти от кого угодно [VC App runtime].
- **Токены в теле события.** На внешний `appUrl` (не на сервер платформы) VibeCode `auth[access_token]` не отправляет, политикой доступа события на внешний адрес не фильтруются — сверяйте `auth[user_id]` сами [VC Event handler].

### 7.5. Логи и публичные ссылки

- **Чего не писать в логи:**
  - ключи и токены (`AUTH_ID`, `REFRESH_ID`, `vibe_*`, `application_token`);
  - адреса с `code=`, `__init=`, `?s=`, `__resource=`, `lc=`;
  - адреса входящих вебхуков;
  - публичные ссылки Диска [VC App runtime, Disk public link; шаблоны].
- **Маскирование.** Маскируйте секреты, как `maskSecrets()` в advanced-шаблоне. Для корреляции пишите `X-Vibe-Request-Id` или свой ID запроса.
- **Публичные ссылки Диска** через REST не отзываются — никогда их не логируйте [VC Disk public file link].
- **Текст ошибок Б24 наружу не отдавайте** [шаблоны marketplace].

### 7.6. Несколько порталов

- **Изоляция по `member_id`:** отдельное хранилище токенов на портал. Отказ, если портал не установлен [шаблоны marketplace].
- **Адрес приложения не берите из `Host` / `X-Forwarded-Host`** — они подделываются. Фиксируйте его при установке [шаблоны advanced].

## 8. Производительность: не грузить всё при открытии

**Почему это важно.**
- **Шлюз VibeCode:**
  - агент туннеля ждёт заголовки ответа приложения до **14 секунд**, потом `504 BH_APP_TIMEOUT`;
  - шлюз ждёт первый кадр до 30 секунд;
  - буферизованный ответ до 1 МиБ должен уложиться в 20 секунд [VC App runtime].
- **Лимиты API.** Портал разрешает единицы запросов в секунду (раздел 3.9), и одна страница даёт максимум 50 записей Б24. Выгрузка десятков тысяч лидов при каждом открытии — это минуты и риск `429`.

**Как правильно:**
1. **Готовьте данные заранее.** Фоновая задача обновляет снимок раз в N минут:
   - на своём сервере — cron или systemd timer под `flock`;
   - на VibeCode VM — cron внутри VM, а чтобы сервер не спал в нужное время — `wake-schedules` или `run-mode ALWAYS/SCHEDULE`;
   - на VibeCode Black Hole — HTTP-задания платформы `jobs` (`POST /v1/infra/servers/:id/jobs`): до 20 на сервер, интервал от 5 минут, подпись `Vibe-Signature`, до 4 попыток с одним `runId`. Для galaxy недоступно (`GALAXY_NOT_SUPPORTED`) [VC Jobs].
2. **Храните снимок** (JSON-файл, SQLite, Redis) с временем обновления. Страница отдаёт снимок мгновенно и показывает «обновлено в 10:15».
3. **Считайте агрегацией, а не выгрузкой:** `POST /v1/leads/aggregate` с `groupBy` вместо листинга. Помните про потолок 5000 — режьте период.
4. **Если выгрузка нужна** (UTM-поля, сложная логика) — инкрементально:
   - курсор `nextAfterId`;
   - `select` только нужных полей;
   - `filter[>updatedTime]` с прошлого прогона — проверьте, что поле допускается в фильтре сущности;
   - batch по 50;
   - backoff на `429`.
5. **Долгие операции:** отвечайте `202` + `jobId`, фронтенд опрашивает статус [VC App runtime].
6. **Кэшируйте справочники** (`statuses`, `users`) на часы.
7. **Таймауты везде.** У каждого `fetch` во фронтенде — `AbortController` (10–15 с) и понятное состояние ошибки. У серверных вызовов — не меньше 150 с при `limit ≤ 50` [VC Optimization].
8. **Холодный старт VibeCode** — от минуты. Если дашборд должен открываться мгновенно в рабочие часы, используйте `run-mode SCHEDULE` (`weekdays-9-18`) или отключите сон — это стоит Вайбов [VC Lifecycle].
9. **Не делайте синхронный POST дольше 14 секунд** через субдомен VibeCode [VC App runtime].

## 9. Частые ошибки и решения

### 9.1. Ошибки из нашего сравнения ИИ-моделей [опыт]

Исходная задача: «Сделай дашборд по лидам с YouTube, встрой в мой Битрикс24 и дай ссылку. Хостинг VibeCode не использовать, только данные и встраивание. Ключ не должен попасть в браузер. Посторонний по ссылке данные не видит, а у владельца рабочая ссылка».

**1. «На аккаунте заняты все 10 слотов API-ключей»**
- **Причина по документации** [VC Keys & Auth, Cowork]:
  - сработал лимит ключей пользователя (`409 KEY_LIMIT_REACHED`). По умолчанию он 100, но администратор может снизить его до 1–100; в примере `keysLimit: 10`;
  - в счёт идут **все неотозванные** ключи: личные, ключи авторизации каждого созданного приложения (`POST /v1/apps` выпускает новый `vibe_app_`), ключи агентов, проектные ключи деплоя. **Истёкшие тоже считаются**;
  - агент, который на каждую попытку создаёт новое приложение или ключ, быстро исчерпывает лимит.
- **Решение:**
  - переиспользуйте уже выданный ключ или приложение (`GET /v1/apps` покажет созданные);
  - отзовите лишние ключи в кабинете («Деактивировать») — удалять не обязательно;
  - попросите администратора поднять «Макс. ключей на пользователя»;
  - проверьте `error.details.scope`: при `"portal"` упёрлись в портальный потолок, и помогает только уменьшение общего числа живых ключей.
- **Профилактика:**
  - агент создаёт ключи и приложения только с согласия пользователя;
  - перед созданием проверяет `GET /v1/apps` и `GET /v1/cowork/applications/defaults` (`quota.keysUsed` / `keysLimit`);
  - не повторяет `POST /v1/apps` при сбое, не проверив, создалось ли приложение. Для мастера Коворк/Код есть обязательный `Idempotency-Key`.

**2. При открытии в Б24 ответ `{"error":"WRONG_PORTAL"}`**
- **Факт:** кода `WRONG_PORTAL` в документации VibeCode нет. Скорее всего, это ответ **собственной проверки портала** в коде приложения.
- **Почему такая проверка ломается** (по документации):
  - **Нет домена в редиректе.** VibeCode передаёт только `placement`, `member_id`, `placement_options` и `__init` / `code`. Проверка вида `DOMAIN === "example.bitrix24.ru"` сравнивает с `undefined` [VC App runtime].
  - **`X-Vibe-Portal-Id` — это UUID в базе VibeCode,** а не `member_id` и не домен. Сравнивать их между собой нельзя [VC App runtime].
  - **Ключ `vibe_api_` и OAuth-приложение VibeCode привязаны к одному порталу.** Открытие из другого портала или с ключом другого портала ведёт к расхождению: у VibeCode это `403 SESSION_APP_MISMATCH` — «сессия выдана другому приложению или порталу» [VC Errors, Apps].
  - **Домен портала бывает в разных формах:** свой домен, переименование. Для коробки VibeCode отвечает `409 PORTAL_ADDRESS_CHANGED` [VC Errors: Auth].
- **Решение:**
  - определяйте портал по `member_id`, сохранённому при установке (классическое приложение), или по `GET /v1/me` → `data.portal` (VibeCode);
  - в отказе логируйте обе сравниваемые величины, без секретов, и показывайте понятное сообщение;
  - в классическом приложении сверяйте `APPLICATION_TOKEN` + `member_id`, а не домен [Б24-док].

**3. Во фрейме всё притемнено, надпись «доступ ограничен», ничего не кликается**
- **Факт:** такого экрана в документации VibeCode нет. Причину нужно установить диагностикой.
- **Шаг 1: чей это экран.** Инструменты разработчика → «Inspect» на затемнении:
  - элемент внутри документа iframe — это ваше приложение;
  - элемент снаружи, в странице портала — это Битрикс24.
- **Если экран вашего приложения** (самый частый случай у агентов, которые делали «защиту от посторонних»), не прошла собственная проверка доступа внутри фрейма. Возможные причины по документации:
  - **сторонние cookie.** Cookie без `SameSite=None; Secure` во фрейме не отправляются (общий веб). Решение — раздел 4.5;
  - **`BX24.init` под обработчиком VibeCode не завершается** — проверка, ждущая SDK, не проходит [VC App runtime];
  - **нет ожидаемых POST-параметров.** Проверка ждала `AUTH_ID` / `DOMAIN` из POST, а VibeCode приводит фрейм GET-запросом с `code` / `__init` [VC App runtime];
  - **истекла сессия.** Gateway-сессия длится около 40 минут, `vibe_session` — 24 часа. На `401` приложение должно предлагать «войти заново или выдать доступ», а не блокировать экран [VC App runtime];
  - **политика доступа на VibeCode не пускает пользователя:** `OWNER_ONLY`, или `NAMED_USERS` с пустым списком → `403 BH_ACCESS_DENIED` [VC Access].
- **Если экран Битрикс24** — гипотезы (не подтверждены документацией):
  - установка не завершена (`BX24.installFinish` не вызван): до этого приложение «не установлено», виджеты не показываются [Б24-док];
  - ограничение тарифа или подписки портала: REST только на коммерческих тарифах, VibeCode требует подписку [VC Infrastructure].
- **Профилактика:** никаких глухих оверлеев. При отказе показывайте конкретную причину и действие («Откройте из меню Битрикс24», «Нет доступа: попросите владельца добавить вас») и пишите в лог код причины.

**4. При открытии приложение пыталось загрузить все данные, долго, и не открылось**
- **Причины** [VC App runtime, Optimization]:
  - синхронная выгрузка всех лидов упирается в лимиты (раздел 3.9);
  - на VibeCode — в 14-секундное окно ожидания заголовков (`504 BH_APP_TIMEOUT`);
  - большие `offset` → `INTERNAL_ERROR`.
- **Решение:** заранее собранный и закэшированный снимок, фоновые обновления, агрегация, курсор (раздел 8). Первая отрисовка — только из кэша.

**5. Зависание на экране «Загружаем данные из Битрикс24… Подключение к порталу…»**
- **Причины:**
  - под обработчиком VibeCode `BX24.init` никогда не вызывает колбэк [VC App runtime];
  - страница открыта вне фрейма Б24, и SDK ждёт родителя (общий REST Б24);
  - скрипт SDK заблокирован CSP или блокировщиком;
  - запрос к своему серверу без таймаута;
  - `vibe_app_` без Bearer → `401 TOKEN_MISSING`, а фронтенд крутит спиннер бесконечно [VC Keys & Auth];
  - сервер VibeCode спал: браузер видит страницу пробуждения со статусом 503, пробуждение занимает минуты [VC App runtime].
- **Решение:**
  - не зависеть от BX24 SDK в схеме VibeCode;
  - вызывать SDK только внутри фрейма и с таймаутом (например, 5 секунд), а затем показывать запасной экран;
  - у каждого шага загрузки — таймаут и состояние ошибки с текстом причины;
  - данные — с сервера, из кэша.

**6. Пустые карточки графиков**
- **Типичные причины по документации:**
  - **Пустые группы не приходят.** Агрегация не возвращает группы без записей. Конверсия по стадии `WON`, которой нет, даёт пустоту [VC Recipe CRM analytics].
  - **Выборка обрезана.** `meta.truncated: true` или `422 AGGREGATION_LIMIT_EXCEEDED` при больше чем 5000 записей [VC Entity API].
  - **Неверные имена полей.** У лидов `createdTime`, `opportunity`, `stageId`; у сделок — `createdAt`, `amount`. Неизвестный `select` → `400 UNKNOWN_SELECT_FIELD` [VC Leads, Deals].
  - **Фильтр по UTM.** Фильтр по `utmSource` → `400 UNKNOWN_FILTER_FIELD`. Если фронтенд не показывает ошибку, получается пустой график [VC Leads].
  - **Угаданный код источника.** «YouTube» — это название источника, а код (`sourceId`) нужно найти в `statuses` (раздел 3.12).
  - **Частичные ошибки batch** при `success: true` (`data.summary.failed`) и `meta.pageErrorSample` при ответе 200 [VC Batch, Entity API].
  - **Разбор не того ключа ответа.** У VibeCode данные в `data`, у классического REST — в `result` (общий REST Б24). Шаблон `_base_universal` принимает оба варианта [шаблоны].
  - **Разные часовые пояса.** Даты сделок приходят в UTC, у лидов — со смещением портала, поэтому группировка по дням съезжает [VC Deals, Leads].
  - **Проблемы фронтенда** (общий веб): библиотека графиков с CDN заблокирована CSP `script-src`; график отрисован в скрытом контейнере нулевой ширины.
  - **Классический REST молча отбрасывает неизвестный ключ фильтра** и возвращает всю коллекцию — цифры есть, но неверные [VC Filtering].
- **Решение:**
  - контракт-тест на реальных именах полей из `/fields` или `/guide`;
  - логирование `meta.warnings`, `truncated`, `pageErrorSample`;
  - явное состояние «нет данных за период» вместо пустой карточки;
  - дорисовка нулевых групп.

### 9.2. Другие частые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| `401 TOKEN_MISSING` на ключе `vibe_app_` | Нет `Authorization: Bearer <vibe_session_>` | Взять сессию: Gateway `X-Vibe-Authorization`, `/v1/oauth/token`, `placement-session` [VC Keys & Auth] |
| `401 TOKEN_MISSING` на ключе `vibe_api_` | У ключа нет вебхука портала (например, не было подписки на Маркет в момент выдачи) | Устранить причину, затем «Переподключить» ключ; проверить `b24Credentials.ready` [VC Keys & Auth] |
| `401 WRONG_AUTH_SCHEME` | `vibe_app_` передан в Bearer | Ключ — в `X-Api-Key`, сессия — в Bearer |
| `401 MISSING_API_KEY` в обработчике события | В Bearer передан `auth[access_token]` Б24 | Его нужно обменять на сессию через `placement-session` или вызывать API ключом `vibe_api_` [VC Event handler] |
| `BITRIX_ACCESS_DENIED` после добавления скоупа | Скоупы закрепляются при выпуске | Перевыпустить ключ или ключ авторизации [VC Keys & Auth] |
| `403 SESSION_APP_MISMATCH` | `X-Api-Key` от другого приложения, чем сессия | Использовать ключ того же приложения [VC App runtime] |
| `402 MARKETPLACE_REQUIRED` / `B24_PAID_TARIFF_REQUIRED` | Нет подписки или коммерческого тарифа | Сообщить пользователю; проверить `GET /v1/me?refresh=tariff` [VC Infrastructure] |
| `400 OAUTH_APP_REQUIRED` при привязке места | Использован личный ключ | Нужен `vibe_app_` [VC Placements] |
| `403 PLACEMENT_SCOPE_MISSING` / `PLACEMENT_APP_GRANT_MISSING` | Нет скоупа `placement` или скоупа группы (`crm`, `im`…) | Пересоздать или перевыпустить с нужными скоупами [VC Placements] |
| `400 NO_USER_TOKEN` при публикации | Приложение ни разу не авторизовали на портале | Открыть приложение из Б24, пройти OAuth [VC Apps] |
| В месте встраивания экран входа вместо приложения | `handler` указывает прямо на субдомен, а не на платформу; или пользователь не в списке, а политика не `NAMED_USERS` | Перепривязать место; включить `NAMED_USERS` [VC App runtime] |
| Под обёрткой авто-высоты приложение не открывается | В CSP `frame-ancestors` нет `https://vibecode.bitrix24.tech` | Добавить его [VC App runtime] |
| Приложение не показывается во фрейме | `X-Frame-Options` или `frame-ancestors 'self'` (часто от helmet или nginx по умолчанию) | Раздел 4.4 |
| `405` при открытии из Б24 | Сервер не принимает POST на адрес обработчика | Разрешить POST, отдавать страницу (общий) |
| Деплой «успешен» (HTTP 200), а приложение не работает | На VM провал приходит со статусом 200 | Проверять `success` и `data.steps[]` [VC Deploy] |
| Healthcheck: `attempt 10/10: curl exit=7` | Приложение не слушает `PORT` / 3000 (даже фоновому нужен слушатель) | Слушать `process.env.PORT` [VC Deploy] |
| `start` с `pm2 start … && pm2 save` | Процесс уходит в фон | Команда должна держать процесс на переднем плане [VC Deploy] |
| После деплоя galaxy пропали переменные | Деплой без `env` сбрасывает прежние | Передавать `env` каждый раз; секреты — в карточке [VC Deploy] |
| Сервер VibeCode «сам» останавливается | Сон через 60 минут без **входящих** запросов; исходящие опросы таймер не сбрасывают | `PATCH /sleep null`, `run-mode`, расписания [VC Infrastructure] |
| События теряются | Прямой `event.bind` на спящий субдомен или без `PUBLIC`; Б24 не повторяет доставку | Управляемые подписки VibeCode или офлайн-события [VC App runtime] |
| `EXEC_BUSY` | Идёт другая операция | Ждать `Retry-After`, затем `POST /unstick`; `DELETE /lock` — только последним шагом [VC Infrastructure] |
| Кириллица превратилась в `???` | Тело запроса из Windows PowerShell | UTF-8 байты (раздел 3.1) |
| `bad range in URL` | curl без `-g` при фильтре со скобками | `curl -g '…'` |
| `INVALID_FILTER_OPERATOR` | `LOGIC: OR` / `$or` | `$in` или отдельные запросы |
| Пользовательское поле «не сохраняется», хотя ответ 200 | Поле записывали под именем Б24 (`UF_CRM_…`) вместо имени из схемы (`ufCrm…`) | Брать имена из `/fields` [VC Entity API] |
| Кракозябры в имени пользователя | Заголовок `X-Vibe-User-Name` прочитан как latin1 | Читать `X-Vibe-User-Name-Encoded` [VC App runtime] |
| Чужой сотрудник в `RESPONSIBLE_ID` | В метод Б24 передан `X-Vibe-User-Id` с префиксом | Передавать только числовые значения [VC App runtime] |
| Ссылка на карточку CRM не открывается | Навигация не по клику или во фрейме | `window.top.location.href` прямо в обработчике клика [VC App runtime] |

## 10. Чек-лист «готово» для агента

**Ключи и секреты**
- [ ] Ключ хранится только в env сервера или в секретах платформы. В Git только `.env.example` с заглушками, `.env` — в `.gitignore`.
- [ ] Staged diff проверен на `vibe_`, `client_secret`, `/rest/`.
- [ ] В DevTools (Network, Sources, Application) нет `vibe_api_`, `vibe_app_`, `vibe_session_`, `AUTH_ID`.
- [ ] Ключ `READONLY` с минимальными скоупами (для аналитики).
- [ ] В логах нет токенов и адресов с `code=`, `__init=`, `s=`.

**Доступ**
- [ ] Открытие из Б24 (меню или место встраивания) работает у владельца.
- [ ] Открытие прямого адреса в приватном окне не показывает данных (401/403 или нейтральная страница).
- [ ] На VibeCode политика не шире согласованной. `PUBLIC` не включён для данных.
- [ ] События: `application_token` проверяется, повтор не дублирует эффект.

**Встраивание**
- [ ] Нет `X-Frame-Options`. `frame-ancestors` содержит портал (и `https://vibecode.bitrix24.tech` при авто-высоте).
- [ ] Обработчик принимает POST (классическое приложение).
- [ ] Cookie во фрейме `SameSite=None; Secure` (и `Partitioned`) или вход без cookie.
- [ ] Под VibeCode не используется BX24 SDK; контекст берётся из URL, домен — из `/v1/me`.
- [ ] Установка завершена (`installFinish`, `INSTALLED=true`) — для классического приложения.

**Данные и скорость**
- [ ] Первая отрисовка — из кэша, за секунды. Обновление идёт в фоне по расписанию, время обновления видно на странице.
- [ ] Агрегации проверяют `meta.truncated`; пустые группы дорисованы.
- [ ] Имена полей сверены с `/fields` или `/guide`; `select` без лишнего.
- [ ] На `429` — backoff по `Retry-After`. У запросов есть таймауты и состояния ошибок.

**Деплой**
- [ ] (VibeCode) Деплой: `success: true`, `healthcheck` ok. Проверка через `api-bearer` пройдена, токен отозван.
- [ ] (VibeCode) Переданы `displayName` и `description`. Настроен сон или режим работы. Пользователь знает о стоимости.
- [ ] (Свой сервер) HTTPS валиден, автозапуск после перезагрузки, бэкап данных и токенов, сделана копия заменяемых файлов, есть план отката.
- [ ] Проверена именно изменённая функция в боевой среде, а не только «сервер жив».

**Отчёт**
- [ ] Указано, что проверено (где и как) и что нет. Локальный результат не выдаётся за боевой.

## 11. Шпаргалка запросов (curl)

Ключи — только из переменных окружения:

```bash
export VIBE_API_KEY="vibe_api_XXXX"   # личный ключ (в реальности — из .env, не в истории shell)
export VIBE_APP_KEY="vibe_app_XXXX"   # ключ авторизации приложения
export VIBE_SESSION="vibe_session_XXXX"
export V=https://vibecode.bitrix24.tech/v1
```

**Проверить ключ и возможности**

```bash
curl -s "$V/me" -H "X-Api-Key: $VIBE_API_KEY" \
  | jq '.data | {type, portal, scopes, accessMode, b24Credentials, servers: .capabilities.servers.create, placements: .placements.bindPrerequisite}'
# После смены тарифа или переподключения ключа: "$V/me?refresh=tariff"
```

**Контракт полей**

```bash
curl -s "$V/leads/fields" -H "X-Api-Key: $VIBE_API_KEY" | jq '.data.fields | keys'
curl -s "$V/guide" -H "X-Api-Key: $VIBE_API_KEY" > guide.json
```

**Список сделок с фильтром** (`-g` обязателен для скобок)

```bash
curl -g -s "$V/deals?limit=50&order[id]=asc&withTotal=false&select=id,title,amount,stageId,createdAt&filter[stageId]=NEW&filter[>=amount]=50000" \
  -H "X-Api-Key: $VIBE_API_KEY"
# Следующая страница: добавьте &filter[>id]=<meta.nextAfterId>
```

**Поиск лидов за период** (POST)

```bash
curl -s -X POST "$V/leads/search" -H "X-Api-Key: $VIBE_API_KEY" -H "Content-Type: application/json" \
  -d '{"filter":{"createdAt":{"$gte":"2026-10-01T00:00:00","$lte":"2026-10-31T23:59:59"}},
       "select":["id","sourceId","stageId","createdTime","utmSource"],"sort":"id","limit":500}'
```

**Справочник источников и агрегация лидов по источнику**

```bash
curl -g -s "$V/statuses?filter[entityId]=SOURCE" -H "X-Api-Key: $VIBE_API_KEY"

curl -s -X POST "$V/leads/aggregate" -H "X-Api-Key: $VIBE_API_KEY" -H "Content-Type: application/json" \
  -d '{"aggregate":[{"field":"*","function":"count"}],
       "filter":{"createdAt":{"$gte":"2026-10-01T00:00:00"}},
       "groupBy":["sourceId","stageId"]}' \
  | jq '.data | {count, groups, truncated: .meta.truncated}'
```

**Batch**

```bash
curl -s -X POST "$V/batch" -H "X-Api-Key: $VIBE_API_KEY" -H "Content-Type: application/json" \
  -d '{"calls":[
        {"id":"new","entity":"deals","action":"list","params":{"filter":{"stageId":"NEW"},"select":["id","title","amount"],"limit":50}},
        {"id":"user1","entity":"users","action":"get","entityId":1}
      ]}' | jq '.data.summary, .data.errors'
# success:true не значит «всё прошло» — смотрите data.summary.failed и data.errors
```

**Создать OAuth-приложение** (ключ `vibe_app_` вернётся один раз в `rawKey`)

```bash
curl -s -X POST "$V/apps" -H "X-Api-Key: $VIBE_API_KEY" -H "Content-Type: application/json" \
  -d '{"title":"Дашборд лидов","scopes":["crm","user","placement"],"mode":"READONLY",
       "appUrl":"https://app-xxxxxxxx.vibecode.bitrix24.tech"}' \
  | jq '.data | {id, bitrixClientId, catalogStatus, handlerUrl}'   # rawKey сразу сохраните в секреты, не выводите в лог
# Перед созданием проверьте, нет ли уже подходящего приложения: curl -s "$V/apps" -H "X-Api-Key: $VIBE_API_KEY"
```

**Задать `appUrl`**

```bash
curl -s -X PATCH "$V/apps/APP_ID" -H "X-Api-Key: $VIBE_API_KEY" -H "Content-Type: application/json" \
  -d '{"appUrl":"https://app-xxxxxxxx.vibecode.bitrix24.tech"}'
```

**Места встраивания: справочник, привязка, проверка**

```bash
curl -s "$V/placements/available" -H "X-Api-Key: $VIBE_API_KEY" \
  | jq -r '.data.groups | to_entries[] | .key as $g | .value[] | "\($g)\t\(.code)\t\(.requiredScope)\t\(.restBindable)"'

curl -s -X POST "$V/placements/bind" \
  -H "X-Api-Key: $VIBE_APP_KEY" -H "Authorization: Bearer $VIBE_SESSION" -H "Content-Type: application/json" \
  -d '{"placement":"CRM_DEAL_DETAIL_TAB","handler":"https://app-xxxxxxxx.vibecode.bitrix24.tech/deal-tab","title":"Аналитика"}'

curl -s "$V/placements" -H "X-Api-Key: $VIBE_APP_KEY" -H "Authorization: Bearer $VIBE_SESSION" | jq '.data.portalSync'
```

**Опубликовать в каталог портала**

```bash
curl -s -X POST "$V/apps/APP_ID/publish" -H "X-Api-Key: $VIBE_API_KEY" -H "Content-Type: application/json" \
  -d '{"placements":["CRM_DEAL_DETAIL_TAB"],"catalogTitle":"Дашборд лидов"}'
```

**Обмен одноразового `code` на сессию** (приложение на своём сервере, вызов с сервера)

```bash
curl -s -X POST "$V/oauth/token" -H "Content-Type: application/json" \
  -d '{"app_key":"'"$VIBE_APP_KEY"'","code":"CODE_FROM_QUERY","redirect_uri":"https://dash.example.com/"}'
# → { access_token: "vibe_session_…", user: {...}, expires_in: 86400 } — хранить только на сервере
```

**Создать сервер VibeCode** (это расход — только с согласия пользователя)

```bash
curl -s -X POST "$V/infra/servers" -H "X-Api-Key: $VIBE_API_KEY" -H "Content-Type: application/json" \
  -H "Idempotency-Key: leads-dash-001" \
  -d '{"provider":"bitrix-cloud","name":"leads-dash","plan":"bc-small","region":"ru-central1-b",
       "displayName":"Дашборд лидов","description":"Лиды по источникам за период"}' \
  | jq '.data | {id, kind, status, blackholeStatus, subdomain, appUrl, accessPolicy}'

# VM: ждать status=running и blackholeStatus=CONNECTED
curl -s "$V/infra/servers/SERVER_ID" -H "X-Api-Key: $VIBE_API_KEY" | jq '.data | {status, blackholeStatus, kind, reachability}'
```

**Задеплоить** (архив base64, таймаут ≥ 690 с)

```bash
tar -czf app.tar.gz -C ./app .
jq -n --rawfile c <(base64 -w0 app.tar.gz) \
  '{source:{content:$c}, runtime:"node24",
    install:"cd /opt/app && npm ci --omit=dev", start:"cd /opt/app && node server.js", port:3000,
    env:{NODE_ENV:"production"}, displayName:"Дашборд лидов", description:"Лиды по источникам за период"}' > deploy.json
curl -s --max-time 700 -X POST "$V/infra/servers/SERVER_ID/deploy" \
  -H "X-Api-Key: $VIBE_API_KEY" -H "Content-Type: application/json" --data-binary @deploy.json \
  | jq '{success, appUrl: .data.appUrl, steps: [.data.steps[]? | {step, status}], error}'
# Ключ VIBE_API_KEY для самого приложения передавайте через секреты карточки, а не в деплой-json в истории.
```

**Логи, лента событий, проверка через публичный путь**

```bash
curl -s "$V/infra/servers/SERVER_ID/logs?service=app&lines=100" -H "X-Api-Key: $VIBE_API_KEY" | jq -r '.data.logs[]'
curl -s "$V/infra/servers/SERVER_ID/activity?limit=20" -H "X-Api-Key: $VIBE_API_KEY"

TOK=$(curl -s -X POST "$V/infra/servers/SERVER_ID/access-tokens" -H "X-Api-Key: $VIBE_API_KEY" \
  -H "Content-Type: application/json" -d '{"mode":"api-bearer","ttlSeconds":600,"name":"smoke"}')
curl -s -o /dev/null -w '%{http_code}\n' "$(echo "$TOK" | jq -r .data.appUrl)/api/health" \
  -H "Authorization: Bearer $(echo "$TOK" | jq -r .data.token)"
curl -s -X DELETE "$V/infra/servers/SERVER_ID/access-tokens/$(echo "$TOK" | jq -r .data.id)" -H "X-Api-Key: $VIBE_API_KEY"
```

**Сон и доступ**

```bash
curl -s -X PATCH "$V/infra/servers/SERVER_ID/sleep" -H "X-Api-Key: $VIBE_API_KEY" -H "Content-Type: application/json" \
  -d '{"sleepAfterMinutes":240}'
# Расширение доступа — ТОЛЬКО с явного согласия пользователя:
curl -s -X PATCH "$V/infra/servers/SERVER_ID/access-policy" -H "X-Api-Key: $VIBE_API_KEY" -H "Content-Type: application/json" \
  -d '{"accessPolicy":"NAMED_USERS"}'
```

**Классический REST Б24** (общий REST Б24; адрес вебхука — это пароль, держите его в env)

```bash
# Входящий вебхук, POST, чтобы секрет не попадал в логи прокси вместе с параметрами
curl -s -X POST "$B24_WEBHOOK_URL/crm.lead.list.json" \
  -d 'select[]=ID' -d 'select[]=SOURCE_ID' -d 'filter[>DATE_CREATE]=2026-10-01' -d 'start=0'

# Продление OAuth-токена локального приложения (сервер — oauth.bitrix24.tech по [Б24-док]; параметры — общий REST Б24)
curl -s "https://oauth.bitrix24.tech/oauth/token/" \
  --data-urlencode grant_type=refresh_token \
  --data-urlencode client_id="$B24_CLIENT_ID" \
  --data-urlencode client_secret="$B24_CLIENT_SECRET" \
  --data-urlencode refresh_token="$REFRESH_TOKEN"
```
