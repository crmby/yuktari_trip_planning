# Настройка CRM и вкладки сделки

## Переменные окружения

Заполнить локальный `.env` для доставки или защищённые переменные сервера, не отправляя ключи в чат:

| Переменная | Значение |
|---|---|
| APP_MODE | bitrix |
| VIBE_APP_KEY | OAuth-ключ существующего приложения, префикс vibe_app_ |
| APP_URL | https://app-13fb2e983443.vibecode.bitrix24.tech |
| B24_DOMAIN | yuktari.bitrix24.by |
| DATA_DIR | /opt/data/yuktari-trip-planning на выделенном сервере |
| PLANNER_MANAGER_IDS | Необязательно: ID менеджеров настроек через запятую |
| B24_ROUTE_IBLOCK_ID | Необязательно: ID инфоблока, если metadata поля его не возвращает |
| B24_ROUTE_IBLOCK_TYPE | Больше не используется: фактический тип определяется через GET /lists/{id}/type |

Ключ управления VIBE_API_KEY нужен только команде доставки; он не передаётся работающему приложению. Пользователь сообщил, что добавит VIBE_APP_KEY. Содержимое `.env` агент не просматривал и ключ не проверял.

Для OAuth-приложения нужны доступы crm, user, lists и placement. Проверить доступы существующего приложения в VibeCode; расширение прав и создание нового приложения агент не выполнял. Список сотрудников требует именно user, а не только user_basic. Каждый сотрудник открывает приложение из портала и проходит обычную авторизацию VibeCode.

## Проверка входа

Сервер использует X-Vibe-Authorization только как кандидат сессии: проверяет её запросом /me вместе с серверным VIBE_APP_KEY, сверяет портал и текущего сотрудника, затем проверяет профиль через /users/me. Роль администратора берётся из подтверждённого профиля. X-Vibe-User-ID, роль из заголовка и ID сделки в адресе сами по себе вход не подтверждают. Внешние API-вызовы не заменяют вход сотрудника. Ключ и bearer не возвращаются браузеру и не сохраняются в базе приложения.

Без VibeCode Gateway локальный APP_MODE=bitrix закономерно показывает требование входа. Для локального просмотра используйте demo. Демо не переключается автоматически при ошибке авторизации рабочего режима.

## Вкладка в сделке

После ручной выкладки и входа администратора нажать «Добавить вкладку в сделку» и подтвердить. Приложение отправит /placements/bind с CRM_DEAL_DETAIL_TAB, своим HTTPS APP_URL и названием «Планирование выездов». Затем открыть сделку заново. Сам деплой регистрацию не выполняет.

Контекст placement_options.ID подставляет текущую сделку и блокирует выбор другой. Поиск доступен при открытии приложения отдельно. Проверка прав на каждую сделку и контакт остаётся на API Битрикс24, ID в адресе её не обходит.

## Сохранение и общий резерв

DATA_DIR содержит planning.json с мастерами, группами, графиками, резервами и незавершёнными операциями. Это приватные данные, не публиковать и не добавлять в Git. Каталог должен переживать перезапуск и чистую перевыкладку. Одна общая файловая база рассчитана на один сервер; несколько независимых серверов без общей базы не поддерживаются.

Перед записью сервер проверяет свежий снимок полей контакта и сделки, повторно считает доступность и резервирует время под файловой блокировкой. Контакт и сделка обновляются последовательно: общей транзакции CRM между ними нет. Поэтому результат подтверждается повторным чтением. При обрыве связи или частичной записи резерв сохраняется, кнопка «Проверить результат» только перечитывает CRM. После перезагрузки страницы незавершённая операция снова предлагается для проверки.

Если значения не совпали, менеджер должен сверить поля контакта и сделки с несохранённой формой и исправить незавершённые значения в CRM, затем проверить результат. Автоматического отката или повторного PATCH нет. Не удаляйте резерв вручную, пока неизвестен результат CRM-записи. После аварийного завершения процесса может остаться planning.lock: администратор должен остановить приложение, убедиться в отсутствии сохраняющего процесса, сохранить копию DATA_DIR и убрать только устаревший lock. Агент этого не выполнял.

Отмена очищает дату и границы окна в сделке; контакт, комментарий, услуги и стадии сохраняются. История остаётся в серверном хранилище. После обновления календарь получает сделки по заполненной дате обслуживания; отменённые с очищенной датой туда не попадают.

## Приёмка на портале

1. Открыть приложение от имени администратора, проверить маршруты из инфоблока. Создать группу, выбрать мастера из сотрудников, настроить его направления и смены.
2. Зарегистрировать вкладку. Открыть тестовую сделку с основным контактом: проверить текущую сделку, адрес, квартиру, маршрут, все услуги и заполненные поля выезда.
3. Сохранить тестовый выезд; сверить три поля контакта и шесть полей сделки непосредственно в CRM и после перезагрузки приложения.
4. В отдельной вкладке найти другую сделку по названию и ID. Проверить маршрутный лист, квартиру, телефон, услуги, отдельные окно и комментарий.
5. Проверить права обычного сотрудника и отказ доступа постороннему; настройки мастеров доступны только администратору или назначенному менеджеру приложения.
6. Проверить одновременную запись на последнее окно, перенос и отмену. Убедиться, что существующие автоматизации портала не дают нежелательных побочных эффектов.

Пока проверено локально на вымышленных ответах API: авторизация, карта полей, пагинация маршрутов, запись и чтение, устаревшие данные, конкуренция, частичный сбой, потерянный ответ, настройки и защита HTTP. В браузере проверены поиск, подстановка, сохранение, лист и контекст сделки. Реальные авторизация, типы полей, доступы инфоблока и встраивание требуют проверки после ручного деплоя.

Календарь перечитывает CRM при выборе даты, по кнопке и раз в минуту, пока открыт лист. Роботы и фоновые подписки не добавляются. Существующие CRM-выезды без назначения в базе приложения показываются без мастера; мастер резервируется при сохранении через приложение. Прямое изменение даты в CRM само не переносит серверный резерв: изменение назначения выполняйте через приложение. Алгоритм использует шаг 30 минут, длительности 30/60/120 минут и 30 минут между выездами; дорожные данные Wialon не используются.

Документация платформы: [авторизация и runtime](https://vibecode.bitrix24.tech/docs/infra/app-runtime), [сотрудники](https://vibecode.bitrix24.tech/docs/entities/users/list), [поля контакта](https://vibecode.bitrix24.tech/docs/entities/contacts/fields).

## Ошибка входа внутри Битрикс24

Сообщение старой сборки «Сессия Битрикс24 истекла» было общим для всех HTTP 401. Оно не доказывало истечение сессии: такой статус бывает также при неверном/отозванном/истёкшем ключе, первом входе без доступа и отказе токена портала. В исправленной сборке сообщение различает причины, содержит безопасный код VibeCode и этап проверки, без ключей, сессий и исходного ответа API.

- INVALID_API_KEY / KEY_INACTIVE / KEY_EXPIRED: проверить VIBE_APP_KEY именно в переменных работающего сервера. Локальная правка .env не обновляет уже работающий сервер сама по себе.
- SESSION_APP_MISMATCH: ключ сервера и сессия посетителя относятся к разным OAuth-приложениям. Сверить существующее приложение, через которое открыт интерфейс; не создавать новые ключи наугад.
- INVALID_SESSION / TOKEN_MISSING и прочие 401 входа: полностью закрыть приложение и открыть заново из меню Битрикс24, при первом входе выдать доступ приложению. Обновление или показ старой вкладки не выполняет новый placement POST.
- Отказ шлюза до Node.js тоже показывается как необходимость входа с безопасным кодом, если шлюз его прислал.

Во время активного заполнения формы приложение раз в четыре минуты делает лёгкий запрос к своему серверу, чтобы Gateway мог продлить свою сессию. Это не обновляет истёкший OAuth-токен, не выдаёт права и не заменяет повторный вход. В скрытой или неактивной вкладке запросы не поддерживаются намеренно. Перед сохранением авторизация по-прежнему проверяется сервером.

Источник: [сроки сессий и восстановление входа VibeCode](https://vibecode.bitrix24.tech/docs/infra/app-runtime).

## Проверка принадлежности OAuth-ключа без пользовательской сессии

Из того же терминала, где работает npm run deploy, выполнить npm run app:check. Команда использует локальные VIBE_APP_KEY, VIBE_API_KEY, B24_DOMAIN, APP_URL и SERVER_ID. Делает только GET /me с OAuth-ключом, затем GET /apps/{OAuth-ID} и GET /infra/servers/{SERVER_ID} с существующим ключом доставки. Проверяет тип ключа, портал, адрес карточки OAuth-приложения и адрес сервера. Не запрашивает CRM, не печатает ключи, их фрагменты, токены или исходные ответы. Если ключ доставки не имеет доступа к карточке, результат явно остаётся неполным.

Совпадение подтверждает принадлежность локального ключа приложению с указанным адресом. Оно не доказывает, что тот же ключ установлен в работающем сервере, и не определяет приложение, которое выдало конкретную сессию посетителя: несколько OAuth-приложений могут указывать на один адрес. Для окончательной проверки нужны код отказа из работающей сборки и сверка её серверных настроек.

## Проверка обновления сборки, версия 0.3.1

Если приложение по-прежнему дословно показывает «Сессия Битрикс24 истекла. Переоткройте приложение из портала.», этот текст соответствует старому клиенту до коммита e6ed068. В текущем src/ и public/ его нет. Само сообщение не подтверждает, что после успешной команды доставки перезапустился именно новый код.

Версия 0.3.1 явно показывает номер внизу экрана, возвращает его в GET /health, GET /api/runtime и заголовке X-App-Version. GET /api/runtime не читает CRM и на уровне приложения не требует пользовательской сессии, но проверку доступа шлюза не обходит. Поэтому номер можно увидеть даже при ошибке проверки сотрудника, если Gateway пропускает запрос к приложению.

После доставки проверить «Версия 0.3.1» и новый полный текст ошибки с кодом и этапом. Пока виден прежний текст, перепривязка OAuth или смена переменных не заменяет проверку того, какой код реально работает. 404 чтения карточки сервера и 401 проверки пользовательской сессии — разные запросы и разные границы доступа; один не доказывает причину другого.

## BITRIX_ERROR при открытии

После исправления выбора управляющего ключа пользователь получил сообщение «Битрикс24 не выполнил запрос. Код: BITRIX_ERROR; доступ к данным» сразу при открытии. Для начальной загрузки этот этап следует после проверки ключа/сессии и профиля: запрашиваются поля сделок, поля контактов, настройки пользовательских полей контактов, категории сделок и элементы инфоблока маршрутов. Общий код без конкретного запроса недостаточен для определения причины; он не доказывает проблему ключей или необходимость перепривязки OAuth.

Обработчик теперь выводит локальное название конкретного этапа и безопасный error.b24Code, если он есть. Распознанный error.cause отдельно сообщает о правах сотрудника, OAuth-скоупах или скоупах ключа. Свободные error.message/details, query-параметры, ID записей и токены не выводятся. Статус 422 сохраняется. Повторную запись, расширение прав и изменение маршрутов по этому общему коду приложение не выполняет.

Источник структуры ошибок: https://vibecode.bitrix24.tech/docs/errors.

## Загрузка маршрутов: фактический тип инфоблока

При BITRIX_ERROR с b24Code=0 на загрузке маршрутов была установлена конкретная граница отказа — /lists/{id}/elements. Сам код 0 не указывает причину. В коде обнаружено неподтверждённое предположение: при отсутствии типа в metadata поля использовался lists. Теперь до запроса элементов выполняется документированный GET /lists/{id}/type, который не требует знания типа заранее. Неподдерживаемый тип или отказ чтения останавливает загрузку без перебора типов и источников.

Запрос элементов упрощён: подтверждённый тип, select и start, без filter ACTIVE. Если ACTIVE возвращён как N/false, такой элемент исключается локально. Пагинация и числовые ID маршрутов сохраняются; демо-значения не подставляются. Это исправление предположения в коде, а не подтверждение причины на реальном портале. При сохранении отказа нужны сведения о самом справочнике от администратора, права/ключи автоматически не меняются.

Источник: https://vibecode.bitrix24.tech/docs/lists/lists/type.

## Сетевой сбой и восстановление интерфейса, версия 0.3.2

Начальная загрузка больше не задерживает подключение обработчиков кнопок: меню разделов работает сразу. Показаны состояния «Загрузка данных» / «Данные недоступны». При отказе начальной загрузки доступна кнопка «Повторить загрузку» — повторяет только чтение runtime/bootstrap и начальных данных, без перезагрузки страницы и без CRM-записи. После успешного чтения возвращаются данные и разрешённые текущему пользователю действия. Формы сохранения до получения данных остаются отключены; навигация и переход обратно к листу доступны.

Сетевой отказ серверного запроса теперь называет этап и безопасную категорию: TIMEOUT, DNS, TLS или NETWORK. Это относится к соединению Node.js на сервере приложения с VibeCode API, а не доказывает сбой браузера пользователя. Исходные сетевые исключения, URL-параметры, токены и ключи не выводятся. Записи CRM при неизвестном исходе по-прежнему требуют сверки; кнопка загрузки не повторяет PATCH.

Локально проверено в браузере с тестовым API: начальный сетевой отказ, переход в «Мастера» при ошибке, повтор загрузки без обновления страницы, появление мастеров/групп, разблокировка разрешённых кнопок и открытие формы мастера. Ошибок JavaScript не обнаружено. Это проверка восстановления интерфейса, не подтверждение сетевой доступности реального портала.

## Все воронки и длительное чтение, версия 0.3.3

В рабочем режиме больше нет списка разрешённых названий. Воронка не определяет доступ к сделке или тип клиента. Доступ проверяет CRM API от имени сотрудника; наличие связанной компании определяет юридическое лицо. В карточке и фильтре показаны реальные ID/названия. Справочник читается постранично через GET /categories/2, включая основную воронку ID 0. Поиск и календарь не отправляют фильтр categoryId; фильтр в интерфейсе применяется к загруженным строкам. Сделка, воронки которой ещё нет в кэшированном справочнике, не блокируется, если CRM разрешил чтение самой сделки. Четыре старых названия остались только в вымышленном демо.

Для GET интерфейс запрашивает фоновое чтение (X-Planner-Async: 1). Сервер немедленно отдаёт 202 с непрогнозируемым jobId; отдельные короткие запросы проверяют результат. Внутри задачи остаются обычные /me, /users/me и все CRM-проверки. До их успешного завершения данные не выдаются. Результат доступен только той же сессии, по хэшу Bearer, без токенов в ответе. Есть защита от одновременных одинаковых чтений, лимиты 4 активных на сессию / 100 задач всего; завершённые результаты недоступны спустя минуту, незавершённые — 10 минут. Очистка при обращениях, задачи только в памяти и теряются при перезапуске. Серверная задача прерывается по общему пределу.

Для фоновых GET ожидание одного ответа VibeCode увеличено с 10 до 150 секунд. Обычные запросы и записи сохранили прежние пределы; POST не переводится в задачи и не повторяется автоматически. Увеличение ожидания не гарантирует устранение проблем DNS/TLS/подключения или перегрузки API. Реальная причина задержки /me на сервере пользователя ещё не проверена.

Основание: [ограничения шлюза и 202 + jobId](https://vibecode.bitrix24.tech/docs/infra/app-runtime), [ожидание API](https://vibecode.bitrix24.tech/docs/optimization), [категории с основной воронкой](https://vibecode.bitrix24.tech/docs/entities/categories).

## Справочники и поиск, версия 0.3.4

По уточнению пользователя списки используют только ID 6, 0, 8 и 10, в этом порядке. Названия берутся из CRM, поэтому переименование не меняет принадлежность воронки. Из фильтра исключены остальные воронки. Поиск и календарь отправляют тот же набор categoryId. Открытие текущей сделки по-прежнему проверяет CRM-доступ, без сравнения названий.

Первый вход загружает схему UF-полей, воронки и маршруты. Затем они берутся из постоянного приватного кэша DATA_DIR/references/planning.json. Кэш разделён по порталу и сотруднику, содержит до 40 наборов, не содержит сессионных токенов и не попадает в архив деплоя. Он переживает рестарт при сохранённом DATA_DIR. Автоматического TTL нет; отсутствующий набор загружается при первом обращении. Мастера и графики уже находятся в общей базе приложения, повторная загрузка справочников из CRM для них не требуется. Проверка сессии /me и /users/me выполняется перед выдачей данных и не кэшируется.

«Подгрузить данные» явно перечитывает схемы, воронки, маршруты и общие настройки мастеров. Для менеджера также обновляется кэш сотрудников. Если один из запросов не выполнен, показано сообщение; прежний успешный кэш не затирается ошибкой. Список сотрудников загружается при первом открытии выбора, страницами по 50 активных записей. Поиск по словам ФИО выполняется в полученном списке, без двух CRM-запросов на каждое нажатие. Сохранение мастера дополнительно проверяет запись сотрудника через CRM. Недостаток user-скоупа/прав/тарифа остаётся явной ошибкой; права автоматически не расширяются. Обновление справочников не записывает CRM и не сбрасывает несохранённые поля выезда; при открытом диалоге настроек предложено сначала закрыть его.

В отдельном приложении список сделок заполняется без ввода: первые 10 доступных активных (closed=false), по возрастанию ID. По названию, начиная с одного символа, читаются все страницы совпадений в четырёх воронках, включая закрытые сделки; точный числовой ввод ищет ID. При более 5000 совпадений показано предложение уточнить запрос вместо неполной выдачи. Старые ответы поиска не заменяют новые; запросы выполняются по очереди, чтобы не создавать параллельную нагрузку. Выбор сделки загружает её актуальные поля. Кэш сделок и контактных данных не создаётся.

Убраны полоса демонстрационных данных, технический текст о синхронизации, подпись текущей сделки и пояснение соответствия маршрутов группам.

API сверены с [фильтрацией](https://vibecode.bitrix24.tech/docs/filtering), [списком сделок](https://vibecode.bitrix24.tech/docs/entities/deals/list) и [списком сотрудников](https://vibecode.bitrix24.tech/docs/entities/users/list). Проверки выполнены на вымышленных данных; работа с реальными правами портала требует проверки после доставки.

## Формы, подтверждение сохранения и живой календарь, версия 0.3.5

Видимый выбор сделки и сотрудника состоит из одного поля с выпадающими результатами, навигацией стрелками/Enter/Escape и идентификатором в скрытом поле формы. После выбора сделки выполняется чтение её актуальных полей, после выбора сотрудника заполняется ФИО. Во вкладке сделки поле содержит текущую сделку и закрыто для изменения. Длительность — целое число минут от 1 до 1440; ограничения 30/60/120 больше нет. Прочие ограничения свободного времени и графика сохранены.

Пользователь выбрал штатный поиск адреса в карточке контакта, без внешнего адресного сервиса. Поле адреса в приложении показывает значение контакта, ссылка «Открыть адрес в контакте» открывает его карточку. После сохранения адреса в Б24 кнопка «Перечитать сделку» читает актуальное значение. Если прочитанное UF содержит текст и суффикс координат после |, в интерфейсе показан текст, а неизменённое исходное значение сохраняется при записи остальных полей выезда. Сырые адреса не отправляются внешним сервисам.

Убраны заголовок «Проверьте параметры», пояснение позиции листа, пояснение проверки CRM и кнопки ручного подтверждения синхронизации / добавления вкладки. Настройка placement по API сохранена для администратора, но кнопки в интерфейсе нет. До заполнения формы показана нейтральная подсказка; запись без корректных параметров остаётся запрещена.

Исправлено восстановление: при старте больше не выбирается первая незавершённая операция из любых сделок. Ранее она могла ссылаться на недоступную сделку, давать ENTITY_NOT_FOUND и глобально блокировать календарь/выбор. Проверка касается только выбранной сделки. Чтение /deals/:id подтверждает совпавшую операцию в локальном журнале без PATCH; клиент повторяет чтение каждые 5 секунд до подтверждения, пока вкладка видима. Опрос не повторяет CRM-запись. При фактическом несовпадении резерв сохраняется, автоматического затирания CRM нет. Старые недоступные операции не удаляются и не снимают резервы только по коду 403/404. При смене основного контакта приватный старый черновик не выдаётся как данные нового контакта.

POST сохранения/настроек теперь также поддерживает 202 + идентификатор задачи. Перед запуском проверяются Origin, X-Requested-With, JSON и размер, внутри задачи выполняются обычная авторизация, права, резерв и проверка результата. Идентичные активные запросы объединены, операция выезда остаётся идемпотентной по operationId. Опрос задачи возвращает готовый результат и не исполняет её заново. Сроки/изоляция сессии те же, что у чтений. Это устраняет необходимость удерживать POST до завершения длительных CRM-запросов за пределами окна шлюза.

Календарь: все направления выбраны по умолчанию, страницы по 20 сделок уже содержат нужные поля UF, поэтому нет обязательного GET каждой карточки поверх списка. Контакт переиспользуется только внутри текущей страницы, не как статичный CRM-кэш. Строка с недоступным/неполным контактом не срывает всю страницу. Выезды из общего хранилища также добавляются после свежей проверки прав CRM, если дата ещё не подтвердилась, чтобы резерв не исчезал из списка. Контактные данные старого резерва не раскрываются при изменившемся контакте. Фильтр воронок 6/0/8/10 сохранён. Ссылки в строках теперь обычные HTTPS-ссылки CRM с target=_blank.

Видимый календарь перечитывается каждые 15 секунд, при возвращении фокуса/видимости и переходе в маршрутный лист. BroadcastChannel сразу сообщает другим открытым вкладкам о сохранении; сообщение содержит только признак изменения, затем получатель сам читает разрешённые ему данные. У страниц есть защита поколений и параллельной загрузки. Поэтому это обновляемый список, не постоянный кэш выездов; между разными браузерами обновление идёт при следующем опросе. Справочники маршрутов/сотрудников по-прежнему обновляются кнопкой «Подгрузить данные». Интервал опроса фоновой задачи начинается со 150 мс и растёт до 1,5 с для долгих операций.

Локально проверены 47 тестов и браузер: выбор в одном поле загружает адрес/квартиру/услуги, ФИО подставляется из сотрудника; старт с посторонней недоступной операцией не даёт ошибки; выезд 75 минут сохранён из вкладки сделки и найден в общем списке на ту же дату; ссылка ведёт в CRM, по умолчанию выбраны все направления. Реальный портал/скорость внешнего API отдельно не подтверждены.
