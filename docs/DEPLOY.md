# Окружение и доставка в VibeCode

## Что подготовлено

`npm run deploy` упаковывает только `src/`, `public/`, `package.json`, `package-lock.json` и отправляет multipart-запрос в `POST /v1/infra/servers/{SERVER_ID}/deploy?stream=false`.

Конфигурация по примеру SyncPoint: runtime `node20`, установка `npm ci --omit=dev`, запуск `node src/server.js`, порт 3000. Скрипт переносим между Windows и Linux, использует Node.js и `tar`.

Перед отправкой проверяются `/v1/me` и режим существующего сервера: допускается только `BLACKHOLE`. Скрипт не создаёт сервер, не меняет политику доступа, не публикует приложение в каталоге и не включает платные режимы. Сетевой таймаут — 15 минут; проверяются HTTP-статус, `success` и статусы шагов ответа.

## Локальный `.env`

Заполните файл локально, без отправки значений в чат:

| Поле | Значение |
|---|---|
| `SERVER_ID` | ID выделенного для этого приложения существующего сервера VibeCode |
| `VIBE_API_KEY` | Ключ с правом доставки на этот сервер (`vibe:infra`) |
| `B24_DOMAIN` | Домен целевого портала без протокола и пути |
| `HOST` | Локально `127.0.0.1`; при деплое устанавливается `0.0.0.0` |
| `PORT` | Локальный порт, по умолчанию 3000 |

Ключ управления передаётся только API VibeCode в заголовке запроса и не устанавливается в среду работающего приложения. Данные CRM на этом этапе не запрашиваются. Секрет интеграции и проверка пользовательской сессии будут добавлены отдельно.

## Порядок выпуска

1. Получить доступ к репозиторию, проверить удалённую историю и отправить согласованные изменения без force push.
2. На машине доставки получить нужный коммит через `git pull --ff-only`.
3. Выполнить `npm ci`, `npm run check`, `npm test`, `npm run deploy:check` и проверить содержимое архива.
4. Проверить, что `SERVER_ID` относится к выделенному серверу этого приложения. `cleanDeploy=true` заменяет рабочий код на целевом сервере. До первой доставки сохранить текущую версию и параметры сервера, если там уже есть приложение.
5. Выполнить `npm run deploy` после настройки целевого сервера. Реальный деплой может расходовать Вайбы.
6. Проверить журнал шагов в VibeCode, `/health` и стартовый экран через шлюз. Ответ API об успехе не заменяет проверку работы в портале.

Для отката доставить прежний проверенный коммит тем же способом. Постоянное хранилище ещё не создаётся; перед добавлением данных понадобятся отдельный каталог, резервное копирование и правила миграций.

## До приёмки приложения в портале

- Проверить актуальный контракт [Deploy API](https://vibecode.bitrix24.tech/docs-content/infra/deploy.md) и [App runtime](https://vibecode.bitrix24.tech/docs-content/infra/app-runtime.md). Получить эти страницы при текущей настройке не удалось; сетевой контракт взят из SyncPoint и приложенного скилла, реальная доставка не проверена.
- Реализовать вход сотрудников и серверную проверку сессии до добавления CRM-данных.
- Настроить приложение/место встраивания VibeCode, включить `placementResizeEnabled`, проверить высоту iframe. Код использует сообщение `vibe:resize`, а не BX24 SDK.
- Настроить нужную политику доступа и проверить открытие сотрудником и посторонним в приватном окне.
- Проверить CSP с фактическим порталом и оболочкой VibeCode.

Домен портала и ID существующего сервера записаны по данным пользователя. Успешного HTTP-ответа API с ключом ещё не получено из-за сетевого сбоя. Версия 0.2 подготовлена для ручной доставки пользователем: [MANUAL-DEPLOY.md](MANUAL-DEPLOY.md). Деплой агентом не выполнялся.
