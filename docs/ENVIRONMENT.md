# Где взять переменные окружения

Заполнять локальный .env в корне Yuktari, рядом с package.json. Не отправлять значения ключей в чат и не заменять заполненный файл .env.example. Этот список не требует создания новых ключей: сначала использовать существующие.

## Обязательные для CRM и доставки

| Переменная | Где взять / что указать |
|---|---|
| VIBE_API_KEY | VibeCode → «Ключи API» (/keys): существующий ключ, которым уже успешно работает npm run deploy на этом сервере. Ему нужен доступ к инфраструктуре сервера. Это ключ доставки; не копировать сюда OAuth-ключ только потому, что он указан в карточке другого приложения. Не перевыпускать работающий ключ наугад. |
| VIBE_APP_KEY | VibeCode → «Ключи авторизации» (/apps) → существующее OAuth-приложение «Планирование выездов». Нужен полный секрет с префиксом vibe_app_, ранее сохранённый при его выдаче. В карточке сверить ID приложения, портал и appUrl. Сокращённая строка с многоточием, client_id, prefix и suffix полным ключом не являются. Если полного секрета нет, восстановление/перевыпуск выполняет владелец в этой карточке; это отдельное действие, не часть проверки. |
| SERVER_ID | VibeCode → серверы → существующий сервер приложения. Уже известен: d4cd0430-b066-441c-bfc7-62107a20b977. |
| APP_URL | HTTPS-адрес в карточке этого сервера. Уже известен: https://app-13fb2e983443.vibecode.bitrix24.tech. Такой же appUrl должен быть у проверяемого OAuth-приложения. |
| B24_DOMAIN | Адрес портала в браузере без https:// и пути: yuktari.bitrix24.by. |
| APP_MODE | Установить bitrix для CRM. demo нужен только для просмотра вымышленных данных. |

OAuth-ключ и ключ доставки выполняют разные задачи. Успешный деплой подтверждает доступ ключа доставки к серверу, но не проверяет вход сотрудника через OAuth-приложение. Локальная правка ключа сама по себе не меняет окружение работающего сервера — параметры должны быть доставлены на сервер.

## Остальные переменные

| Переменная | Где взять / значение |
|---|---|
| NODE_ENV | Задаётся вручную: development локально, production на сервере. Скрипт доставки задаёт production сам. |
| HOST | Локально 127.0.0.1. Скрипт доставки сам задаёт 0.0.0.0 для сервера. |
| PORT | 3000; скрипт использует этот порт на сервере. Менять не нужно. |
| DATA_DIR | Локально можно оставить пустым: будет var/planning. На сервере скрипт сам задаёт /opt/data/yuktari-trip-planning и объявляет его постоянным через dataDirs. Не указывать public/ или /opt/app. |
| PLANNER_MANAGER_IDS | Необязательно. ID сотрудников, которым нужно управление мастерами и графиками, через запятую. ID виден в адресе открытого профиля сотрудника Битрикс24 или через GET /v1/users. Если настройками управляет администратор портала, оставить пустым. |
| B24_ROUTE_IBLOCK_ID | Обычно оставить пустым. Приложение читает settings.IBLOCK_ID у UF_CRM_1619006158 через GET /v1/userfields/contacts. Если настройки поля не возвращают ID, его должен уточнить администратор справочника маршрутов. Это ID инфоблока, не ID поля и не отдельного маршрута. |
| B24_ROUTE_IBLOCK_TYPE | Больше не нужен и не передаётся при доставке: приложение определяет фактический тип через GET /lists/{id}/type. Уже существующую строку в .env можно оставить, она не используется. |
| DEPLOY_CHANGELOG | Необязательно. Коротко написать, что изменилось; это текст для подписчиков в канале приложения. Если пусто, скрипт отправляет описание изменений версии 0.3. Ключи и внутреннюю диагностику сюда не вставлять. |

Не нужны для выбранной VibeCode-схемы: client_secret, отдельный webhook, вручную скопированный vibe_session_ и ключ Wialon. Сессию сотрудника передаёт Gateway при открытии приложения через Битрикс24.

## Проверить и доставить

Из того же терминала, где у пользователя работает доставка:

```powershell
git pull --ff-only
npm run app:check
npm run check
npm test
npm run deploy:check
npm run deploy
```

app:check ничего не меняет: проверяет локальный OAuth-ключ через /me, карточку приложения и адрес сервера. Его безопасный вывод можно передать для диагностики. Эта проверка не читает ключ из работающего сервера и не подтверждает приложение конкретной пользовательской сессии.

Перед отправкой deploy читает полную карточку сервера. Только если showInBitrix24=NOT_CHOSEN и b24CatalogSync.itemId=null, интерактивный терминал задаёт один вопрос: «Показывать ли приложение сотрудникам в Битрикс24 — карточку в каталоге и чат приложения?» Да/нет передаётся в showInBitrix24; пустой или неизвестный ответ не задаёт параметр. Уже сохранённый выбор и существующая карточка сохраняются без вопроса. Неинтерактивный запуск выбор не передаёт.

Каждая доставка указывает displayName=«Планирование выездов», description=«Планирование выездов сотрудников Юктари» и changelog. accessPolicy, права и ссылки не меняются. В конце повторно читается карточка сервера и одной строкой выводится фактическое состояние показа или очереди. Если чтение не удалось, неизвестный результат не выдаётся за успешную публикацию.

Источники: [OAuth-приложение](https://vibecode.bitrix24.tech/docs/apps/get), [сервер](https://vibecode.bitrix24.tech/docs/infra/servers/get), [состояние каталога](https://vibecode.bitrix24.tech/docs/infra/servers/b24-catalog-publish).

## Сервер Юктари управляется ключом приложения

По карточке, подтверждённой пользователем, сервер связан с OAuth-ключом, сохранённым как VIBE_APP_KEY. Сверка внутри процесса показала: VIBE_APP_KEY совпадает с указанными пользователем видимыми частями ключа сервера; VIBE_API_KEY — другой личный ключ. Ранее скрипт всегда использовал VIBE_API_KEY, поэтому проверял сервер другим ключом.

Для этого сервера выбирать источник явно:

```powershell
npm run app:check -- --key-source=app
npm run deploy -- --key-source=app
```

Первую команду выполнить до доставки. Параметр выбирает существующий VIBE_APP_KEY для инфраструктурных запросов. Другие ключи после отказа не перебираются. Переменные, привязка сервера, права, режим и настройки видимости не меняются. Без параметра сохраняется прежний источник VIBE_API_KEY. Для GET карточки сервера и POST deploy ключу приложения достаточно скоупа vibe:infra; пользовательская Bearer-сессия для этих инфраструктурных операций не требуется. Это исключение не распространяется на CRM: там сессия сотрудника обязательна.

app:check по-прежнему использует имеющийся VIBE_API_KEY для чтения карточки OAuth-приложения, а для сервера — явно выбранный источник. Поэтому наличие доступа к обеим карточкам проверяется раздельно. При любом отказе проверки сервера доставка останавливается.

Источник: [авторизация инфраструктурных операций](https://vibecode.bitrix24.tech/docs/infra), [управляющая привязка сервера](https://vibecode.bitrix24.tech/docs/infra/server-access-recovery).
