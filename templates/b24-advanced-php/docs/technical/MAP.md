## Точки входа

> **Что вообще отвечает по прямой ссылке.** Деплой публикует каталог целиком, поэтому под
> веб-корнем лежит и то, что вызывают только по `require`. У каждой такой библиотеки стоит
> одинаковый забор: прямой HTTP получает `404` и `Cache-Control: no-store`. Точный состав —
> в разделе «Инвентарь» внизу (собирается из кода, колонка «Забор прямого HTTP»); числа здесь
> намеренно нет: счётчик в тексте отставал от кода и обещал больше, чем стояло на деле. Отвечают только перечисленные ниже точки входа;
> проверяется это HTTP-инвентаризацией в `tests/security_test.php` — живым сервером, а не
> чтением кода. Прежде такие файлы отдавали пустой `200`, то есть подтверждали свой путь.

- **`www/index.php`** — ЕДИНСТВЕННЫЙ обработчик установки и вход из iframe Битрикс:
  install-триггеры (первая установка — только по криптодоказательству `verifyAndAdopt`)
  → фиксация владельца → **гейт доступа** (ACL) → рендер `template.html` с токеном
  сессии. После окончательного выбора токенов держит shared lifecycle-fence до конца
  запроса: migration не вклинится между опознанием пользователя A и записью сессии B.
  Нет доступа → заглушка.
- **`www/index.php` (продолжение)** — на экране «Нужно проверить результат установки» есть кнопка
  «Повторить завершение установки»: она снимает маркер поколения и выдаёт сплэш заново. Автоповтора
  нет намеренно, выход из состояния делает администратор портала. Форма кнопки возвращает поля
  текущего портального POST — без них её собственный POST не проходит транспортный забор и кнопка
  мертва; если полей в запросе нет, кнопка не рисуется вовсе. Поля берутся теми же помощниками,
  что и сам забор (`portalPostAppSid()`/`portalPostDomain()`): коробочный портал присылает не
  `APP_SID`/`DOMAIN`, а `APPLICATION_TOKEN`/`SERVER_ENDPOINT`. Оттуда же берут домен и адрес REST
  установка (`saveTokensFromInstall()`) — иначе на коробке без `Referer` установка падала, а при
  нескольких именах портала сохранённое имя расходилось с тем, что сверяет забор, и приложение
  навсегда отвечало «открывается только из портала». Сам забор в этом случае пропускает по
  СВЕРЕННОМУ `APPLICATION_TOKEN`: он доказывает больше, чем имя в заголовке.
  Опознание человека прикрыто двумя лимитами: личным (`identify-who:<адрес+токен>`, 30/мин) и
  потолком на адрес (`identify-ip:<ip>`, 120/мин) — иначе один сотрудник закрывал вход всему офису
  за общим внешним адресом. Запись отказов в журнал — лимитом `index-deny-log`.
- **`www/api/event.php`** — приём событий портала (`ONCRMDEALUPDATE` и т.п.):
  сверяет `application_token` и `member_id`, складывает событие в очередь и только
  потом отвечает 200. Обычное событие держит lifecycle-fence от проверки поколения
  до записи в очередь; lifecycle-события меняют поколение через exclusive CAS.
  Тело и одна запись ограничены 64 КиБ, весь inbox — 4 МиБ; переполнение получает
  413/503 без ложного 200. Публичные отказы подлинности журналируются через persistent
  limiter, а недоверенное имя события нормализуется и обрезается.
- **`www/bin/process.php`** — cron-воркер (если фоновая обработка не нужна — не активируется).
  На каждом запуске убирает старые журналы, разбирает очередь событий портала (`drainInbox()` —
  порциями, через аренду из `api/queue.php`), считает порцию долгой задачи и выполняет работу
  проекта — `projectJob()` (она зовёт `projectCronJob()` из файла проекта `api/project-hooks.php`;
  сам `process.php` не правят, `runJob()` — общая механика), после
  чего отмечает в состоянии
  время и исход прогона. Обычное событие держит shared lifecycle-fence через business writes и
  `queueAck()`; успешный `ONAPPUNINSTALL` очищает state/journal и завершает процесс.
  Обработчик события —
  `handleEvent(string $code, array $data, string $eventGeneration): bool` в этом же файле: uninstall
  разбирает ядро, всё остальное уходит в `projectHandleEvent()` файла проекта `api/project-hooks.php`;
  `true` означает, что uninstall завершил уборку и worker обязан остановиться.
  **`www/api/project-hooks.php` в шаблоне НЕТ** — это файл проекта (настройки, работа тика, порция
  задачи, сверка unknown-шага, события); ядро подключает его, если он есть (ревью 23.09.2026). Мутации портала
  оборачиваются в `runOnce()`; после `unknown` обязателен read-back.
  Ручные команды администратора — `replay` (вернуть события из ящика неразобранных) и
  `forget-once <ключ>` (снять залипший ключ операции после проверки исхода в портале). Они идут
  МИМО анти-нахлёста: пока крутится обычный тик, команда обязана ответить человеку, а не молча
  закончиться с кодом 0. Несовпадение поколения установки — тоже внятный отказ, а не тишина.
- **`www/bin/deploy-private-store.php`** — CLI-only deploy-preflight: исполняет env конкретного
  release, доказывает private `DATA_ROOT`/creds, штатную запись/read-back store и настоящий
  `journalAppend()` с его stable-lock.
- **`tools/env-define-names.php`** — не исполняя `env.php`, токенами PHP извлекает только
  настоящие `define('NAME', ...)`; deploy использует один и тот же код локально и на сервере,
  поэтому строка/комментарий-приманка не подменяет обязательную настройку. Второй изолированный
  runtime-режим сверяет, что эти константы реально созданы, а не спрятаны в мёртвой ветке.
- **`tests/env-contract.txt` + `tests/env-contract-history.txt`** — эталон обязательных настроек
  и история его версий. История — цепочка: строка на версию конфига, в ней отпечаток набора имён
  и отпечаток предыдущей строки. Смысл в том, что набор нельзя поменять «заодно с кодом»: сумма
  считается от самого `env.php`, поэтому согласованная правка кода и эталона больше не проходит —
  нужна новая версия `BXAPP_ENV_SCHEMA` и новая строка истории. Обновлять руками не надо:
  **`php tools/env-contract-bump.php`** пересчитает эталон и допишет строку (и откажется, если
  версию конфига забыли поднять). Оба файла — в списке защищённых файлов самопроверки: пропажа
  останавливает выкладку.
- **`www/bin/logs.php`** — журнал с сервера: `tail`, `errors`, `ref <код обращения>`, `grep`,
  `stats`, `prune --apply`. С рабочей машины — `bash scripts/logs.sh <подкоманда>`.
- **`tools/recipes-check.php`** — сверка каталога рецептов (`docs/RECIPES.md` + `docs/recipes.json`)
  с ЖИВЫМИ донорами в чужих проектах: файл на месте, опорные функции всё ещё в нём, отпечаток
  не разошёлся. Каталог отправляет за кодом в чужие проекты, а такая ссылка гниёт молча —
  проект переименовали, функцию убрали, и человек, не найдя готового, пишет своё. Чужие
  проекты только читает. Нет каталога проектов (другая машина) — говорит «не проверено»
  отдельным словом, а не выдаёт это за успех. `--json` — для испытаний.
- **`tools/release-template.php`** — зовёт `deploy-prod.sh` при сборке выпуска: `template.html` становится
  `template.php` с первой строкой «404 + exit», и каркас интерфейса по прямой ссылке постороннему
  не отдаётся; `index.php` читает его `appTemplateHtml()` (`www/api/lib.php`). В исходниках остаётся
  `template.html` — его правят руками и открывают живые прогоны.
- **`tools/gotovnost.sh`** — готов ли шаблон к стабильному срезу: семь условий машинно
  (подробнее — раздел «Где что искать» ниже).
- **`tools/instances.sh`** — разбор `instances.conf`: список независимых установок
  одного и того же кода (`<slug> | <домен портала> | <комментарий>`). Проверяет символы
  slug'а и повторы; негодный список останавливает выкладку до действий на сервере.
  `deploy-prod.sh` без этого файла работает как одна установка по имени папки проекта,
  с ним — обходит все по очереди, каждую полным заходом со своим замком и откатом.
- **`deploy-prod.sh`, блок «приложение живо»** — после read-back проверяет не только, что по
  адресу отвечает новый release: в теле страницы не должно быть следов ошибки PHP, эндпоинт без
  пропуска обязан ответить отказом в общем формате (401/403/409/503 — у неустановленного
  приложения это честный 409), а фоновый рабочий — разбираться серверным PHP. Красный итог
  откатывает release, а не остаётся предупреждением в логе.

## Фронтенд

- **`www/template.html`** — разметка приложения (не `index.html` — обход Apache DirectoryIndex).
- **`www/css/style.css`**, **`www/js/app.js`** — стили и логика фронта. UI — vanilla JS + CSS;
  b24ui в шаблоне НЕ подключён, при необходимости подключается в проекте.
- **`www/js/frame.js`** — наблюдает за изменениями разметки и через `BX24.resizeWindow()`
  подгоняет высоту iframe без внутренней полосы прокрутки.
- **Раздел «Настройки»** (`www/js/app.js`, разметка — `www/template.html`) — форма строится
  ИЗ ОПИСАНИЯ `api/settings-schema.php`, руками под каждый ключ ничего не рисуется. Тип поля →
  свой контрол: число `ui.number`, да/нет `ui.switchBox`, выбор `ui.select`, остальное — поле
  ввода с кнопкой осознанной очистки (пустое поле означает «не менять»). Секрет на страницу
  не приходит, отказ сервера показывается у своего поля. Живой прогон — `node tests/settings-live.js`.

## Бэкенд (`www/api/`)

- **`http.php`** — **единый вход любого эндпоинта**: `apiBoot()` (метод → пропуск → роль →
  частота → заголовки), `apiBody()` и разбор входа (`apiStr/apiInt/apiEnum/apiList`),
  ответы `apiOk()`/`apiFail()`/`apiFailFromThrowable()`. `apiBoot()` держит shared
  lifecycle-lock до shutdown, поэтому прикладные state-записи не переживают migration.
  Новый эндпоинт начинается с него.
- **`settings.php`** — настройки приложения и **образец эндпоинта**: новый делать его копией.
- **`settings-schema.php`** — ОПИСАНИЕ настроек: имя, заголовок, тип, границы, подсказка.
  По нему проверяется приходящее значение и строится форма — руками валидацию под
  каждый ключ больше не пишем. Секрет наружу не отдаётся никогда: клиент видит только
  признак «задан».
- **`task.php`** — долгая задача с экрана: `GET` — состояние, `POST {"do":"start|cancel|forget"}`; `{"do":"resolve","id":…}` — администратор снимает порцию с неизвестным исходом после ручной проверки (`taskResolveManually()`).
  Запуск и отмена — от роли edit. «Уже выполняется» приходит отдельным кодом, чтобы экран
  показал саму задачу, а не отказ. В каждом ответе — признак `cron`: молчащий планировщик
  означает, что задача поставлена, но считать её некому, и экран говорит это сразу, а не
  через пять минут «нет признаков жизни».
- **`task-state.php`** — состояние долгой задачи (файл `data/task.php`): запуск под замком
  (два одновременных нажатия дают ОДНУ задачу), отметка порции, отмена флагом, исход.
  Прогресс только вперёд; задача без признаков жизни дольше пяти минут показывается
  отдельным состоянием и разрешает перезапуск — иначе падение рабочего блокировало бы
  кнопку навсегда. Считает `bin/process.php` (`runPendingTask()` → порция `taskStep()`),
  бюджет порций (`TASK_TICK_BUDGET_SECONDS`) заведомо меньше ожидания установки: весь он
  проходит внутри общего замка, и больший бюджет делал бы переустановку невозможной.
  Файл задачи принадлежит УСТАНОВКЕ: удаление приложения и перенос на другой портал его
  очищают (`api/lib.php`), перевыпуск регистрации на том же портале — намеренно нет.
  Cursor ограничен 64 КиБ JSON, `result`/`error` — 16 КиБ каждый, весь private snapshot —
  256 КиБ; oversized legacy отклоняется до JSON decode, а не переписывается пустым.
  Порция начинается с КВИТАНЦИИ (`taskClaimStep()` пишет `step` той же записью, что и
  разрешение) и закрывается отметкой прогресса с той же меткой попытки. Незакрытая квитанция
  = процесс умер жёстко между работой в портале и отметкой: `runPendingTask()` такую порцию
  НЕ повторяет, а останавливает задачу с человеческой причиной — повтор мог бы сделать ту же
  работу второй раз. Порции передаётся паспорт шага (`taskStepKey()`: стабильные задача+позиция),
  чтобы проект мог обернуть внешний эффект в `runOnce($step['key'], …)`.
- **`b24.php`** — клиент REST Битрикс. `->batch()` сам обновляет токен и повторяет пакет, если ВЕСЬ пакет лёг на протухшем токене (успехов ноль, все ошибки про токен); смешанный ответ не повторяется — иначе выполненное задвоится. Дальше: `->call()`, **`->callChecked()`** (отказ портала →
  исключение, а не пустой результат), **`->readBackChecked()`** (точечный `get` той же
  сущности + сверка реально сохранённого subset полей), **`->deleteVerified()`** и
  **`->actionVerified()`** (закрытые официальные контракты для delete/action без универсального
  `get`), **`->batch()`/`->batchAll()`/`->batchAllChecked()`** (пакеты любого размера
  по 50; checked-вариант не пропускает partial-ошибки мутаций), **`->fetchAll()`** (весь список курсором по ID;
  входные `limit`/`LIMIT` намеренно удаляются, потому что контракт — весь список) и
  **`->fetchAllBatched()`** (все start-страницы со сверкой `total`, размера и уникальности ID),
  токены, refresh, `saveTokensFromInstall`, verify application_token. Повторы решает
  `isRetryable()`: исчерпанная корзина и обычная 5xx повторяются, а блокировка по накопленному
  времени метода и ручная блокировка REST — НЕТ (первая снимается корзинами по 10 минут, вторая
  только через поддержку Битрикса; повтор там лишь дольше держит воркер). Отказ сервера
  авторизации переводится в совет человеку через `oauthRefusalText()`: протухший ключ зовёт
  переустановить приложение, чужие креды — проверить карточку local-app. Здесь же — ЕДИНСТВЕННОЕ
  место разбора входящего POST портала (`portalPostDomain()`, `portalPostRestEndpoint()`):
  облако присылает `DOMAIN`/`APP_SID`/`PROTOCOL`, коробка — `SERVER_ENDPOINT`/`APPLICATION_TOKEN`,
  и пока поля читали в трёх файлах по-своему, коробка ставилась с одним именем портала, а
  проверялась по другому. Чужой `SERVER_ENDPOINT` адресом REST не становится: только при
  точном совпадении хоста с доменом установки.
  Замена поколения — один exclusive CAS: другой портал сначала очищает весь portal-bound
  state; новый `client_id`/reinstall того же портала очищает sessions, placement fingerprint,
  rate и очереди, сохраняя settings/ACL/kill-switch и `runOnce` от повторного эффекта.
  Lifecycle-замена `TASK_FILE` и `CRM_DICT_FILE` проходит через owner-хелперы задачи и
  CRM с их pre-decode ceilings. Oversized legacy поэтому останавливает переход fail-closed
  и оставляет прежний файл неизменным, а не подменяется пустым состоянием.
- **`store.php`** — приватный файловый стор (`.php` c `404 + exit` + атомарная запись;
  legacy `<?php exit;` читается всегда и временно остаётся writer-форматом только в первом
  release, чей rollback-target ещё не доказал dual-read).
  **Менять состояние только через `storeUpdate($файл, function(array $было): array)`** —
  чтение и запись под одним замком, иначе параллельный запрос затрёт правку.
  `storeWrite()` — только для полной замены. Битый файл не считается пустым: копия
  откладывается как `<имя>.bad-<отпечаток>.php`, запрос падает (`StoreCorruptedException`).
  Temp, lock и quarantine обязаны получить точные права 0600 до данных; payload проходит
  полную запись и flush/fsync до атомарной публикации, иначе операция падает fail-closed.
  Там же **`withKeyLock('ключ', fn)`** — замок на саму РАБОТУ, а не на файл: импорт, выгрузка
  и рассылка не должны идти в два прохода одновременно. Занято — `KeyLockBusyException`
  (работа не начиналась), замок снимается в `finally`, вложенный тот же ключ — ошибка вызова.
- **`cache.php`** — память о тяжёлом ответе портала: `cacheRemember($ключ, $секунды, $загрузчик,
  $force)`, `cacheForget()`, `cacheFiles()` (уборка при удалении приложения). Значение лежит в
  `data/cache-<ключ>-<отпечаток>.php` по обычным правилам стора; пока один запрос идёт за
  ответом, остальные ждут его на `withKeyLock` вместо второго похода в портал. Замок держат
  дольше отведённого → отдаётся прошлое значение, если оно есть. Отказ загрузчика наружу и
  ничего не запоминает. Ключ ограничен 512 байтами, JSON value — 8 МиБ, весь private cache-file —
  8 МиБ + 64 КиБ; превышение не публикуется. Всё семейство ограничено 128 файлами и
  64 МиБ: create/replace/delete сверяют квоту под одним family-lock. Рабочие key-lock
  распределены по фиксированным 32 shard-файлам, поэтому новые ключи не создают
  неограниченное семейство lock-файлов. В шаблоне так помнится справочник отделов (`api/users.php`).
- **`session.php`** — сессии + **ГЕЙТ ДОСТУПА**: `tryCreateSessionFromB24Post()` (опознание
  по `user.current`, решение по ACL), `requireSession()` (её зовёт `apiBoot()`),
  `revokeSessionToken()`/`revokeSessionsForUser()`. Роль перечитывается из списка доступа
  на КАЖДОМ запросе (отзыв прав действует сразу), пропуск привязан к порталу по `member_id`
  (после переустановки старые пропуска мертвы). Опознание по порталу, ACL и физическая
  запись сессии выполняются под одним shared lifecycle-fence.
  Там же **`sessionApplyPortalDepartments($uid → отделы)`** — перевод сотрудника ИЗ разрешённого
  отдела снимает пропуск за минуты, а не за восемь часов: отделы приходят в `UF_DEPARTMENT` того
  же ответа `user.get`, роль пересчитывается, а про кого портал промолчал — того не трогаем.
  Там же **`revokeSessionsOfBlockedUsers()`** — сверка с порталом: заблокированный в Битриксе
  сотрудник теряет пропуск, не дожидаясь восьмичасового срока. Зовёт её фон (`bin/process.php`,
  не чаще раза в 10 минут): уволенный сам в приложение не зайдёт, поэтому проверка «при
  следующем открытии» не сработала бы именно тогда, когда нужна. Молчание портала про
  сотрудника пропуск НЕ снимает — иначе один сбой выборки разлогинил бы всех сразу.
- **`access.php`** — ACL-хелперы: `aclUserRole()`, `aclHasAccess()`, `aclSetOwner()`, `aclLoad()`,
  `aclUpdate()` (единственный способ менять список доступа — под замком), `roleAtLeast()`
  (одно сравнение ролей на всё приложение), **`auditLog()`** (кто что сделал — в Битриксе
  все наши вызовы выглядят как действия установщика), **`runOnce()`** (завершённый повтор
  возвращает сохранённый результат; после сбоя исход `unknown` до read-back).
  Журнал операций ограничен по размеру: `RUN_ONCE_MAX_BYTES` (веб-путь на разросшемся файле
  честно отказывает вместо фатала по памяти), крупный результат хранится урезанным
  (`runOnceStorableResult()` оставляет идентификаторы и метку `truncated`), а истёкшие ключи
  убирает `runOncePrune()` из фоновой задачи — не на каждой боевой мутации. У уборки потолок
  выше, чем у веб-пути: иначе переросший файл нечем было бы разобрать. Уборки по сроку мало —
  журнал переполняют и свежие записи, поэтому переполненный файл дожимается по возрасту:
  завершённые ключи снимаются досрочно (в журнал приложения уходит сколько), а `running`/`unknown`
  не трогаются никогда — их снимает только человек командой `forget-once`.
- **`acl.php`** — управление списком доступа (**admin-only**): GET список / POST
  add|update|delete; `claim_owner` разрешён только самому недавно подтверждённому portal-admin,
  атомарно меняет owner и отзывает доступ/сессии прежнего владельца.
- **`users.php`** — поиск сотрудников И ОТДЕЛОВ для выдачи доступа (**admin-only**, GET):
  валидирует `q`, читает `user.get` и `department.get` через `fetchAllBatched()` до доказанного
  конца в пределе 500 совпадений и отдаёт фронту не больше восьми `id/name`. Хвост или
  превышение предела — ошибка, а не молчаливо неполный список.
- **`health.php`** — состояние приложения одним ответом (**admin-only**): портал и владелец,
  выданные права против объявленных в `APP_SCOPES`, получен ли токен событий, объявленные
  плейсменты против реально привязанных, время и исход последнего фонового прогона, последние
  ошибки. Каждая проблема названа вместе с действием — экран без «что делать» отправляет человека
  к разработчику ровно так же, как его отсутствие.
- **`logs.php`** — журнал для человека (**admin-only**, GET): день, уровень, вид записи, поиск,
  код обращения. Второе окно в тот же журнал — команда `bin/logs.php`.
- **`journal.php`** — ЖУРНАЛ ПРИЛОЖЕНИЯ, один на всё: сбои, действия людей, работа крона.
  `appLog($уровень, $событие, $подробности)` — единственная запись; `logRef()` — код обращения,
  один на запрос (его человек и называет); `logContextSet()` — объявить, с чем работает запрос,
  чтобы каждая строка несла эти идентификаторы; `journalQuery()` — чтение с конца с фильтрами;
  `journalPrune()` — уборка по возрасту. Файлы: `data/logs/<дата>.log.php`, по одной json-строке
  на запись, 404+exit-заглушка первой строкой, права 0600. Секреты маскируются на входе, персональные
  поля (телефон, почта) уходят коротким хешем. Запись и дневной файл имеют жёсткий byte-cap:
  слишком большая запись остаётся коротким JSON-маркером `truncated`, а чтение никогда не собирает
  гигантскую legacy-строку целиком. `appLog()` возвращает код обращения только после полной
  записи и flush/fsync; missing/unreadable generation и физический отказ уходят в системный
  error_log без ложного кода journal. Недоступный каталог журнала — обычный неуспех записи, а не
  исключение: бросок отсюда улетал в обработчик необработанных ошибок, который сам зовёт запись в
  журнал, и человек получал пустой 500. Адрес в записи берётся тем же `apiClientIp()`, что и в
  счётчиках частоты, — иначе за прокси у всех записей аудита один адрес балансировщика.
  Два окна в этот журнал: экран `api/logs.php` и команда
  `bin/logs.php` (с сервера — `scripts/logs.sh`).
- **`fetch-all-compat.php`** — ПОЛНАЯ ВЫБОРКА ДЛЯ ЧУЖОГО ДВИЖКА: `fetchAllCompat($call, метод, ...)`
  забирает весь список портала, используя любую функцию вызова — кладётся в проект со старым
  клиентом поверх его кода, ничего не заменяя. Курсор по идентификатору (счётчик страниц врёт
  при удалении записей во время чтения). Неполной выборки не отдаёт: предел страниц, застрявший
  курсор и отказ портала — исключение, а не обрезанный список. В самом шаблоне пользуйся
  `$b24->fetchAll()` — там богаче. *Замер 05.08.2026: 256 мест в 44 проектах читают списки
  без перелистывания вовсе.*
- **`plan.php`** — ТАРИФ ПОРТАЛА И ТЕМП ЗАПРОСОВ. Тип портала (облако/коробка) имеет ИСТОЧНИК
  (`planKindSource()`): `configured` — оператор сказал прямо через `BXAPP_PORTAL_KIND=box|cloud`,
  `license` — узнали по ответу портала, `unknown` — не знаем. Неопознанный портал больше не
  считается облаком молча: измеренная ёмкость `BXAPP_RATE_PER_SEC` применяется и при неизвестном
  типе, а на облаке приложение прямо пишет, что эта настройка не действует. Портал ограничивает не объём данных, а
  ЧАСТОТУ обращений, и пороги зависят от тарифа: Энтерпрайз — 5 запросов в секунду и корзина
  250, прочие — 2 и 50 (официальные цифры из `limits.md`). `planRefresh($b24)` спрашивает
  `app.info` (раз в сутки; при установке тариф берётся из уже полученного ответа, без лишнего
  запроса), `planRatePerSecond()` отдаёт предел, `planHuman()` — готовую строку о темпе для служебного блока и журнала.
  Клиент портала держит этот темп сам (`throttleByPlan()` в `b24.php`), поэтому прикладному коду
  делать ничего не нужно. **Тариф неизвестен — берётся самый строгий предел:** ошибиться в эту
  сторону значит работать медленнее, в другую — получить блокировку метода у клиента. Коробке
  облачный предел не навязывается: там интенсивность настраивают на сервере. Темп не заменяет
  пакеты: пакет из 50 команд — один HTTP-запрос для облачной корзины, но пакеты не отменяют ресурсную стоимость команд,
  REST resource guard и ёмкость сервера. Коробке облачная leaky-bucket корзина интенсивности не назначается. Это не отменяет два отдельных ограничения:
  серверную ёмкость и resource guard REST-модуля, который по умолчанию выключен, но может быть включён и настроен администратором. Без замера берётся
  самый осторожный бюджет, а измеренную серверную ёмкость задают через `BXAPP_RATE_PER_SEC`; `portal-plan` не опрашивает resource guard. У числа есть
  источник (`planRateSource()`): предел портала · измерено человеком · ёмкость неизвестна. Темп
  общий для ВСЕХ процессов приложения (`planWaitTurn()`, отметка в `data/rate.php`): веб-запрос,
  фоновый обработчик и воркер по расписанию иначе превышали бы предел кратно числу процессов.
  Устроен как РЕЗЕРВИРОВАНИЕ будущего слота: под замком процесс занимает себе момент времени и
  сразу отпускает замок, а ждёт уже снаружи. Сон ПОД замком (как было до 09.08.2026) делал
  очередь длиннее предохранителя, и при шести процессах все уходили «каждый сам за себя» — залп
  вместо темпа. Потолок ожидания разный: `PLAN_WAIT_CAP` в вебе (человек за экраном),
  `PLAN_WAIT_CAP_CLI` в фоне. Не дождался своей очереди — это пишется в журнал
  (`plan.rate.degraded`, `planNoteDegraded()`), а не остаётся тихим переходом на свой счётчик.
- **`capability.php`** — ДОСТУПНЫ ЛИ ПРИЛОЖЕНИЮ МЕТОДЫ ПОРТАЛА. Выданное право и работающий
  метод — разные вещи: на коробке модуль может быть выключен, а версия старее (замер на живой
  коробке: при 71 выданном праве `crm.item.list` вызвать нельзя). `capRefresh($b24, $методы)`
  спрашивает портал ОДНИМ пакетом (`method.get`, по 50 команд, список длиннее — несколько
  пакетов) и помнит ответ сутки; `capAllowed('crm.item.list')` — можно ли звать; `capMissing()`
  и `capMissingRequired()` — чего не хватает; `capHuman()` — готовая строка о правах для служебного блока и журнала.
  Нужные методы объявляет проект в `env.php` (`APP_METHODS_REQUIRED` / `APP_METHODS_OPTIONAL`);
  отсутствие ОБЯЗАТЕЛЬНОГО метода не даёт начаться работе проекта (проверка в `bin/process.php`
  перед `projectJob()` — механика тика при этом идёт дальше). Свежесть карты не равна её полноте:
  метод, которого в карте нет, спрашивается отдельно, а ошибки подкоманд разбираются
  (`METHOD_NOT_FOUND` → «нет на портале», прочее — «не ответил», прежнее знание не стирается).
  `capAllowed($метод, true)` — строгий режим: непроверенное считается запретом.
  **Непроверенное считается разрешённым:** пока портал не ответил, приложение работает как
  раньше — предохранитель, который останавливает всех подряд, хуже отсутствующего.
- **`crm-dict.php`** — СПРАВОЧНИКИ CRM человеческим языком: `crmDict($b24)` отдаёт воронки,
  стадии и названия полей одним вызовом и помнит их сутки (неполный ответ — пять минут, чтобы
  получасовой сбой портала не застыл на день). `crmDictStageName()`, `crmDictCategoryName()`,
  `crmDictFieldName()` переводят коды в названия: без них клиент видит «C5:NEW» вместо
  «Договор подписан». `crmDictStageCode()` собирает код стадии по правилу префикса воронки
  (у первой воронки префикса нет) — на этом чаще всего ошибались, и часть сделок не попадала
  ни в одну стадию. Один code — до 1 КиБ, label — до 16 КиБ, полей одного типа — до 5000,
  всех entries — до 20000, private snapshot — до 8 МиБ. Bounded RMW проверяет merged candidate
  под тем же замком и не меняет прежний файл при отказе; кнопка «Обновить» — `crmDict($b24, true)`.
- **`uf.php`** — СВОИ ПОЛЯ В КАРТОЧКЕ ПОРТАЛА: `ufEnsure($b24, 'deal', [...])` читает, каких
  полей не хватает, создаёт недостающие одним пакетом и подтверждает результат перечитыванием.
  Повторный вызов не создаёт дублей — иначе при каждой установке в карточке появляется
  «Номер заявки (1)», «(2)», а данные остаются в первом поле. Имя поля собирается с меткой
  приложения (`UF_PREFIX` в `env.php`), проверка и создание идут под общим замком
  (`withKeyLock`), след действия пишется через `auditLog`. Сущности: lead, deal, contact,
  company, quote; смарт-процессы не поддержаны намеренно. Испытания — `tests/uf_test.php`.
- **`notify.php`** — УВЕДОМЛЕНИЯ ЛЮДЯМ ЧЕРЕЗ ОЧЕРЕДЬ: `notifyQueue()` кладёт сообщение в
  `NOTIFY_OUTBOX_FILE` и сразу возвращает управление (запрос человека не ждёт портал),
  `notifyDrain($b24)` отправляет накопленное пачками из крона. Дублей нет за счёт метки
  сообщения: портал по ней заменяет прежнее уведомление. Временный отказ повторяется с
  растущей паузой, безнадёжный уходит в список недоставленных с причиной (`notifyFailed()`).
  Очередь очищается и при удалении приложения, и при переносе на другой портал — получатели
  там другие люди. Отправка идёт через `batchAllIdempotent()` с явным объяснением, почему
  повтор безопасен. Требует scope `im`. Испытания — `tests/notify_test.php`.
- **`events-bind.php`** — ПОДПИСКА НА СОБЫТИЯ ПОРТАЛА. Список нужных событий объявляется
  в `env.php` (`APP_EVENTS`), подписка ставится сама при установке — там же, где вкладки:
  портал снимает обработчики при обновлении приложения, поэтому ставить их надо заново
  каждый раз. `bindEvents()` подписывает и ПЕРЕЧИТЫВАЕТ результат (портал отвечает успехом
  и при не вставшей подписке), `eventsActual()` показывает, на что портал реально шлёт,
  `eventsHealth()` даёт строку «объявлено — подключено» для ответа `api/health.php`.
  Отказ подписки установку не останавливает: приложение без событий работает, а
  неустановившееся — нет; расхождение видно на экране, а не всплывает у клиента.
  Судьбу подписки решает перечитывание списка (`eventsReconcile()`), а не код ошибки: 
  код повторной привязки в документации не описан, и приговор по нему объявлял бы поломкой 
  рабочую установку при каждой переустановке.
- **`queue.php`** — очередь событий портала: `queueTake()` берёт порцию В АРЕНДУ (событие
  остаётся в очереди с меткой времени), `queueAck()` подтверждает разобранное и возвращает
  то, что нужно повторить, `queueSize()` — длина. Аренда протухает сама (`QUEUE_LEASE_SEC`),
  поэтому убитый посреди работы воркер не уносит порцию с собой. Неудача откладывает событие
  с нарастающей паузой (`queueDefer()`, 60 → 120 → 240 секунд), а после `QUEUE_MAX_TRIES`
  попыток оно уходит в ЯЩИК НЕРАЗОБРАННЫХ (`queueDeadLetter()`, `data/dead-letters.php`) —
  целиком, вместе с текстом ошибки. Оттуда его возвращают в работу командой
  `php www/bin/process.php replay` (`queueReplayDead()`), а число таких событий показывает
  карточка «Настройки → Служебное». РЕЕСТР ЗАКРЫТЫХ (`queueMarkDone()` / `queueIsDone()`,
  `data/queue-done.php`,
  память семь суток) не даёт выполнить событие дважды: «нет в очереди» не значит «не было» —
  разбор ящика возвращал событие, которое воркер только что доделал, а вернувшееся после
  падения событие исполнялось заново. Метка `eid` случайна и выдаётся при первом взятии в
  работу, поэтому отсекается ровно повтор, а не похожее новое событие. Пользуется этим `bin/process.php`; приёмник `api/event.php` только кладёт
  события в файл. Потолок попыток проверяется в самом `queueTake()`, а не только в обработчике
  ошибок: событие, на котором процесс УМИРАЕТ (нехватка памяти, фатал, снятие по таймауту), до
  обработчика не доходит, и без этой проверки оно забирало порцию за порцией бесконечно.
  Состояние очереди проверяется один раз на вход в мутатор — разбор ящика был квадратичным и
  занимал 33 секунды из 48 всего проверочного контура. Не-массив внутри inbox считается повреждением: `queueTake()` падает
  fail-closed и не переписывает очередь, вместо тихого удаления записи. Перед декодированием
  проверяется размер файла; лимиты одной записи (64 КиБ), всего inbox (4 МиБ) и числа записей
  одинаково действуют на приём, аренду, ack и replay. У ящика неразобранных потолок ПРИЁМА
  (`DEADLETTER_MAX_BYTES`) и потолок РАЗБОРА (`DEADLETTER_RECOVERY_MAX_BYTES`, восьмикратный)
  — разные: переполненный ящик обязан отказывать в приёме, но оставаться разбираемым, иначе
  события не достать ничем, кроме правки файла на сервере.
- **`export-csv.php`** — выгрузка таблицы в CSV, который откроется в Excel без плясок:
  BOM для кириллицы, разделитель «;» для русской локали, экранирование формул (значение с `=`
  Excel выполняет — так из выгрузки делают атаку на того, кто её открыл). `csvDownload()` принимает
  iterable, ограниченно спуливает его во временный файл и отдаёт чанками с точным `Content-Length`;
  строки/байты/ячейки имеют cap. `csvBuild()` оставлен для небольшого текста и при превышении своего
  малого cap бросает контролируемое исключение вместо роста памяти.
- **`fmt.php`** — даты портала и деньги: `b24Day()` (день срезом строки, без часовых поясов),
  `b24Range()` (период полуоткрытым: `>=от` и `<до+1 день`), `b24Today()`/`b24PortalTz()` (сегодня
  по времени ПОРТАЛА; без подтверждённой таймзоны явно падают, а не подменяют её таймзоной
  сервера), `money()`/`moneyStr()`/`moneyForB24()` (целые копейки, округление один раз).
- **`placements.php`** — где приложение видно в портале. Список объявлен в `APP_PLACEMENTS`
  (`www/env.php`), адрес обработчика подставляется сам из `APP_URL`. `bindPlacements()` зовётся
  при установке и при смене адреса, идемпотентна (unbind перед bind) и в портал не ходит, пока
  список и адрес не менялись; `placementsActual()` показывает, что портал считает привязанным —
  расхождение и есть ответ на «почему вкладки нет, хотя приложение работает».
- **`bind.php`** — эндпоинт «пересобрать плейсменты» (**admin-only**, POST). Раньше был служебной
  страницей под cookie — её нельзя было открыть в браузере (cookie партиционирована порталом).
- **`ops.php`** — эндпоинт «снять залипшую операцию» (**admin-only**, POST `{key}`). Операция с
  внешним эффектом идёт через `runOnce()`; если процесс оборвался между работой и записью
  «сделано», ключ остаётся в статусе `unknown` — портал мог сделать, мог нет, и повторять вслепую
  нельзя. Снять ключ вправе только человек, проверивший портал глазами. Раньше это умела лишь
  командная строка сервера (`php www/bin/process.php forget-once`), а служебный блок настроек советует
  «повторите действие» — администратору портала совет был неисполним, и такие операции копились
  вечно вместе с файлом журнала операций. Снимает эндпоинт ТУ ЖЕ запись, которую прочитал и
  показал человеку: `runOnceForget($key, $rec)` сверяет отпечаток под арендой и отказывает с
  `version_conflict`, если состояние успело смениться (иначе поздний клик стирал уже записанное
  «сделано» и открывал дорогу второму внешнему эффекту). Принудительное снятие без сверки
  осталось за командной строкой — это последний рубеж, когда журнал упёрся в потолок.
- **`lib.php`** — общие хелперы: **`maskSecrets()`** (прогонять через неё ВСЁ, что уходит в лог
  или на экран: текст ошибки Б24 несёт URL с токеном), **`sendNoStoreHeaders()`** (страницы
  приложения не кэшируются — иначе правку человек увидит только после жёсткой перезагрузки),
  settings, **`renderServicePage()`** — единый вид всех служебных экранов (отказ, заглушка,
  «портал не отвечает»): заголовок, причина и обязательное «что сделать».
  Там же **`httpJson()`** — обращение к ЧУЖОМУ (не Б24) REST-API: только http(s), редиректы не
  идём, не-JSON в ответе считается ошибкой, а не пустым результатом. Оба таймаута на каждом
  вызове (соединение 10 с, ответ 30 с) и ограниченный повтор: `429`/`5xx` — сначала по
  `Retry-After` (число секунд ИЛИ дата, `httpRetryAfterSeconds()`), иначе 1 → 2 → 4 с
  разбросом; изменяющий метод после сбоя НЕ повторяется без явного
  `['safeToRepeat' => true]` (ответ мог потеряться уже после выполнения). Весь вызов с
  паузами укладывается в бюджет (`budget`, по умолчанию 45 с в вебе, 120 в cron).
  БЕЗОПАСЕН ПО УМОЛЧАНИЮ (09.08.2026): только `https`, без `user:pass@` в адресе, стандартный
  порт, имя разрешается заранее и запрос идёт на ПРОВЕРЕННЫЙ адрес (`httpResolveAndPin()` +
  `CURLOPT_RESOLVE`, поэтому повторное разрешение имени никуда не уведёт), перенаправления
  выключены, у ответа есть потолок с обрывом чтения (`maxBytes`, 5 МиБ). Внутренние адреса,
  открытый http и нестандартный порт разрешаются ТОЧЕЧНО — `allowPrivate`, `allowInsecure`,
  `allowPorts`, — и каждое разрешение видно в коде вызывающего, а не спрятано в блоке.
  Для Битрикса он не нужен и не годится — там `b24()` с повторами, обновлением токена и
  пакетами по 50.
  Ещё там: **`appInstalled()`** (установлено ли приложение — по содержимому токенов, а не по
  наличию файла: после удаления файл остаётся) и **`appPurgeInstallState()`** (стереть ВСЁ
  состояние установки при `ONAPPUNINSTALL`; файлы проекта добавляются через `APP_PURGE_EXTRA`
  в `env.php`). `appPurgeExtraFiles()` до первой мутации разрешает там только собственные
  `.php` внутри `DATA_ROOT` и запрещает core/locks/logs/symlink: ошибочная конфигурация не может
  очистить tokens или inbox в обход двухфазного порядка. Lifecycle RW-барьер и
  `install_generation` не дают поздним запросам/worker
  установки A писать в B; migration-throttle меняется только при совпавших generation+phase.
  Там же ответ при аварийном завершении: **`installFailureHandler()`** (первой строкой каждой
  точки входа) и пара **`appChangesStarted()` / `appChangesMayBeApplied()`** — отметка в памяти
  процесса «изменения уже пошли». Её ставит сам `b24()` на изменяющий вызов и на пакет, где
  есть хоть одна мутация, а также перезапись нескольких state-файлов; вручную — там, где
  проект меняет данные мимо клиента портала. От отметки зависит текст экрана и признак
  `changes` (`not_started` / `maybe_applied`) в JSON: без неё ответ обещал «данные не
  пострадали» даже после отправленного `crm.deal.add`, и человек повторял действие.

## Конфиг

- **`www/env.php`** — единственное место настроек: креды B24, `APP_PLACEMENTS` (где приложение
  видно в портале), пути и константы файлов состояния. Здесь же `BXAPP_DATA_ROOT` (явно задать
  стор; тесты уводят им данные во временный каталог), generated `BXAPP_RELEASE_DATA_ROOT`
  (штатный private shared вне webroot) и `UNVERIFIED_FIRST_INSTALL` (разовый БИЛЕТ на обход: домен + секрет 32+ + срок, сгорает после применения; прежний выключатель убран 09.08.2026 —
  подтверждения установки для коробочного портала со своим сервером авторизации).
  **Креды ищутся по цепочке:** значения окружения → private `DATA_ROOT/creds.php` → значения
  в самом env. Без generated release путь файла можно переопределить `BXAPP_CREDS_FILE`; в
  release путь авторитетно закреплён за private shared и проверяется деплоем.
  `APP_PURGE_EXTRA` принимает только собственные `.php`-файлы строго внутри `DATA_ROOT`;
  core-state, очереди, locks, credentials, журналы и пути через symlink/`..` отклоняются до
  любой reset/uninstall-записи.
  **Что деплой делает с `env.php`:** у каждого release своя копия. Обычная выкладка наследует
  её из активного release; при первой выкладке или по явному `--push-env` берётся локальная.
  До переключения деплой сверяет не только имена настроек, но и точный положительный целый
  `BXAPP_ENV_SCHEMA`: он версионирует исполняемую логику env. Отсутствие, нечисловое значение или
  несовпадение останавливает обычную выкладку, не меняя `live`.
  Смена только значения schema не повышает, но и сама не доезжает с обычным deploy: её применяют
  явным `--push-env` после слияния клиентских значений.
- **`www/release.php`** — метка выкладки: `deploy-prod.sh` генерирует её во временной сборке и
  кладёт только в новый release, не меняя исходный `www/`. Приложение отдаёт метку заголовком
  `X-App-Release`, и по нему выкладка проверяет, что на бою именно та версия, которую отправили.
- **`scripts/set-creds.sh`** — записать креды local-app прямо на сервер (`--show` — посмотреть,
  что лежит; `--local` — для своего тестового хостинга).
- **`scripts/bxapp-remote.sh`** — общий ответ на вопрос «на какой сервер идти»: и запись кред, и
  чтение журнала берут хост и раскладку каталогов оттуда же, откуда выкладка. Свой путь в каждой
  команде однажды увёл секрет клиента на посторонний хост с бодрым «Готово».
- **`scripts/snap.sh`** — точки возврата: `save ["чем занимались"] [--stable]`, `list`,
  `diff <точка>`, `restore <точка>`, `prune`. Снимки — в `[внешний каталог снимков]` (вне проекта,
  жёсткие ссылки на неизменившиеся файлы). Каталог данных приложения не снимается и не
  возвращается ни при каком исходе; боевой сайт эта команда не трогает. Отдельный слой данных —
  `data-save`, `data-list`, `data-restore <снимок> --я-понимаю-что-теряю` (без слова подтверждения
  возврат не выполняется, про токены портала предупреждает отдельно). После подтверждённой
  выкладки `deploy-prod.sh` сам ставит точку с меткой «стабильно». Испытания — `tests/snap_test.php`.
  ЦЕЛОСТНОСТЬ ТОЧКИ ДОКАЗЫВАЕТСЯ СОДЕРЖИМЫМ (09.08.2026): у каждой точки и каждого снимка
  данных есть `.snap-manifest` — отпечатки sha256 всех файлов; полная сверка идёт перед
  возвратом (до первой правки проекта) и по команде `verify [точка]`. Число файлов подмену не
  ловило: ни правку байта, ни замену, ни переименование. Точки старого формата не отвергаются,
  но честно названы непроверяемыми.

## Выкладка на сервере

- **Публичный путь** `~/<DOMAIN>/www/<slug>` — ссылка `live` на один из каталогов
  `~/<DOMAIN>/.bxapp/<slug>/releases/`, а не изменяемая rsync-папка.
- **Публикация:** `deploy-prod.sh` берёт серверный lock, собирает новый release целиком и
  атомарно переключает `live` только после успешной сборки. Красный read-back возвращает прежнюю
  ссылку; после очистки остаются активный, предыдущий и ещё три свежих release-каталога —
  ограниченная история для разбора и отката. Чужой или stale lock автоматически не удаляется.
  После смены symlink одноразовый token-probe сбрасывает OPcache/realpath-cache PHP-FPM, а release
  принимается только после непрерывного окна внешних ответов с точной новой меткой: не менее
  24 запросов и полного `realpath_cache_ttl` плюс запас. Probe без случайного deploy-token отвечает
  пустым 404 и после проверки удаляется. Это не даёт редкому старому worker скрыться за короткой
  случайно удачной серией. Rollback проходит то же TTL-окно уже с точной меткой предыдущего
  release; каталог, который хотя бы пытались публиковать, сразу не удаляется и безопасно попадёт
  под retention следующей успешной выкладки.
  Перед сборкой previous-reader исполняемо проверяется на новый prefix; до успеха generated
  `release.php` включает переходный legacy-writer, а следующая выкладка переключается на 404.
- **Legacy-каталог** в публичном пути автоматически не переносится: миграция требует остановить
  записи и явно передать оба флага `--migrate-legacy --confirm-quiesced`.

## Хранилище (логический `DATA_ROOT`, физически private `shared/data`)

На сервере данные лежат вне webroot в `~/<DOMAIN>/.bxapp/<slug>/shared/data`. Путь передаёт
сгенерированный `release.php`; symlink `release/data` не создаётся. Поэтому переключение кода не
копирует и не откатывает state, а публичный `/data/...` отвечает 404. Исполняемый префикс каждого
`.php` остаётся обязательной защитой-в-глубину и для переносов/локального режима.

- Несущие файлы состояния: `b24-tokens.php` — OAuth-токены портала + `install_generation` ·
  `settings.php` — настройки из UI · `sessions.php` — сессии · `state.php` — состояние/кеш и
  доверенный `app_url`, зафиксированный при установке · **`acl.php` — список доступа**
  (`{owner_uid, users:[{uid,name,photo,role}]}`) ·
  `switches.php` — примерка/боевой режим · `operations.php` — журнал операций (защита от повтора) ·
  `ratelimit.php` — счётчики частоты · `inbox.php` — очередь принятых событий портала ·
  `preview-key.php` — ключ доверенного предпросмотра с дев-портала: его кладёт панель при подъёме
  публикации, приложение только читает. Удаление приложения уносит его вместе со стором, при
  переносе на другой хостинг он не едет — и это правильно: там предпросмотра нет и быть не должно.
  Пропал — панель заведёт заново на следующем открытии, ничего восстанавливать руками не нужно ·
  `dead-letters.php` — ящик событий, которые не удалось разобрать за все попытки.
  **ПОЛНЫЙ список — в разделе «Инвентарь» внизу:** он собирается из `www/env.php` машиной, а
  этот перечень вручную отстал (было 10 названных из 17 фактических) — семь файлов состояния
  существовали, но в карте не значились вовсе.
- Без generated `release.php` state по умолчанию лежит в корневом `data/` вне локального
  DocumentRoot; переменная `BXAPP_DATA_ROOT` задаёт нестандартную раскладку и временный store
  тестов. В release generated private-путь имеет приоритет над окружением;
  deploy исполняет env и доказывает фактическую запись/read-back именно в него.
- Служебное, создаётся само: `lifecycle.lock.php` — общий RW-барьер установки,
  `<имя>.lock.php` — файлы замков (не удалять на работающем
  приложении: снятый замок перестаёт удерживать соседние запросы);
  `state-transition.php` — process-crash-манифест восстановления оборванной межфайловой смены state (без гарантии power-loss: каталоги не fsync)
  (вручную не удалять); `logs/<дата>.log.php` —
  ЖУРНАЛ приложения (сбои, действия людей, фоновая работа) с кодами обращений;
  `<имя>.bad-<отпечаток>.php` — отложенная копия повреждённого состояния.
  **Всё в `DATA_ROOT` обязано быть исполняемым `.php` с exit-префиксом**; штатно это `404 + exit`.
  Legacy допустим для чтения и как автоматически ограниченный rollback-bridge первой выкладки.

## Потоки данных

- **Установка:** Б24 → POST на `index.php` → **криптодоказательство** (`verifyAndAdopt`:
  присланный REFRESH_ID меняем на токены нашим client_secret, домен и портал берём из
  ответа oauth) → под exclusive lifecycle-fence очистка прежнего portal/registration state
  и публикация нового generation → shared-fence точного поколения → `recordAppOwner`
  (**owner = установщик**, всегда доступ, нельзя оставить приложение без owner; действующий
  portal-admin может безопасно передать владение себе с отзывом доступа прежнего owner)
  → `rememberAppUrl` (адрес фиксируется, дальше не берётся из заголовков). Владельца
  зафиксировать не вышло — установка не падает, но на странице результата появляется
  предупреждение: до этого момента внутрь пускает только админов портала.
- **Открытие:** Б24 iframe POST → `index.php` → гейт `session.php` (`user.current` → роль по
  ACL: owner / список / админ портала) → сессия `{uid, role, member_id, install_generation}`
  + токен в `template.html`; весь участок держит shared lifecycle-fence.
  Нет доступа → заглушка «Нет доступа».
- **API-запрос:** фронт шлёт `X-App-Token` → `api/*.php` → `apiBoot()`: метод из белого
  списка → пропуск по заголовку (cookie не принимается) → роль из свежего ACL → запрос со
  своего сайта → лимит частоты → прикладной код, всё под одним generation-fence до shutdown.
  Ответ всегда `{ok:true,...}` либо `{ok:false,error,code}`. До проверки сессии состояние
  установки отдаётся по единой матрице `appInstallationFailureSpec()`: установки не было →
  `409/not_installed`; удалена → `409/uninstalled`; очистка после удаления ещё идёт →
  `503/installation_cleanup_pending` + `Retry-After: 60`; поколение сменилось →
  `409/installation_changed`. Занятый lifecycle-lock отдельно даёт `503/installation_busy`.
- **Самопроверка:** `bash tools/self-check.sh` — единый PHP/JS/tests-гейт; внутри
  `php tests/run.php` печатает число проверок и поднимает встроенный сервер для HTTP-сценариев
  (см. SECURITY.md, раздел «Как это проверяется»). `deploy-prod.sh`
  прогоняет их до сборки release, а после атомарного переключения проверяет боевой адрес:
  страница отдаёт `no-store`, опубликована нужная метка, токены и конфиг снаружи не читаются.

## Забор проверок (кто и чем не даёт выкатить непроверенное)

Это не «просто тесты», а несущая конструкция: без неё правила шаблона превращаются в пожелания.
Ломать её случайно нельзя, а осознанно — только вместе со всеми четырьмя местами сразу.

- **`tools/self-check.sh`** — ОДНА команда для всех: человек запускает руками, деплой зовёт её
  же вместо своих копий проверок, а общий debt-aware `project-self-check.sh` запускает с `--hook`
  для Stop обоих агентов. В режиме хука отказ уходит в stderr с кодом возврата 2 — только это
  Claude Code понимает как «ход заканчивать нельзя».
  Перед прогоном проверяет, что файлы забора вообще на месте. У runtime есть предел: после восьми
  последовательных Stop-блокировок Claude Code может аварийно снять хук; поэтому окончательный
  fail-closed — деплой, который сам запускает self-check и не публикует красный релиз.
- **`tools/docs-contract-check.php`** — сверка документации с кодом (заведено 09.08.2026 по
  находке ревью R3-018/R3-023). Ловит два класса: доки зовут в архитектуру, которую код и гейт
  запрещают (серверный посредник, портальный SDK во фронте), и ссылки на личный каталог заметок
  одного владельца в owner-нейтральном шаблоне. Отрицательные упоминания («такого нет»,
  «запрещён гейтом») законны и пропускаются. Область политики ссылок названа явно: `PORTING.md`
  и `docs/*.md`; `README.md`, `CLAUDE.md` и код в неё пока не входят и потому не считаются
  проверенными.
- **`tools/bounded-output-check.php`** — бюджет выдачи (находка R3-030). Ищет эндпоинты, где
  результат полной выборки портала уходит в ответ без единого признака верхней границы: среза
  строк, страницы, потолка байт или типизированного `too_large`. Забор проверен в обе стороны:
  образец нарушения краснеет, правильный код проходит.
- **`docs/legacy-donor-migration.md`** — как переносить код из приложения-донора с другой
  архитектурой, не таща её в шаблон. Вынесено из `PORTING.md`: рядом с действующим договором
  описание чужой схемы читалось как рекомендация.
- **`tests/run.php`** — раннер: `REQUIRED_SUITES` перечисляет обязательные наборы ПОИМЁННО
  (счётчика мало: два набора-забора удалялись «штатно», оставляя порог довольным), предупреждения
  PHP валят прогон, временный стор убирается сам. В контракт включены не только сам гейт, но и
  `modules_test.php`/`resource_limits_test.php`: удалить проверки готовых модулей и получить
  зелёный итог нельзя. Для каждого suite есть отдельный минимальный объём: заглушка с одним
  зелёным `check()` тоже не проходит. Ранний `exit(0)` из include-набора и пустой обязательный
  набор считаются сбоем; внешний скрипт принимает успех только с итоговым completion-marker.
- **`tests/gate-lib.php`** — предикаты гейта «пользуйся готовым»: разбор структуры кода и
  прослеживание, что лежит в переменной, которую подставили в вызов.
- **`tests/uses_template_test.php`** — гейт по коду ПРОЕКТА (рекурсивно по `www/`), в том числе
  положительные требования: CRUD-мутация портала — через `runOnce()`,
  `callChecked()`/`batchAllChecked()`, точный `readBackChecked()` и `auditLog()`;
  delete/action — через `deleteVerified()`/`actionVerified()` и `auditLog()`;
  список — с пагинацией; input — через `apiBody()`,
  REST Б24 — через `b24()`, frontend transport — через
  `ui.api()`. JS/MJS/CJS ищется во всём `www`, а не только в `www/js`; PHP-like расширения,
  двойные PHP-backup и webroot-конфиги тоже инвентаризируются; require обязан статически вести
  в `.php`, поэтому исполняемый `.dat/.txt` не становится слепой зоной. Browser API ловятся и
  через global/bracket/alias без ложного срабатывания на комментарии. `www/bin` допускает только
  фиксированные CLI-точки с ранним пустым HTTP 404. `www/vendor/` не является слепой зоной;
  зависимости кладутся вне webroot.
- **`tests/gate_test.php`** — проверка САМОГО гейта на образцах обхода плюс сверка списков
  (ядро шаблона, обязательные наборы) и контракта хука. Тем же гейтом закреплено, что
  `www/index.php` остаётся точным готовым security-controller без вставок до session gate, а
  `deploy-prod.sh` начинает с верхнеуровневого fail-closed self-check через путь текущего Bash;

### Куда приходит запрос снаружи

Точка входа сама разбирает запрос ПРИ ЗАГРУЗКЕ: зовёт `apiBoot()` либо сверяет токен

отвечать 404: деплой публикует каталог целиком. Поэтому `НЕТ` в колонке «Забор прямого
HTTP» ниже — это не пометка, а открытый файл: он отвечает по прямой ссылке и никого не
спрашивает.

- **`www/api/logs.php`** — журнал приложения для человека

- **`www/api/task.php`** — ДОЛГАЯ ЗАДАЧА: запуск, ход, отмена, продолжение после закрытия окна
- **`www/api/users.php`** — поиск сотрудников И ОТДЕЛОВ для выдачи доступа (admin-only)
