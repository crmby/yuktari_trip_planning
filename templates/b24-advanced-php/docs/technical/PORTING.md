# PORTING.md — читать ПЕРВЫМ

Этот файл — когда тебя просят **«перепиши/сделай приложение как в этом шаблоне»** или
когда правишь уже собранный из него проект. Здесь **несущие инварианты**: куски, которые
при сыром чтении кода выглядят необязательными, но при выкидывании ломают приложение
**у части пользователей** — как правило у не-админов, которых при разработке под своим
(админским) аккаунтом не видно.

Формат пункта: **СИМПТОМ → инвариант → где в шаблоне → правило в общей базе → как проверить.**

Глубина по install-флоу — [docs/install-flow-diagram.md](install-flow-diagram.md).
Правила «как я работаю» и стек — [CLAUDE.md](../../CLAUDE.md) и [README.md](../../README.md), их не дублирую.

## Сначала реши: приложение открывает НЕ-админ?

Шаблон по умолчанию пускает **владельца (установщика), сотрудников из списка доступа и
администраторов портала**; остальным — заглушка «Нет доступа». Гейт живёт в
[www/api/session.php](../../www/api/session.php), роли — в [www/api/access.php](../../www/api/access.php).
Это правильно для инструмента узкого круга и НЕПРАВИЛЬНО для дашборда/виджета, которым
пользуются все подряд. Отсюда ловушка **в обе стороны**:

- **Открывает не-админ** → обязательны пункты **1, 2, 3** (иначе плашки/пустые данные).
- **Только админ** → шаблон подходит как есть, но пункт **1** всё равно проверь.

Определись до того, как трогать код.

## Несущие инварианты

### 1. Не-админ (или вообще любой) видит «Приложение ещё не установлено» / «…до конца»
- **Инвариант:** установка local-app **организационная, не per-user**. Один
  `BX24.installFinish()` от админа переключает у портала `app.info.INSTALLED → true`, после
  чего пускаются ВСЕ. Handler обязан пройти двухфазно: install POST → сохранить токены →
  отдать installFinish-splash → reload.
- **⚠ Источник истины «установлено» — `app.info.INSTALLED`, а НЕ серверный маркер.** Маркер
  `install_finish_requested_generation` глобален на поколение установки: `installFinish` —
  организационная операция, а не действие каждого сотрудника. Маркер может **рассинхронизироваться**
  с реальностью: reinstall в карточке, перевыдача scope, апгрейд коробки (`ru_selfhosted`)
  сбрасывают `INSTALLED→false` на стороне Б24, а маркер остаётся `finished` → сплэш повторно НЕ
  показываем → не-админ навсегда упирается в нативную плашку (Б24 при `INSTALLED=false` его handler
  даже не зовёт, доступ только админам). Поэтому: когда открыл **подтверждённый текущий
  portal-admin**, сервер не чаще раза в 5 секунд (`$appInfoCooldown` в
  [www/index.php](../../www/index.php)) сверяет `app.info.INSTALLED` живым токеном этого же человека.
  `INSTALLED=true` — поколение помечается подтверждённым; `false` и маркера ещё нет — сплэш
  выдаётся штатно.
  **Автоповтора при «маркер есть, подтверждения нет» НЕТ — и это осознанно:** результат первого
  `installFinish` неизвестен, а повторять установочный эффект вслепую нельзя. В этом состоянии
  админ видит экран «Нужно проверить результат установки» (409) **с кнопкой «Повторить завершение
  установки»**: нажатие снимает маркер поколения (`resetInstallFinish()`) и выдаёт сплэш заново.
  То есть выход из состояния есть, но делает его человек. **Форма кнопки обязана вернуть поля
  забора из текущего портального POST** (`APP_SID`, `DOMAIN`, `AUTH_ID`): её собственный POST
  проходит тот же транспортный забор, и без этих полей админ получает «Приложение открывается
  только из портала», а тупик остаётся навсегда. Выкинете поля «как лишние» — кнопка станет
  украшением, и это не будет видно ни по коду, ни по проверке текста страницы. Сам `app.info` идёт installer-токеном,
  но право запустить его появляется лишь после browser-fence и свежего `user.current` +
  `user.admin` по `AUTH_ID`.
- **Теряется потому что:** `renderInstallFinishPage()` и `BX24.installFinish()` выглядят как
  лишняя заставка — их срезают «для чистоты»; либо доверяют только маркеру без сверки `app.info`.
  Под админом (кто ставил) всё работает, симптом виден только не-админам → всплывает поздно.
- **Та самая плашка — не наша: её рисует сам портал**, когда `app.info` отвечает
  `INSTALLED=false`. Наш код влияет на неё единственным способом — вызовом
  `BX24.installFinish()` на странице установки (`renderInstallFinishPage()` в
  [www/api/b24.php](../../www/api/b24.php), запускается из [www/index.php](../../www/index.php)).
  Поэтому искать причину надо не в разметке, а в том, дошёл ли installFinish.
- **Где в шаблоне:** [www/index.php](../../www/index.php), блок «INSTALL POST handler» (install POST →
  сверка `app.info` → `renderInstallFinishPage()`); `www/api/b24.php` → `saveTokensFromInstall()`,
  `claimInstallFinishForCurrentGeneration()`, `claimAppInfoCheck()`,
  `installFinishRequestedForCurrentGeneration()`/`installFinishConfirmedForCurrentGeneration()`,
  `resetInstallFinish()` (снимается кнопкой админа), `renderInstallFinishPage()`;
  [www/api/b24.php](../../www/api/b24.php) → `renderInstallFinishPage()` (`BX24.installFinish()`).
- **Правило:** `b24-local-app-two-phase-install` (grep по общему INDEX.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект)),
  b24-oauth-install.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект),
  `b24-local-app-app-reinstall-application-token-mismatch` (grep по общему INDEX.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект)),
  `install-finish-once-or-loop` (grep по общему INDEX.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект)).
- **Проверка:** открыть приложение под **НЕ-админом** портала → плашки «не установлено»
  быть не должно. Появилась → под токенами портала `app.info` вернёт `INSTALLED:false`; с self-heal
  чинится автоматически при первом заходе админа (сплэш → `installFinish` → `INSTALLED→true`).

### 2. Не-админу `ACCESS_DENIED` / `ENTITY_NOT_FOUND` при чтении данных портала
- **Инвариант — ОДИН договор, других в шаблоне нет:**
  1. **Данные портала** (`crm.item.*`, `entity.*`, смарт-процессы, поля) — всегда
     **серверным installer-OAuth-токеном** через фабрику `b24()` против `https://<portal>/rest/`.
     НЕ iframe-`AUTH_ID` рядового юзера (не видит app-entity-store → `ENTITY_NOT_FOUND`,
     у не-админа → `ACCESS_DENIED`), НЕ `oauth.bitrix24.tech` (режет scope → `METHOD_NOT_FOUND`).
  2. **Личность смотрящего** — тоже на сервере: портал присылает в POST `AUTH_ID` открывшего,
     сервер меняет его на контекст вызовом `resolveUserContextFromAuth($authId, $domain)`
     (`user.current` + `user.admin` под токеном САМОГО зрителя). Результат — id, признак
     администратора и отделы; на них стоит гейт доступа. Токен зрителя при этом **не
     сохраняется**: перезапись installer-токена ломает фон и привязку плейсментов.
  3. **Фронт в портал не ходит вообще.** Любой запрос браузера — только в свои эндпоинты
     `www/api/*.php` через готовый `ui.api()`; он же кладёт заголовок сессии. Прямой вызов
     портального SDK из фронта запрещён гейтом `tests/uses_template_test.php` («frontend ходит
     в сеть через ui.api»).
- **Теряется потому что:** при сыром чтении кода видно фабрику `b24()`, но не видно, что
  личность берётся отдельным резолвом под чужим токеном. Наивное портирование пробует взять
  её на фронте — и получает у не-админа пусто/отказ, а серверный гейт доступа при этом
  остаётся без входных данных.
- **Где в шаблоне:** [www/api/b24.php](../../www/api/b24.php) → фабрика `b24()`, class `B24` и
  `resolveUserContextFromAuth()`; [www/api/session.php](../../www/api/session.php) →
  `tryCreateSessionFromB24Post()` (гейт по контексту); [www/js/ui.js](../../www/js/ui.js) → `ui.api()`.
- **Правило:** rule-b24-which-token-for-what.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект)
  — какой токен для чего; полный разбор — по grep в
  [внешний ресурс исходного контура] (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект).
- **Донор со своей архитектурой** (в приложении-доноре бизнес-вызовы шли через серверного
  посредника, а личность бралась на фронте) — это НЕ договор шаблона. Как переносить такой
  код, не таща чужую схему: docs/legacy-donor-migration.md (`docs/legacy-donor-migration.md`, внешняя/исходная ссылка; не входит в комплект).
- **Проверка:** под не-админом данные грузятся так же, как под админом; в `www/js/` нет ни
  одного сетевого вызова мимо `ui.api()` — это же проверяет гейт.

### 3. Гейт доступа — дефолт ШАБЛОНА, а не закон приложения
- **Инвариант:** сессию получает владелец (установщик), сотрудник из списка доступа или
  администратор портала; остальным — заглушка «Нет доступа». Решение принимается в
  `tryCreateSessionFromB24Post()` (`www/api/session.php`) по ответу портала на токен САМОГО
  открывающего, роль — из `aclUserRole()` (`www/api/access.php`).
- **Увольнение владельца:** обычным delete owner не снимается, чтобы приложение не осталось
  бесхозным. Действующий portal-admin на вкладке «Доступ» передаёт владение себе; сервер
  принимает только uid самого открывшего администратора со свежим доказательством портала,
  прежнего owner удаляет из ACL и немедленно гасит его сессии.
- **Для приложения «для всех»** гейт ослабляют до «валидный B24-POST с совпавшим DOMAIN +
  двусторонний REFERER-fence», без сверки со списком доступа. Ослаблять — осознанно и целиком,
  а не «на время отладки».
- **Теряется наоборот — тащат лишнее:** переписывая «как в шаблоне», копируют строгий список
  доступа в приложение для рядовых сотрудников → все, кого не внесли, видят заглушку и идут
  жаловаться, что «приложение не работает».
- **⚠ Не путать с двумя другими воротами:** запросы к `api/*.php` пускаются ТОЛЬКО по заголовку
  `X-App-Token`; cookie там не принимается, потому что её приложит и чужой сайт. Служебных страниц
  под cookie в шаблоне больше НЕТ: пересборка плейсментов стала обычным эндпоинтом `api/bind.php`
  с заголовком. Cookie приложения имеет `SameSite=None` для работы в iframe портала, а при прямом
  открытии адреса, наоборот, может не отправиться — поэтому прежняя страница была недостижима для
  самого человека. Если служебная страница всё же появится, ей нужны cookie + роль и сверка
  `Sec-Fetch-Site`/`Origin`.
- **Правило:** `b24-app-admin-only-gate` (grep по общему INDEX.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект)).

### 4. REFERER-fence в session-gate — двусторонний (B24 + self)
- **Симптом если сломать:** между установкой и финальной страницей мигает 403 / приложение
  не открывается сразу после `installFinish`.
- **Инвариант:** iframe-reload после `BX24.installFinish()` приходит с REFERER = наш APP_URL,
  а не с портала. Fence обязан пускать оба: B24-портал И self-APP_URL.
- **Где:** [www/api/session.php](../../www/api/session.php), REFERER-fence в `tryCreateSessionFromB24Post()`.
- **Правило:** `b24-install-finish-reload-self-referer` (grep по общему INDEX.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект)).

### 5. Токены Б24 сохраняем ТОЛЬКО на install И только по ПОДЛИННОМУ POST'у
- **Инвариант:** перезаписывать `b24-tokens.php` только когда POST **аутентичен** И это первая
  установка / формальный (re)install (`INSTALL=Y` | `event=ONAPPINSTALL`) / смена scope от админа
  (`$scopeRefreshOk`). На штатных open'ах — не трогать, иначе admin-токен затрётся токеном
  случайного открывшего. `isAccessExpired` НЕ в условии — протухший access чинится refresh'ем.
- **⚠ Подлинность — по секрету, НЕ по Referer/DOMAIN** (они подделываемы). Гейт `$tokenAuthentic`:
  strict-сверка `application_token` из POST с сохранённым (`hash_equals`), либо — для старой
  установки без него — TOFU строго на тот же домен + валидный `AUTH_ID`. Без этого анонимный
  `INSTALL=Y`-POST перезаписал бы installer-токены (DoS) или увёл `client_endpoint` на чужой домен.
- **Теряется потому что:** наивная save-policy (`isFirst||isFormal||isAccessExpired`, как было до
  секьюрити-раундов) выглядит достаточной — но `isFormal` = `INSTALL=Y`, а его шлёт кто угодно.
  Проверка `application_token` — отдельный слой, его добавляют в аудите и легко «забыть» при
  портировании / скаффолде. `$scopeRefreshOk` тоже часто срезают как «лишнее» → «закисший» scope.
- **Обработчик установки ОДИН — `www/index.php`.** Раньше их было два (второй —
  `www/api/install.php`), и политика записи токенов в них разъезжалась: в запасном
  её однажды не было вовсе. Второй обработчик удалён; если переносишь старый проект,
  где он есть, — удали и там, оставив единственный путь через `index.php`.
  Первая установка принимается ТОЛЬКО по криптодоказательству (`verifyAndAdopt`):
  присланный REFRESH_ID обменивается на токены нашим client_secret.
- **Где:** [www/index.php](../../www/index.php) (`$tokenAuthentic`/`$scopeRefreshOk`/save-gate),
  `www/api/b24.php` → `installPostAuthenticity()`,
  `www/api/b24.php` → `applicationToken()`, `savedScope()`, `backfillApplicationToken()`,
  `saveTokensFromInstall()` (хранит `application_token`+`scope`).
- **Правило:** `rule-b24-verify-application-token` (grep по общему INDEX.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект)),
  `b24-local-app-tokens-save-only-on-install` (grep по общему INDEX.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект)).
- **⚠ Не гейтить installFinish-self-heal (инвариант #1) этим токен-гейтом** — `app.info`-проверка идёт
  нашим installer-токеном и в подлинности POST'а не нуждается; иначе reinstall с новым
  `application_token` не восстановит доступ не-админам. См. rule-audit-contours «НЕ флагать».
- **⚠ Смена ПРИВЯЗКИ (другой портал / пересоздание local-app) — отдельная ветка `verifyAndAdopt`
  (#app-migration).** Тут strict-сверка `application_token` заведомо не пройдёт (он от прежней
  привязки) — поэтому токен усваивается иначе: криптостойким доказательством владения (пробный
  `refresh` присланного `REFRESH_ID` нашим `client_secret` — проходит только для НАШЕГО client_id) +
  domain/member_id СТРОГО из ответа oauth (не из POST) + **admin-гейт** + троттл 30с (DoS). Без этой
  ветки single-tenant НЕ переезжает на другой портал: токен «закисает» на старом, `member_id` не
  меняется, чистка (инвариант #8) не срабатывает. НЕ ужесточать до «только `INSTALL=Y`» (событие
  одноразовое, теряется — открытие из меню обязательный фолбэк). Где: `www/index.php`
  (`$appChanged`/`$portalPosted` → `verifyAndAdopt`), `www/api/b24.php` → `verifyAndAdopt()`,
  `clientId()`, `doRefreshRequest()`. **⚠ marketplace:** тезис держится на per-portal секрете
  LOCAL-app — при публикации в marketplace модель усвоения пересмотреть. KB:
  `b24-local-app-portal-migration-self-heal` (grep по общему INDEX.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект)),
  rule-audit-contours «НЕ флагать» #app-migration.

### 7. `.htaccess` НЕ используем by design — защита и её следствия
- **Политика:** приложение **не полагается на `.htaccess`** (mod_rewrite / `AllowOverride` /
  `Deny`). На shared-хостингах (beget, sprinthost, ihc) и коробках `AllowOverride` часто
  урезан — `.htaccess` молча не применяется, и всё, что на него завязано, отваливается без
  ошибки. В шаблоне `.htaccess` нет вовсе. Следствия, которые нельзя терять:
  - **State защищён без `.htaccess deny`:** deploy хранит его в private-каталоге
    `~/<DOMAIN>/.bxapp/<slug>/shared/data` вне webroot и не создаёт `release/data` symlink.
    Все state-файлы начинаются с `<?php http_response_code(404); exit; ?>` + JSON
    (через `www/api/store.php` `storeRead`/`storeWrite`, атомарная запись + `chmod 600`).
    Старый `<?php exit; ?>` reader понимает только ради rollback совместимости. Прямой URL
    `/data/...` обязан дать 404; `env.php` ничего не выводит. Не хранить state открытым `.json`.
  - **Handler URL с `/index.php` и `template.html` (пункт 6)** — тоже следствия отсутствия
    `.htaccess`: без mod_rewrite «папочный» URL даёт 403 (`DirectoryIndex` без `index.php`),
    а `index.html` перехватил бы статику в обход сессии.
- **Не «чинить» добавлением `.htaccess`.** Соблазн положить `.htaccess` (DirectoryIndex/deny)
  — ловушка: на другом хостинге не сработает, а ты будешь думать, что защищён / что URL
  починен. Не отдаётся — правь handler URL и раскладку, `.htaccess` не добавляй (то же в
  [CLAUDE.md](../../CLAUDE.md), секция «Apache, не nginx»).
- **Правило:** `b24-app-single-tenant-pattern` (grep по общему INDEX.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект))
  (секции «Защита через PHP-exit», «Handler URL»).

### 8. Смена привязки обнуляет сессии + портал-специфичный data/; пагинация во всём списочном
- При смене **портала** (`member_id`) ИЛИ пересоздании local-app (`client_id`, #app-migration) старые
  сессии сбрасываются — не выкидывать. Полную чистку портал-специфичного `data/` (права по ID, кэши
  entity/SP-id, ID БП-шаблонов/Диска) вешать ТОЛЬКО на смену ПОРТАЛА (`$portalMigrated`): при
  пересоздании app на том же портале ID валидны. Токен новой привязки усваивает `verifyAndAdopt`
  (инвариант #5). Триггер чистки — ПОСЛЕ усвоения (иначе `member_id` ещё старый).
- Любой вызов, способный вернуть >1 записи (списки, CRM, задачи, `lists.element.get`,
  батчи) — **сразу с циклом до конца**.
  `rule-always-paginate-list-methods` (grep по общему INDEX.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект)).

### 9. Адрес приложения не хардкодят, страницы-инструкции в шаблоне нет
- **Инвариант:** адрес приложения берётся в три шага, и порядок важен:
  `APP_URL_OVERRIDE` из `env.php` → сохранённый при установке `app_url`
  (`rememberAppUrl()` кладёт его в `data/state.php`) → и только пока приложение
  не установлено — автоопределение из заголовков запроса. После установки
  заголовок `Host` на адрес уже не влияет: на этом хостинге он подделывается
  через `X-Forwarded-Host`, а от APP_URL зависят проверка «свой источник», путь
  cookie и адреса плейсментов.

- **Чего в шаблоне намеренно НЕТ:** отдельной страницы с шагами установки. Раньше тут жил
  `init.php`, который печатал ссылки и правил `env.php` из браузера. Убран 29.07.2026 по
  решению владельца: инструкция в браузере устаревает молча и её всё равно никто не открывает,
  а половина её работы дублировала то, что код делает сам.
- **Куда переехало:**
  - ссылки для карточки local-app, скоупы и команда планировщика — в вывод `deploy-prod.sh`,
    оттуда агент отдаёт их человеку **в чат** в момент, когда просят установить;
  - подстановка адреса — не нужна, автоопределение уже в `env.php`;
  - создание `data/` с правами 700 — делают `index.php` и `api/store.php`;
  - креды приложения клиента — отдельный `data/creds.php`, который безопасно пишет
    `bash scripts/set-creds.sh`; `env.php` на хосте для этого не правят, см. «Перенос» в README.
- **Грабля:** хост берётся из заголовков `X-Forwarded-Host`/`HTTP_HOST` — на фронт-прокси
  (NetAngels) они подменяемы, поэтому на них нельзя строить авторизацию.
  `netangels-http-host-spoofable-via-forwarded` (grep по общему INDEX.md (`[внешний ресурс исходного контура]`, внешняя/исходная ссылка; не входит в комплект)).

### 10. Состояние правится только под замком — `storeUpdate`, а не «прочитал → записал»
- **Инвариант:** любое изменение файла в `data/` идёт через
  `storeUpdate($файл, function (array $было): array { ... })`. Он держит эксклюзивный
  замок от чтения до записи, поэтому параллельный запрос дождётся и увидит уже
  изменённое. Замок не взялся за 5 секунд — исключение и **ни одной записи**.
- **Почему это несущее.** Приложение живёт в iframe: портал открывает несколько запросов
  разом. При старой схеме два из них читали одно состояние и по очереди писали целиком —
  правка первого исчезала. Живой случай: один запрос обновил протухший `access_token`,
  второй одновременно отметил пройденную установку; кто записал вторым, тот и затёр.
  Для пользователя это выглядит как случайный разлогин или повторный сплэш установки.
- **Токены сливаются, а не перезаписываются:** `B24::persist()` пишет поверх свежего
  состояния только те поля, которые изменил ЭТОТ запрос (сравнение со снимком при чтении).
- **Снятые функции.** `saveSessions()` и `aclSave()` из шаблона убраны — они и провоцировали
  гонку. Переносишь новый `store.php` в старый проект — замени их вызовы на
  `storeUpdate` / `aclUpdate`, иначе будет «функция не найдена».
- **Повреждённый файл — стоп, а не «пусто».** Нечитаемое состояние больше не выглядит как
  «приложение не установлено» (иначе следующая же установка затрёт остатки токенов):
  рядом откладывается копия `<имя>.bad-<отпечаток>.php`, а запрос падает с внятной
  страницей. Оригинал остаётся на месте — до разбора человеком.
- **Грабля:** замок живёт в отдельном файле `<имя>.lock.php` рядом с состоянием. Удалять
  файлы в `data/` по маске (чистка, ручной `rm data/*`) во время работы приложения нельзя:
  снесённый замок перестаёт удерживать соседние запросы.

### 11. Деплой публикует release атомарно, состояние общее
- **Инвариант раскладки:** публичный `~/<DOMAIN>/www/<slug>` — symlink `live` на каталог из
  `~/<DOMAIN>/.bxapp/<slug>/releases/`. Постоянный store физически находится вне webroot в
  `~/<DOMAIN>/.bxapp/<slug>/shared/data`; `release.php` передаёт этот путь коду, публичного
  `data/` symlink нет.
- **Конфиг относится к коду:** у каждого release свой `env.php`. Обычная выкладка копирует
  активный серверный конфиг, первая берёт локальную заготовку, а явный `--push-env` заменяет его
  локальной версией. Shared data при смене release не копируется и не откатывается.
- **Совместимость env версионируется:** `BXAPP_ENV_SCHEMA` — положительный целый литерал.
  Изменилась исполняемая логика или состав обязательных `define` — увеличить ровно на 1; простая
  смена значений scopes/placements/URL/log-level версии не требует. Обычный deploy при отсутствии,
  нечисловом значении или несовпадении schema останавливается до публикации. Для перехода сначала
  перенести клиентские значения в новый env, затем осознанно применить `--push-env`.
  Value-only изменение тоже требует `--push-env`, если его надо доставить на сервер, но schema
  при этом не повышается.
- **Публикация:** серверный lock не даёт двум деплоям менять `live` одновременно. Новый release
  сначала полностью собирается, затем ссылка переключается атомарно; красный read-back возвращает
  прежнюю ссылку. Активный, предыдущий и ещё три свежих release-каталога — ограниченная история
  для разбора и отката, не временный staging rsync.
- **Формат state раскатывается в две фазы:** deploy вызывает `storeDecode()` предыдущего release
  на canary нового формата. Пока rollback-target не умеет его читать, generated `release.php`
  включает legacy-writer; следующая выкладка автоматически включает `404 + exit`. Private layout
  и внешний HTTP 404 от этой переходной фазы не меняются.
- **Legacy не мигрирует молча:** физический каталог в `www/<slug>` может содержать живые записи.
  Сначала остановить iframe, cron и события, затем запускать только с двумя подтверждениями:
  `--migrate-legacy --confirm-quiesced`. Обычный деплой при такой раскладке обязан остановиться.

## Быстрый пост-чек после портирования / переработки

- [ ] Открыл приложение **под НЕ-админом** — нет плашки «не установлено (до конца)» (п.1)
- [ ] Под не-админом данные портала грузятся (п.2), либо он осознанно заблокирован (п.3)
- [ ] После `installFinish` нет мигания 403 — REFERER-fence двусторонний (п.4)
- [ ] Токены не перезаписываются на штатных open'ах (п.5)
- [ ] Главный UI — `template.html`; handler URL в карточке оканчивается на `/index.php` (п.6)
- [ ] State лежит вне webroot; новые `.php` штатно начинаются с `404 + exit`, а transitional
      legacy-writer разрешён только generated-флагом после проверки previous; `/data/...` даёт 404;
      `env.php` ничего не выводит; **`.htaccess` в проекте НЕТ** (п.7)
- [ ] Все списочные вызовы Б24 листаются до конца (п.8)
- [ ] `APP_URL` идёт из `APP_URL_OVERRIDE`/автодетекта, не захардкожен; страницы с шагами установки нет (п.9)
- [ ] Все изменения `data/` идут через `storeUpdate`/`aclUpdate`; вызовов `saveSessions`/`aclSave` не осталось (п.10)
- [ ] Подлинность install-POST проверяется на ВСЕХ публичных входах одной функцией; дозапись `application_token` — только после подтверждения админом своего портала (п.5)
- [ ] Запросы фронта к `api/*.php` идут с заголовком `X-App-Token`; cookie для эндпоинтов не принимается нигде (п.3)
- [ ] В `DATA_ROOT` нет файла без `.php` и исполняемого exit-префикса; `404 + exit` обязателен,
      кроме автоматически ограниченного rollback-bridge (п.7, п.11)
- [ ] На сервере `www/<slug>` — live-symlink, релизы отдельные, private shared не опубликован;
      legacy переносился только после quiesce (п.11)
