# Защита приложения: что уже вшито и чего не надо изобретать

Документ отвечает на три вопроса: **какой уровень защиты нужен** приложению Битрикс24 такого
класса, **что из этого шаблон делает сам**, и **что обязан сделать разработчик** конкретного
приложения. Написан после разбора наших боевых проектов и архива ревью: почти всё, что ревью
находило раз за разом в разных проектах, здесь либо закрыто кодом, либо проверяется тестом.

---

## 1. От чего вообще защищаемся

Приложение — не публичный сайт. Это внутренний инструмент на 5–100 сотрудников одного портала,
который работает с данными CRM клиента. Отсюда реалистичная модель угроз:

| Угроза | Насколько реальна | Чем закрыта |
|---|---|---|
| Адрес приложения узнал посторонний и открыл его | **Высокая.** HANDLER-URL публичен, его видно в карточке приложения и в логах | Сессия выдаётся только после подтверждения личности у портала; остальным заглушка |
| Сотрудник портала, которому доступ не давали, открывает приложение | **Высокая.** Ссылку пересылают друг другу | Список доступа: владелец + явно добавленные + админ портала |
| Доступ отозвали, а человек продолжает работать | **Высокая.** Обычная ситуация при увольнении | Права перечитываются на КАЖДОМ запросе, пропуска гасятся сразу; перевод из разрешённого отдела ловит фон за десять минут. Если увольняется owner, недавно подтверждённый portal-admin передаёт владение себе на вкладке «Доступ» — прежний owner удаляется из ACL и его сессии отзываются |
| Чужой сайт выполняет действие от имени открытого приложения | **Средняя.** Требует, чтобы сотрудник открыл чужую страницу, пока работает в портале | Мутации только по заголовку `X-App-Token`, cookie не принимается; проверка `Origin`/`Sec-Fetch-Site` |
| Соседнее приложение на общем origin пытается забрать пропуск | **Средняя.** Один скомпрометированный путь не должен открыть остальные | `'self'` исключён из `frame-ancestors`, фоновые запросы страницы запрещены, same-origin top-level popup отклоняется по Fetch Metadata. Браузер без этих заголовков не даёт полной изоляции путей — для такого окружения нужен отдельный origin |
| Файлы состояния (токены, сессии) скачивают по прямой ссылке | **Высокая.** Имена предсказуемы | Shared store физически вне webroot и не связан с release; каждый файл — `.php` с `404 + exit`, права 0600; deploy требует точный HTTP 404 |
| Посторонний присылает поддельную установку и занимает приложение | **Средняя.** Адрес установки публичен | **Любая** запись токенов — только по криптодоказательству: присланный REFRESH_ID обменивается на токены нашим client_secret, домен и портал берутся из ответа oauth |
| Голый `AUTH_ID` заставляет публичный handler ходить в портал / `app.info` вызывается при каждом открытии | **Средняя.** Занимает worker и расходует REST-лимит | До проверки токена обязателен transport-fence (`APP_SID` + точный сохранённый `DOMAIN` + portal/self `Referer`); `app.info` — только после свежего `user.current + user.admin` текущего portal-admin и с атомарным single-flight-cooldown 5 с (не кеш: после реальной переустановки состояние должно перечитаться на следующем открытии). Само опознание ограничено дважды: лично (адрес + токен открывающего, 30/мин) и потолком на адрес (120/мин) — один сотрудник не должен закрывать вход всему офису за общим внешним адресом |
| Поддельное событие портала (обновление сделки, удаление приложения) | **Средняя.** Адрес обработчика публичен | `api/event.php`: сверка `application_token` и портала, ответ 200 только после сохранения события |
| Нас встраивают в чужую страницу и перехватывают нажатия | **Низкая**, но цена ошибки высокая | `frame-ancestors` — до установки маски порталов Битрикса, после установки ровно свой домен; эндпоинты — `frame-ancestors 'none'` |
| Портал отвечает «слишком много запросов», данные приходят наполовину | **Высокая.** Адрес хостинга общий для всех наших приложений | Повтор с растущей паузой на `QUERY_LIMIT_EXCEEDED`/5xx; неполная выборка бросает ошибку, а не выдаёт себя за полную |
| Два запроса одновременно обновляют токен и убивают друг друга | **Высокая.** Портал открывает запросы пачками | Обновление токена под замком с перечитыванием: второй запрос берёт готовый результат первого |
| Повторный клик/ретрай создаёт вторую запись в CRM | **Очень высокая.** Происходит постоянно | `runOnce()` возвращает результат завершённой попытки; после любого сбоя оставляет `unknown` и запрещает слепой повтор до read-back |
| Параллельные запросы затирают состояние друг друга | **Очень высокая.** Портал открывает несколько запросов разом | `storeUpdate()` — чтение и запись под одним замком |
| Токен утёк в журнал вместе с текстом ошибки | **Высокая.** Пишут дамп ответа, не думая, что там токен | `maskSecrets()` на всех путях записи в журнал |
| Приложение завалили запросами | **Низкая.** Внутренний инструмент | Ограничение частоты на ИЗМЕНЯЮЩИЕ запросы — 120 в минуту на сотрудника. Чтения намеренно не считаются: их шлёт пачками каждая открытая вкладка, и счётчик выстроил бы приложение в очередь на замке файла. Тяжёлому читающему эндпоинту лимит задаётся явно: `apiBoot(['rate' => [30, 60]])`. Адрес для анонимных счётчиков берётся из `REMOTE_ADDR`: `X-Forwarded-For` пишет сам клиент, поэтому ему верят только из рук доверенного прокси (`APP_TRUSTED_PROXIES`, по умолчанию пусто). Иначе одним заголовком обходился бы любой лимит, а подставив чужой адрес, можно было бы закрыть вход именно ему |

**Чего мы намеренно НЕ делаем** (это избыточно для внутреннего приложения и только усложняет):

- шифрование состояния на диске мастер-ключом — ключ лежал бы рядом, на shared-хостинге это
  видимость защиты, а не защита; вместо этого файлы закрыты от HTTP и правами 0600;
- собственная двухфакторная аутентификация — вход и так через портал Битрикса;
- сложная система привилегий с матрицей на каждый объект — трёх ролей (`view`/`edit`/`admin`)
  хватает; когда не хватает, это признак, что приложение переросло шаблон;
- защита от подбора паролей, капча, блокировки по IP — паролей у приложения нет.

## 2. Что шаблон делает сам

### Вход и права

- `apiBoot()` в `www/api/http.php` — единственная дверь любого эндпоинта. Проверяет метод, пропуск,
  роль, частоту, ставит заголовки. Эндпоинт, начинающийся с `apiBoot()`, защищён целиком.
- Пропуск принимается **только из заголовка `X-App-Token`**. Cookie выдаётся с `SameSite=None`
  (иначе приложение не работает в iframe) и потому не годится как доказательство — чужой сайт
  приложил бы её к своему запросу.
- Роль берётся **из списка доступа на каждом запросе**, а не из самого пропуска: снятие прав
  действует немедленно.
- **Отделы** — единственное, что берётся из снимка в пропуске: состав отдела живёт в портале, и
  каждый запрос за ним не сходишь. Поэтому перевод сотрудника ИЗ разрешённого отдела ловит фон:
  тем же ответом `user.get`, которым проверяется блокировка, приходит `UF_DEPARTMENT` — состав
  обновляется, роль пересчитывается, а у кого оснований не осталось, пропуск гасится
  (`sessionApplyPortalDepartments`). Окно — до десяти минут, а не до восьми часов, как было до
  09.08.2026, — **только при заведённом планировщике**: гасит пропуска фон, и без него пропуск
  заблокированного живёт весь срок (до 8 часов). Молчащий больше часа фон «Состояние» показывает
  тревогой. Про кого портал промолчал, того не трогаем: один сбой выборки иначе отобрал бы
  доступ у всех разом.
- Owner нельзя удалить, оставив приложение без владельца. Для увольнения owner действующий
  portal-admin открывает вкладку «Доступ» и передаёт владение себе: сервер принимает только
  uid самого администратора с доказательством `user.current + user.admin` не старше пяти минут,
  атомарно убирает прежнего owner из ACL и отзывает его сессии.
- Пропуск привязан к порталу (`member_id`). Переустановили приложение на другой портал — старые
  пропуска мертвы.
- `roleAtLeast($role, 'edit')` — одно сравнение ролей на всё приложение.

### Состояние

- `storeUpdate($файл, fn)` — единственный способ менять состояние. Замок на весь цикл
  «прочитал → поправил → записал», запись через временный файл и переименование, права 0600.
- Повреждённое состояние **не считается пустым**: работа останавливается, копия откладывается
  рядом. Иначе первая же запись затрёт остатки токенов.
- Shared store на сервере физически вне webroot. Все его файлы — `.php` с
  `http_response_code(404); exit;`, включая журналы, замки и карантинные копии;
  прежний `<?php exit;?>` принимается reader'ом только для бесшовной миграции.

### Действия и повторы

- `auditLog($действие, $детали, $uid)` — кто что сделал. В Битриксе любой наш вызов выглядит как
  действие установщика, поэтому наш журнал — единственное место, где остаётся настоящий автор.
- `runOnce($ключ, fn)` — завершённая операция на повторе возвращает сохранённый результат. Любой
  `Throwable` оставляет `unknown`: внешнее действие могло уже пройти, поэтому сначала нужен
  read-back, и лишь для подтверждённо невыполненного — `runOnceForget($ключ)` и новый вызов.

### Работа с порталом

- `$b24->callChecked()` — отказ портала становится исключением, а не «пустым результатом»,
  который поедет дальше по коду.
- `$b24->batchAll()` — пакет любого размера, режется по 50, ошибки отдельных команд возвращаются
  (частичное применение — это факт, а не сбой).
- `$b24->fetchAll()` — весь список курсором по ID, а не первая страница и не `start`, который на
  живом списке пропускает и дублирует записи.

### Секреты

- `maskSecrets()` — маскирует по вхождению слова в имя поля (`secret_token`, `userAccessToken`
  тоже попадают), плюс типовые формы в тексте: `ключ=значение`, `print_r`, `serialize`,
  `Authorization: Bearer`.
- Наружу отдаётся человеческий текст и код обращения; техническая правда — в защищённый журнал.
- Адрес приложения фиксируется при установке (`rememberAppUrl()`), а не берётся из заголовка
  запроса: на этом хостинге `Host` подделывается через `X-Forwarded-Host`.

## 3. Что обязан сделать разработчик приложения

1. **Начинать эндпоинт с `apiBoot()`.** Не писать свои проверки пропуска — их уже написали.
   Образец: `www/api/settings.php`, копировать его.
2. **Разбирать вход через `apiStr/apiInt/apiEnum/apiList`.** Всё, что уходит в REST-вызов,
   обязано пройти проверку. «Взял из тела и передал в Битрикс» — способ получить в CRM то, чего
   никто не просил.
3. **Мутации CRM оборачивать в `runOnce()`** с осмысленным ключом и **писать `auditLog()`**.
   Если `runOnce()` вернул `['unknown' => true]` — прошлая попытка оборвалась между самим
   действием и отметкой «сделано» (процесс убили, хостинг оборвал). Повторять вслепую нельзя:
   проверьте по данным портала, прошло ли действие, и только если НЕ прошло — снимите метку
   (`runOnceForget($ключ)`) и повторите. Такие операции видны в «Настройки → Служебное».
4. **Менять состояние только через `storeUpdate()`**, никогда не «прочитал → записал».
5. **Списки портала брать через `fetchAll()`**, пакеты — через `batchAll()`.
6. **Не отдавать наружу текст исключения.** Для этого есть `apiFailFromThrowable()`.
7. **Добавить свои проверки в `tests/`** — по одной на каждое правило, которое легко нарушить
   в этом приложении. Деплой их прогоняет и не выпускает красный код на бой.

## 4. Как это проверяется

`php tests/run.php` — точное число печатает сам раннер (здесь его намеренно не дублируем: вбитое
руками число устаревает первым). Больше трети проверок бьют по живому HTTP: поднимается
встроенный сервер и эндпоинты проверяются снаружи, как из браузера. Проверяются, в частности:

- публичный путь `data/...` отвечает ровно HTTP 404 и не отдаёт содержимое;
- эндпоинт без пропуска отвечает отказом, и отказ не кэшируется;
- одной cookie недостаточно ни для чтения, ни для изменения;
- пропуск с другого портала не действует;
- снятие прав действует немедленно, пропуск гасится;
- запрос с чужого сайта отклоняется;
- метод не из списка, нечитаемое тело, отсутствующее поле, слишком большое тело — понятные отказы;
- поток запросов упирается в ограничение частоты;
- секрет в журнале замаскирован;
- повтор завершённой операции возвращает прежний результат, а сбой даёт `unknown` и не запускает
  внешнее действие снова без read-back + `runOnceForget`;
- поддельная установка отклоняется и не создаёт состояние;
- событие с чужим токеном приложения отклоняется и не попадает в очередь;
- изменение без признаков источника и с соседнего сайта хостинга отклоняется;
- недостаточную роль отсекает сам единый вход, а не эндпоинт;
- подлинное событие принимается и целиком попадает в очередь (проверка «отказ работает» без
  проверки «приём работает» ничего не стоит: эндпоинт, отклоняющий всё, прошёл бы её на отлично);
- креды читаются из отдельного файла, который деплой не синкает, и сам файл закрыт от HTTP;
- при незаполненных кредах человек видит «приложение ещё не настроено» с конкретным действием,
  а не общий отказ подтверждения;
- **готовое не обходят**: эндпоинт без `apiBoot()`, запись состояния мимо стора, свой `curl` в
  портал, свой формат ответа, браузерный `confirm`, сырой текст исключения в журнале и файл в
  `api/` без упоминания в карте — красный результат и остановленный деплой. Та же инвентаризация
  видит JS/MJS/CJS в любой папке `www`, browser API через alias/bracket, PHP-like/backup-расширения,
  non-`.php` require и webroot-конфиги; `env.php` до auth ограничен отдельным structural-гейтом;
  произвольный PHP в `www/bin` и штатный bin без раннего
  пустого HTTP 404 тоже останавливают прогон. Корневой `www/index.php`, где install/lifecycle
  неизбежно идут до session gate, защищён точным content invariant и отдельным ask-правилом.

`bash deploy-prod.sh` прогоняет это до сборки release и **после атомарного переключения** проверяет
боевой адрес: он опрашивает его, пока НЕ НАБЕРЁТСЯ 24 ответа подряд с новой меткой и `no-store`
и пока стабильное окно не перекроет `realpath_cache_ttl + 15` секунд (иначе часть PHP-FPM-воркеров
ещё отвечает из старого release, и «зелёный» read-back доказывал бы смесь версий), оба canary под
`data/` получают ровно 404, а `env.php` не отдаёт тело. Красный read-back возвращает `live` на прежний release.
Перед switch deploy исполняемо проверяет, читает ли rollback-target новый `404 + exit` формат.
Если нет, переходный release пишет legacy-префикс ещё одну выкладку; это не даёт общему state стать
нечитаемым после автоматического отката, а отсутствие публичного `data` всё равно обеспечивает 404.
